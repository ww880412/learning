Holon · AI 交付的四道验收防线
这篇文章讲什么？

代码写得快了，瓶颈变成谁来验收

文章用一个使用 Holon 的团队做例子，讲代码写完后的四道验收防线。

所有结论以可复核的执行证据为准。

团队的项目包含 Node.js 服务端、C++ 底层通信库、Swift 与 Kotlin 客户端，以及音频硬件协议。

四道防线：主干交付的角色分工与验收分流；现场故障与客诉排查；长周期环境巡检；端到端测试的自愈与语义裁决。

Holon 博客 开头、「自动交付流的验收赤字」
上游流水线源源不断产生 PR
下游大家不敢把它们推向生产
只自动化写代码审查、环境测试、端到端验证、排障全留给人
结果前端省下的时间，在下游验收和排障里耗光
不验证就发系统容易被隐蔽的回归问题拖垮
文章的方向把验收也自动化，并留下证据
为什么需要验收防线？

只自动化写代码，省下的时间会在下游耗光

文章把这种状态叫「验收赤字」（产出快于能证明它没问题的速度）。

难题变成：怎么证明改动没有破坏性，谁对质量负责。

「自动交付流的验收赤字」
盲区共享理解有偏差，代码错，测试也顺手迎合这个偏差
对策审查和验收由别的角色做
无意义的绿灯断言恒真、忽略异常、只测虚构 Mock
对策以执行证据为准，不以 CI 绿灯为准
缺乏监督同一个人既写又审，评估流于形式
对策职责分离，标准统一
一个 Agent 包办为什么不行？

自己写代码又自己写测试，会共享同一个盲区

单 Agent 闭环（同一上下文里理解需求、改代码、写测试、审查、合并）在小脚本里看似顺畅。

在中大型工程里，「很容易」出现左边三个问题。

「为什么单 Agent 自编自导自演行不通？」
验收的前提是什么？

需求和 Bug 必须写进 Issue，不留在 Prompt 里

理由一：编码跨多轮，常由新会话接手，要有记录才能对齐目标。

理由二：验收 Agent 不参与编码，没有独立需求就只能听代码作者的描述。

任务进入开发前，先要有明确且可测试的需求或 Bug 描述。

「前置原则：需求与 Bug 绝不能停留在 Prompt 里」
角色怎么分？

灵活性留在本地，统一标准留在公共环节

Reviewer Agent 按统一规范审 PR，给出疑点和代码证据，不直接改代码。

QA Agent 不依赖编码 Agent 的自我说明，直接拉原始需求验证。

「本地编码与团队统一验收」
QA Agent 怎么验？

按改动性质分流，不全部送去跑全量测试

不需运行时的查代码；需要运行时的进隔离环境；要等上线的先挂起。

挂起不轮询：部署系统发出就绪事件时，才唤醒对应任务回测。

原文强调：代码合并不等于发布，发布也不等于验证通过。

人工兜底时，Agent 整理好版本号、前置条件、复现步骤、预期表现和关键疑点，交给工程师最终确认。

「验收的分流机制」及原文分流图

动态验证的真实例子

测试工具本身也可以由 QA Agent 来写

这是该团队的一次实践。

交付物不是「我修好了」，而是抓到的拦截日志。

「验收的分流机制」独立环境动态验证
一个改动会被哪道防线拦下？

不同的缺陷，要靠不同的防线才拦得住

补充：教学示例；防线分工见原文各节
第二道防线：现场故障

上报一触发就排查，赶在现场消失之前

传统路径：客服转技术支持，再提单排期，等研发去调日志已过数日。

排查 Agent 产出两份东西：给研发的 Issue，给客服的简要说明。

Agent 判断的候选原因包括：网络抖动、接口异常、蓝牙协议握手超时、本地状态不一致。

原文举的客服说明例子：特定系统版本蓝牙重连超时，临时可重启应用恢复，正式修复正在排期。

「第二道防线：现场故障与客诉排查闭环」
缺陷运行数小时后的轻微内存泄露
巡检看进程内存趋势
缺陷长连接在网络波动下静默假死
巡检查双向心跳与重连
缺陷缓存状态逐步漂移
巡检对比服务端与客户端的数据版本
缺陷偶发的跨端并发竞争
巡检扫描不中断运行的警告和隐式错误
第三道防线：长周期巡检

有些缺陷只在环境跑了几小时后才出现

单元测试和单次 CI 太短，暴露不了这些问题。

巡检 Agent 挂在常驻测试环境上，按周期（如每数小时）检查活跃实例。

「第三道防线」；左右配对是学习搭子按原文清单排的，原文未逐一对应
第四道防线：端到端测试

测试失败时，先分清是 Bug 还是用例过时

两个痛点：界面微调就让用例脆断；生成式输出难以用固定断言比对。

输出不固定时，测试 Agent 当语义裁判（LLM-as-a-Judge）。

语义裁判的依据：业务意图、上下文边界、事实准确性、安全要求。

它看逻辑是否自洽、意图是否达成、有没有违规或有害输出，不看字面是否一致。

「第四道防线：E2E 测试的自愈与语义裁决」
四道防线靠什么跑起来？

等待时 Agent 休眠，事件来了再唤醒

原文认为这些机制很难在单次运行的聊天脚本或命令行死循环里可靠运转。

状态与证据持久化，所以等几小时或环境重启后仍能接着做。

唤醒时只注入当前决策所需的最小上下文。

生产发布、关键配置变更始终保留人工确认（Operator Gate）。
