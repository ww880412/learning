清单与插件格式
manifest、索引条目、派生数据和安装链路

插件 manifest

  • 插件的 package.json 必须声明 dsh.bundle: { "patch": "./cordis.patch.yml" }；只声明 dsh.client 的不能安装，这是投稿被拒的头号原因。带前端界面的再加 dsh.client: { "platform": "web" }。
    • 根目录放 cordis.patch.yml，内容是 - insert: [{ id, name }]。启用或禁用就是往 profile 的补丁层写 - id: … disabled: true|false，DSH 热加载约 1 秒生效。
    • 宿主版本要求写在 engines.dsh，或写成 @deepseek-ai/dsh-* 的 peer 范围。peer 范围要显式写预发布分支，例如 >=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0，否则会静默排除 rc 版。

索引条目

data/plugins/<owner>__<repo>.yml，monorepo 子包命名为 <owner>__<repo>--packages-x.yml。字段如下：

  • url：必须与仓库完全一致。
  • name：显示名；子包用 owner/repo#sub。
  • category：23 类之一。
  • description.en：唯一必填字段。
  • description.zh：可选，维护者会补。
  • tarball：可选；必须是 GitHub Release 上的 https .tgz。用 latest/download/ 时资产名不能带版本号，否则发下一版就 404。

派生数据

都按 url 做键：

  • data/capabilities.json：version、spec、capabilities[]、redLines[]、scannedAt、tool。
  • data/stars.json、data/downloads.json、data/added-dates.json、data/screenshots.json。
  • 能力数据的写入规则在 scripts/lib/capabilities.mjs：只写真正读到的事实；下载失败、扫描器崩溃或格式看不懂时一律留空，界面显示「未检出」，不写成「安全」。扫描器输出带 schemaVersion，换扫描器只需改这一个文件。

发布形态

  • scripts/publish-catalog.mjs 把 plugins.json 发成 npm 包 dsh-plugin-catalog。原因有两个：中国大陆访问 GitHub Pages 慢，npm 镜像快；目录也因此有了版本号，出错可以回滚。
  • scripts/lib/market-index.mjs 按官方「format 1」生成索引，并用 @deepseek-ai/dsh-plugin-market-index 同一套解析器校验。
  • format 1 要求每个条目有 npm 包名、精确版本和发布时间，所以只在 GitHub、不发 npm 的那一半插件暂时进不了官方索引。
  • 宿主拉索引的超时是 15 秒，因此描述截到 160 字。
  • 索引地址：https://cdn.jsdelivr.net/npm/dsh-plugin-catalog/index.json（见 dsh-market README）。

dsh-market 的安装链路

  • 来源优先级：经仓库验证的 npm 包 → 作者 Release 的预构建 tarball → 整仓源码。tarball 必须属于条目自己的仓库，防止「名字写可信仓库、实际装别处的包」（src/sources.ts）。
  • 构建脚本默认不执行；安装接口只接受同源 POST；重启接口只接受环回地址。
审核流程
contributing.md、scripts/check-submission.mjs、.github/workflows/*

CI 只校验形式

  • 仓库里存在 dsh.bundle（遍历整棵树查找）。
  • 仓库创建满 1 天。提交数门槛已于 2026-09-03 取消，理由是它衡量的是开发习惯，不是质量。
  • 仓库存在且未归档，并且不是 DSH 本身。
  • 每个 PR 最多新增 3 条（依据他们统计的历史 PR 分布）。
  • PR 改动了哪些既有条目，gate 会逐条列出来供追问（起因是曾两次有 PR 偷改别人的描述）。

维护者合并前读源码

看 8 点：

  • 描述里的数字和 API 是否与代码一致（夸大是被打回的主因）。
  • 分类是否合理。维护者直接改，不会因此打回。
  • 是不是真实可用的代码。
  • 是否与已有条目重复。按「谁更好」决定，不是先来先得。
  • 源码里有没有混淆、凭据外传或异常的安装期行为。这只是常识检查，不算安全审计。
  • PR 有没有动无关条目。
  • 是否是只有依赖清单的纯聚合包，这种不收。
  • 聚合包的依赖是否指向原作者。

持续维护

  • decay-scan.yml 每周一扫一次，标记 gone、archived、dormant、subpath-gone、unbundled 五种状态，汇总到一个跟踪 issue；删除由人决定。
  • held-rescan.yml 每天把作者已修好、但仍挂着 held: author 的 PR 列出来，避免被遗忘；它不会自动去掉标签。

最值得抄的 5 个机制 5
对企业工作台插件市场
01

一插件一文件的索引，CI 只管形式，人工管真实性

awesome-dsh-plugin

  • 一个插件一个 YAML，README 和网站都由脚本生成，所以 PR 之间不会冲突。
  • CI 检查 manifest、仓库年龄、PR 改动了哪些既有条目；维护者对照源码核实描述里的数字和 API。
  • 每周做一次腐烂扫描，结果汇总成跟踪 issue，删除由人决定。
  • 企业内部市场照搬即可：把「仓库年龄」换成「负责人 / 安全评审已签」。
02

能力披露代替安全背书，安装只认白名单来源

dsh-trust-check + data/capabilities.json + dsh-market src/sources.ts

  • 卡片上展示插件会碰到的 shell、文件、网络、凭据、动态代码、子 agent，每条附「文件 + 行号 + 片段」作证据。
  • 没扫到的显示「未检出」，不显示「安全」。
  • 只能安装精选列表里的来源；npm 包和 tarball 必须绑定条目自己的仓库。
03

升级契约规则库 + 预检 + 快照回滚 + 隔离坏插件

gating-hub 的 lib/contracts/rules.json；dsh-market 的 src/trial.ts、src/snapshot.ts、src/recovery.ts

  • 规则必须附事故证据。
  • 任何渠道升级框架后都要先跑预检。
  • 写入顺序或预设之前先离线回放组合，并自动打快照。
  • 新框架加载不了的插件直接禁用，服务端返回 409，用户无法强开。
  • 启动失败时，由一个不依赖宿主的进程提供「调整插件」的恢复界面。
04

工具级治理要两层落地

dsh-mcp-connector

  • 规则优先级 Tool > Server > Connection > 默认。
  • 改动先预览影响面，再带 baseRevision 提交，保留最近 20 份可回滚。
  • 执行层同时用宿主的 restrict()（模型看不到）和 guard()（调用也会被拒）；宿主没有 guard 时，干脆不允许保存 deny 规则，不能只在界面上隐藏。
05

开放扩展点 + 声明式权限 + 第二模型审查

DSH-better-sidebar、dsh-permission-rules、dsh-auto-review

  • DSH-better-sidebar 的 registerTab / registerFileViewer：描述符带 id 前缀、order、available()，注册返回 disposer，内置功能也走同一个 API。
  • dsh-permission-rules：有序规则，first-match，内置高危基线排在用户规则之后。
  • dsh-auto-review：规则覆盖不到的，交给只读审查子 agent，默认 fail-closed。
