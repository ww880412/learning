今日主线
  1. Anthropic 官方发文《Building always-on agents》：常驻只是使用体验，agent 大部分时间在睡，被事件叫醒后跑一个 run、存状态再睡；外围五个原语是事件收件箱、定时器、记忆、权限和发件箱。官方称 Opus 5.5 在一个长周期编程基准上，每解开一个任务比 Opus 5 便宜 78%，典型工作负载上只便宜 40%（官方文章）：作者 William Hu（官方文章）。收件箱是唯一事实来源，每inbox 同时只有一个 worker，可按来源 ID 去重、把连发消息合成一轮；定时器分跟进和排期，到期后往收件箱投事件；记忆只存查不到的东西，别处已有的只存指针；凭证不进 agent 环境，由外部代理注入，auto mode 用分类器拦高危动作，hook 可把 tool call 挂起等用户批准，期间 worker 可处理别的事；用户只收结果和少量细节，建议先少发、用评测再调消息量。meng shao、yibie、宝玉分别做了中文拆解（meng shao、文章、yibie、原文链接、宝玉）；花叔当天按该文在开源驾驶舱 FanBox 2.20.0 做了一版，终端 agent 等待而人不在时，微信或飞书会收到一句话（作者自测，原帖、跟进、仓库）
    前提或争议：这是工程指南，不是新产品发布；78% 和 40% 是官方在文中给的数字，基准名称未写。FanBox 是作者自己产品上的复现，不是 Anthropic 官方实现，云端常驻方案他们没做；话题组里还有他踩到的四条可抄限制
    为什么值得看：这是可直接抄进工作台的拆法——先把叫醒、排期、记忆、权限和通知从模型循环里拆开，不要把「始终在线」做成模型一直挂线烧 token
    另见：X 海报 #1
  2. Addy Osmani 再次强调：大多数编码先用 Opus 5.5 的 medium（他也称这是 Claude Code 给 Opus 5.5 设的默认），吃力先加 effort，再把 Fable 5.2 留给大迁移和长时间无人值守；他引用的一项 52 任务评测里，Fable 并不明显更准，但每个解开任务大约贵 2.80 倍（作者经验，并对照官方开发者博客）：Addy 发帖并链到自己 11/9 在 claude.dev 写的选模型指南，官方建议大多数工作从 Opus 5.5 的默认 medium 起步，并写明它是 Claude Code 的默认模型，每输入/输出 token 价格是 Fable 5.2 的一半（原帖、选模型指南、补充）。他引用 Garry Tan 在 Claude Code 2.1.322 上 52 个编码任务的评测：Fable 5.2 解开约 82.7%，Opus 5.5 为 84.6%，但每个解开任务成本约 2.80 倍（Garry Tan）。向阳乔木的用法是先让 Opus 5.5 出方案，再让它「请求自己的 Fable 5.2 评估方案」，会另起智能体复审，他感觉能省至少 3 倍消耗；有人问为何不用 /advisor，他说目前只能选 Fable 5.1，「有点奇怪」（作者自测，原帖、省消耗、/advisor）
    前提或争议：Fable 5.2 是 11/9 已发布的模型，不是今天新品。52 任务数字来自 Garry Tan 的评测，口径是「每个解开任务的成本」，和官方博客里「每 token 贵一倍」不是同一件事；向阳乔木「省 3 倍」是个人感觉，不是对照实验。/advisor 只见 Fable 5.1 是作者界面观察，未见官方说明
    为什么值得看：你日常用 Claude Code 时，可先把 Opus 5.5 留在 medium，把 Fable 用在复审或确实啃不动的长任务上，避免默认上最贵模型
  3. 宝玉认为，Grokbot / Dots 那种「一个主会话」和 Claude Code 那种「一堆 Session」都不够好；他更看好把任务和作品从主会话里沉淀出来，并称自己在用的 Claude Duet 的 Tasks / 作品视图最接近（作者观点）：只有主会话时，子任务不好干预细节、不好补上下文；只盯主会话则既不好找做过哪些任务，也不好找产出，就像在微信群里翻文件（原帖、沉淀任务和成果）。评论里他说 Duet 偏办公效率，普通用户也许更喜欢 Grokbot 那种不必看见任务；他还认为先建 Project 再开 Session 对普通任务很反人性，Bot 默认带一个主会话更顺（Duet、最接近、Project/Session）。TestingCatalog 称 Claude Duet 已邀请所有在 waitlist 上的美国 Pro / Max / Ultra 用户（转述，原帖）
    前提或争议：这是产品判断，不是评测。Duet 邀请范围目前只看到 TestingCatalog 的聚合转述，关注名单里没有官方账号帖，但宝玉已在用，说明至少部分人已经用上
    为什么值得看：工作台如果只做「一个主聊天」或「一堆互不相认的 Session」，都会在找任务和找结果上卡住；可对照 Duet 的任务视图和作品视图，看要沉淀哪两样东西
  4. Google Antigravity 上线 Dynamic Workflows：用 /run-workflow 让 agent 写一段 Python，以 parallel() / pipeline() 等编排子 agent；官方文档写明面向 Google AI Pro / Ultra，App 和 CLI 都可用（官方文档，changelog 标注 v2.32.0、11/13）：TestingCatalog 今日作了转述（原帖）；官方说明见 Dynamic Workflows。脚本先展示再请用户批准，除非权限预设（如 Turbo）已允许；子 agent 各有独立会话，按 JSON Schema 交回结果，文件读取和测试日志不进主对话；工作流在后台跑，可把可用脚本存进项目里再跑。文档把它和 Orchestrator、子 agent、/swarm、/boost、/teamwork 做了分工：要可预期、按名单做同样检查或分阶段推进时用工作流，要 agent 彼此商量则用 /swarm
    前提或争议：功能在 11/13 的 changelog 里已经写出，不是今天才发布；关注名单里几乎没有独立实测，限制和用法以官方文档为准
    为什么值得看：这是可对照的多 agent 编排方式——用短脚本把并行和阶段写死，而不是靠一段很长的对话即兴拆活
  5. Guillermo Rauch 分享两套可抄的做法：用 feature flag 把 agent 写的代码先只对自己可见，推送时做验证和安全审计，再让 agent 盯指标；以及用 fx.sh 的子 agent，在 ~/.fx/AGENTS.md 里写一行「最强模型做规划，快模型子 agent 执行」（作者经验）：他称可用 Vercel CLI 的 vercel flags、vercel metrics、vercel deploy，并引用 @marclou 的说法——功能先在生产环境只对自己开放，AGENTS.md 里强制测试（原帖、marclou）。同日他称 fx.sh 上的子 agent 好用，包体 6.33MB；引用 fx v0.0.17：子 agent 与 Token Pass 成为一等公民，可在运行中 steer，工具定义缩小 48%（原帖）
    前提或争议：这是 Vercel 相关作者的用法和产品自报，不是对所有工作台的评测；48% 和 6.33MB 来自 fx 版本说明
    为什么值得看：可抄的是上线路径（先做只对自己可见的开关，再用验证门和监控），以及把「谁规划、谁执行」写成一条家目录规则，而不是每次在对话里重说
  6. 花叔发布达尔文.skill 3.0：结合 Fable 5.2 和近期论文做了重构；他发现让评委读两版 SKILL.md 投票并不靠谱——评委 3:0 说新版更好，真机跑却多绕了 33 次工具调用（作者自测）：他还引用 NVIDIA 研究，称读文档打的分和实跑效果几乎零相关（原帖）
    前提或争议：3:0 和多绕 33 次是作者自己的一次对比，不是公开基准；NVIDIA 那句是他转述，本文未打开原始论文
    为什么值得看：改 skill 或规则时，不要只让模型给文档打分；要以真机工具调用次数和任务结果为准
  7. yibie 介绍 SparseRead：在 agent 原生读取工具前加一层控制，先产出带源锚点的证据包，再决定要不要回退全文；论文自称 token 最多降 92.9%、墙钟最多降 89.0%，但尚无第三方复现，目前只能从源码安装（论文数字，作者整理）：链路是 Read Gate → Reader Backend → EvidencePack；小文件和低稀疏任务可直接走原生读取，停止权仍在 agent。论文称 125 个任务、5 类场景、6 个前沿模型（含 Claude Opus 5），97% 的设置保持或提高质量；移植到 NanoBot / OpenCode / OpenClaw 的 token 中位数分别降 69.0% / 71.8% / 28.7%。yibie 写明 Claude Code、Codex、Pi 三个适配器还没进论文基准表，当前 v0.1.3，PyPI 和 npm 未通（原帖、论文、代码、链接）
    前提或争议：数字全部来自作者论文，目前没有第三方复现；不能把它写成已在 Claude Code 或 Codex 上验证过
    为什么值得看：处理长报告、日志或多文件审计时，可参考「先读证据、必要时再读全文」，但要自己复测后再接到工作台

  • 花叔（@AlchainHust）：当天在 FanBox 2.20.0 落地，并写出四条可抄限制（作者自测）。没人触发的那一轮只给读和搜索，不能改文件、跑命令或写长期记忆，想动手必须先在微信上问；人在不在由系统看键鼠，不让模型猜，离开满 10 分钟且 5 分钟无输入才叫；微信值守每次醒来约 4 到 11 秒、折合约 0.14 到 0.16 美元，所以两次醒来至少隔 3 分钟、一天最多 48 次；推不到本机的来源用「盯梢」，最短 5 分钟跑一次命令，输出里多出来的新行才算事件。发件箱则是夜里 23 点到早上 8 点不发，两条至少隔 10 分钟，一天最多 20 条。他还写明：云端常驻没做，是自己选择把 agent 放在本地；微信值守目前只支持 Claude Code，飞书只能发不能回，在岗只看键鼠，每种通知情况只跑了一两次（原帖、跟进、仓库）
  • 还没确认：官方文是架构指南，不是 Anthropic 要上架一个「24 小时 Agent」产品；FanBox 的耗时、费用和通知策略都是作者自己环境里的实测，稳定性和别的机器上的表现还不能外推
