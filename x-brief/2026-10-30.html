今日主线
  1. Cursor 插件市场被投毒：假冒的 Claude Code 扩展会装 SSH 后门：Cursor 官方称，北京时间 10/29 17:27 到 10/30 04:35，它的 VS Code 扩展市场上的 Anthropic.claude-code 2.1.312 / 2.1.313（Windows、macOS）是被篡改的版本，最多影响 5000 名用户。这个版本会收集主机信息，往 ~/.ssh/authorized_keys 写入一把标着 svc-telemetry 的攻击者公钥，还装上 LaunchAgent 或计划任务，反复尝试建立反向 SSH 隧道（Amjad Masad 原帖、Alex Albert 转 Anthropic Felix Rieseberg 原帖、Cursor 原帖、Cursor 安全公告、StepSecurity 报告）
    前提或争议：只影响在这段时间里从 Cursor 市场安装或自动更新的人（StepSecurity 称恶意版本是经 Open VSX 镜像进来的）。Anthropic 的 Felix Rieseberg 称这次不是 Anthropic 的系统或员工电脑被攻破，官方渠道的版本不受影响。Cursor 称恶意代码有 bug，多数机器也没有管理员权限，所以开启 SSH 服务这一步通常会失败，攻击服务器已经下线；但公钥和自启动项还是会留下，只卸载扩展不够，Cursor 要求升级到 2.1.314。Amjad 猜它和币安被盗有关，这只是猜测，目前没有证据
    为什么值得看：用 Cursor 装过 Claude Code 扩展的机器，先 grep 一下 svc-telemetry、查一遍 LaunchAgent，再从一台可信的机器上轮换凭据。工作台应该默认管住三件事：扩展从哪来、锁定版本、新版本晚几天再放行，别让编辑器自动更新第三方镜像
  2. Claude Max 20x 改名 Ultra，验证过的账号不再有 5 小时限额：Claude 官方宣布 Max 5x 改名 Max（仍是每月 $100），Max 20x 改名 Ultra（仍是每月 $200）。北京时间 10/31 起，Ultra 里验证过的账号陆续取消 5 小时限额；较新的账号在验证通过前保留一个临时限额；周限额不变。Boris Cherny 转发确认（Claude 原帖、Boris Cherny 原帖、Claude 订阅产品负责人 Michael Boverell 原帖、宝玉 原帖）
    前提或争议：官方已公告。订阅负责人解释「20x」一直只指 5 小时窗口，周限额本来就是 Pro 的 10 倍，并为这个名字带来的误解道歉。宝玉根据帮助页补充：验证由 Anthropic 按账号和付款记录自动完成；用量页上看不到「Current session」进度条，就说明已经取消；Ultra 另有一个单独的 Fable 周限额。验证要多久，官方没说
    为什么值得看：在 Ultra 上长时间跑 Claude Code 或多个 Agent 并行，不会再被 5 小时窗口打断，但一周的总量没变多。工作台的用量调度要从「躲开 5 小时窗口」改成「把周配额摊开用」；$100 的 Max 档仍然有两道限额
  3. Claude Code 的系统提示被服务端加了一句：不许复刻现有游戏：用户 Chasm 发现 Claude Code 的系统提示里多了一条经 tengu_heron_brook 下发的规则：可以做原创游戏、同类型游戏、用自己素材做的游戏，但不许复刻某一款具体的现有游戏，改了名也不行。Peter Steinberger 认为这正说明该用自己的 harness，elvis 也劝大家自己搭 harness（Chasm 原帖、Peter Steinberger 原帖、elvis 原帖、Game Developer 报道、XDA 报道、GitHub issue #62061）
    前提或争议：Anthropic 已回应。据 Game Developer 报道，Anthropic 发言人引用了 Addy Osmani 的说法：在 Opus 5.5 的 Claude Code 提示里加了两句话，因为用 Claude 侵犯 IP 违反使用政策，原创游戏和同类型游戏照常能做。XDA 在 v2.1.314 的程序里找到了这句原文，并发现 tengu_heron_brook 是一个通用的远程下发提示词通道，不是专门为游戏加的；另外 Opus 5.5 的提示包里也带着这句。GitHub issue 里一条以团队口吻的回复说这是系统提示实验，可以用 CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 和 DISABLE_GROWTHBOOK=1 退出；这两个变量能不能关掉 Opus 5.5 提示包里的那句，没有说明
    为什么值得看：工作台跑 Claude Code 时，系统提示可能被服务端改写（这个开关每 60 秒刷新一次）。要么设上面两个环境变量，要么在审计里记下每次会话实际用的系统提示版本；遇到说不清原因的拒绝，先查这一层
  4. OpenAI Agents API 本周更新：执行命令前自动审查、压缩放到后台、模型有「时间感」：OpenAIDevs 转发了 Agents API 团队 Steven Coffey 列的本周更新：Auto Review（和 Codex 一样，执行命令前先判断有没有危险行为）；Async Compaction（压缩在后台跑）；实验性的 Time awareness（模型能感知时间过去了多久）；会话进行中随时可以更新工具；系统提示自动跨会话缓存（OpenAIDevs 原帖、Steven Coffey 原帖）
    前提或争议：官方发布，功能介绍都是厂商自己说的，没给效果数字；Time awareness 标明是实验功能；没看到第三方实测
    为什么值得看：这几项几乎就是工作台 harness 的待办清单：执行前审查对应权限，后台压缩不卡住会话，时间预算给长任务限时，运行中换工具可以按阶段放权。可以先照着做「限时」和「中途换工具」这两个接口
  5. 「压缩是个错误」：上下文满了就开新会话，按需去旧会话里查原文：Alezander9 在一个约 40 万 token 的 Opus 5.5 真实会话上测了压缩：它要把整段会话重新 prefill 一遍，缓存过期时花 38 秒、$1.99，缓存没过期时 29 秒、$0.17。他开源的 Mainplane 改成把每个会话完整存成文件，上下文满了就直接开新会话，让 Agent 边做边去旧会话里搜要用的原文，同一个会话 15 秒、$0.10 就能接着干（Alezander9 原帖、宝玉 原帖、原帖）
    前提或争议：数字是作者自己测的一次。宝玉认为 Claude Code 压缩后本来也会按需去历史会话里找信息，区别只是多了一段摘要；评论里有人指出，真正的差别在压缩时要把整段会话重读一遍，宝玉随后也同意「缓存过期了再压缩，代价很大」
    为什么值得看：工作台的会话存档如果本来就留着完整记录，就可以把「去旧会话里查」当成默认的续接方式，至少缓存过期以后别再触发一次全量压缩。能抄的是「完整存档 + 新会话按需检索」这个续接方式
  6. Addy Osmani：到了 Opus 5.5，别再过度提示 Claude：Anthropic 的 Addy Osmani 写文章说，给 Opus 5.5 一条提示就够了，说清要做成什么、怎么证明做完，/effort 从 medium 起调；目标还不清楚时，先让 Claude 采访你、写出规格，再开一个新会话照规格实现。Claude Code 给 Opus 5 / Fable 5 的系统提示删掉了八成以上，编程评测没有明显下降；/doctor 里的 prompt-audit 会标出那些像是为旧模型写的指令（meng shao 原帖、Viking 原帖、Addy 原文）
    前提或争议：「删掉八成、评测不降」是 Anthropic 自己的说法；作者也提醒，默认开启的 auto mode 靠分类器判断动作，并不能保证安全。Viking 由此认为以前写的大部分 skills 都可以删掉，这是他个人的看法
    为什么值得看：工作台的 skill 和系统提示可以照这个办法过一遍：先删，只把模型真会漏掉的加回来；验收写成能执行的条件（E2E 通过、录屏通过），长任务再配上 /goal，让另一个模型每一轮检查一次
  7. Anthropic 让 Claude 把 Messages API 重写成 Rust，CPU 占用降了 40–50%：据 somi_ai 转述 Latent Space 播客里 Anthropic 的 Katelyn Lesse 的说法，团队里没有一个 Rust 工程师，代码由 Claude 来写，人负责写计划，再用真实流量核对新旧两版的输出一致，CPU 占用降了 40–50%。播客主持人 swyx 转发说「是真的」（swyx 原帖、somi_ai 原帖）
    前提或争议：转述，出自播客片段；没看到 Anthropic 的书面文章，也没有具体时间线
    为什么值得看：这种大重写能落地，关键在「拿真实流量比对新旧输出」这一步。工作台交给 Agent 做迁移或重构时，可以把影子流量比对定为标准验收，不能只靠单测
  8. 阿里云开源《AI Agent Handbook》：企业 Agent 真正上了生产的约占 18%：meng shao 介绍了阿里云这份采用 Apache-2.0 协议的企业 Agent 手册，覆盖架构、构建、运行、治理、调优和案例，并附 2026 年调研数据：已开发完或正在开发的合计约 46%，真正上了生产的约 18%；单 Agent 约 40%，多 Agent 约 42%；做出来以后，最大的难点是上下文和记忆（约 90%），其次是多模型路由和成本治理（约 63%）；评估大多靠人工抽查（约 55%），基于轨迹的自动评估不到 8%；MCP 在企业内部私有部署的只有约 9%，缺的是注册中心、鉴权、灰度、审计和网关（meng shao 原帖、手册仓库）
    前提或争议：这是阿里云自己做的调研，样本和统计口径写在仓库的调研报告里，厂商立场明显；手册在 10/23 云栖大会上发布，每周增补新内容
    为什么值得看：这组数字可以直接拿来排工作台需求的先后：记忆、路由成本、轨迹评估、MCP 网关这四块是企业最缺的；手册的治理篇和研发效能那 9 个案例值得一章一章对照着看
