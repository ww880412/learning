今日主线
  1. OpenAI 官方介绍 Performance Factory：用 Codex 在云端自动调查性能回退、提出修复供工程师审查，并在上线后复查是否回到基线；回归工作流在三个多月里跟踪了 1700 多次调查，定位了 600 多个根因，约合每天 17 次自动调查（官方博客）：OpenAI 开发者号和官方博客（Okay Zed、Cyrus Forbes，2026-11-19）写，团队先把性能调查过程收成共享 skill perf-forensics（告诉 Codex 有哪些工具、何时用、怎么查变慢），再用过去的回退案例做评测，做到「给一条告警、单次跑完诊断」；随后把调查搬到云端，告警可自动开 Codex 会话。再往后做成工厂：任务服务用配置和 Markdown 提示定义工作流和状态；调度循环按任务当前状态启动一轮 Codex；云端执行；订阅在出现审查评论或部署完成时把任务重新唤醒，人不审的时候不必让 agent 一直挂着。官方称系统由这四部分组成。官方还写，今天的瓶颈可能已经变成等人审查和合并修复，他们也在探索能否让 agent 自己做这一步（介绍帖、perf-forensics skill、任务状态与调度、1700/600 数字、官方文章）
    前提或争议：这是官方说明和内部运行数字，不是外部复现。官方写的是「提出修复供工程师审查」，不是已经无人值守合入生产
    为什么值得看：这是可抄进工作台的工厂做法：先把调查写成带评测的 skill，再把告警接到云端会话，最后用带状态的任务机把人审、合并、上线复查串起来。不要把「多开几个 Codex」当成已经做成了工厂
  2. OpenAI 官方称，从最新前沿模型起，Responses API 里每条推理都绑在它之前的对话历史上，改早先的消息会丢掉后面的推理；用 GPT-6.2 Astra 或 Sol 时应只追加新轮、不改前面的历史（官方帖与文档）：开发者号写，这样 agent 才能少花 token、多打中缓存，并在已有推理上继续干活。改推理强度或增删工具，也可能在不知情时改到前缀；官方为此提供了 Responses API 的 input_transformations 对象，以及 Usage 仪表盘里的「Reasoning removals」。官方文档补充：改 reasoning.effort 或结构化输出 schema，应追加 configuration_update，而不是改请求级参数；加工具用 additional_tools，限制工具用 tool_choice / allowed_tools，并保持已有工具定义顺序；更新开发者说明应追加新的 developer 消息。文档还写明：从 GPT-6.2 起，顶层 instructions 会被接到 input 后面，并按未缓存输入计费。Peter Steinberger 另提到 Codex issue #62312：有人发现 Astra/Sol 把内容放在 Responses API 顶层 instructions 时缓存不生效、账单上升；他已在 OpenClaw 的嵌入式 harness（作为插件，而不是走 Codex）里修了，并称多数 harness 还没更新（官方说明、检测工具、Astra/Sol 应只追加、官方文档、Steinberger 引用该 issue）
    前提或争议：前缀保护、检测工具和「GPT-6.2 顶层 instructions 按未缓存计费」是官方说明；#62312 本身是 issue 与作者自报修复，不是 OpenAI 对该 issue 的单独公告。官方文档还写：用 OpenAI 自己的 compaction 会保留后续推理，自行做 compaction 则可能丢掉
    为什么值得看：这已经不是「为了缓存尽量别改前缀」的建议，而是接口会丢掉后续推理的硬约束。工作台如果走 Responses API，要把改 effort、改工具和改早期消息都改成追加，并看 Usage 里有没有 Reasoning removals
  3. Matt Pocock 写了精简 Claude Code 系统提示的做法：先用 /context 和本地日志代理看清每轮真正发出去的工具定义和系统指令，再用 disable* 开关和「裸工具名」的 permissions.deny 把不用的能力从请求里拿掉；他自称自己每轮少了数万 token（作者自报）：关键区别是：裸名（如 "NotebookEdit"）会把工具定义移出 payload；带范围的规则（如 "Bash(rm *)"）只拦调用，定义仍在、照样计费。disableBundledSkills 是一刀切；若只想关个别 skill，要用 skillOverrides 设成 "off" 或 "user-invocable-only"。他同时回答 Home Repo 相关问题：代码库就是记忆；要狠剪初始配置；多个主仓库用 Home Repo；不需要 session-start skill；Claude Code 做子 agent 编排就够；共享领域用语可把 GLOSSARY.md 放在 Home Repo（文章链接帖、精简文章、五条原则、GLOSSARY.md）
    前提或争议：token 降幅是作者自测，不是官方基准。文中的 deny 列表是菜单不是处方；若你用 plan mode、notebook，或依赖 Workflow、后台任务等多 agent 机制，就要把对应工具留着。改完要重启 Claude Code 再跑一次 /context
    为什么值得看：这直接动到 Claude Code 每轮都在付的隐藏成本，步骤可以抄进工作台的默认配置；也补了昨天 Home Repo / skills 视频里没写细的「怎么量、怎么剪」
  4. Google 官方在 Gemini Interactions API 上线 Tool Retrieval 预览：大工具库不必每轮都把完整参数 schema 发给模型，可按需加载；官方称无单独加价，只按所用模型的输入输出计费（官方文档）：做法是在工具列表里加 {"type": "tool_search"}，并对要推迟加载的 function 或整个 mcp_server 设 defer_loading: true。模型仍能看到推迟加载工具的名称和描述，但参数 schema 先不进上下文；需要时再加载，默认同一次请求内完成。也支持 execution: "client" 的客户端检索（自建索引或按用户权限过滤），但每次检索会多一趟往返。官方文档举例：200 个工具、每个约 400 token 时，静态加载约 16.4 万输入 token，用 Tool Retrieval 约 2.365 万。官方还写它和前缀缓存兼容：推迟的 schema 不进提示开头。Logan Kilpatrick 评论称，这对用 Gemini API 做 agent 的客户是一次很好的发布。文档列出的支持模型是 gemini-4-hydrogen、gemini-4-argon、gemini-3.8-flash、gemini-3.6-flash（Logan 评论、Google AI Studio 介绍帖、官方文档）
    前提或争议：这是预览，需 v1beta，接口在正式版前可能改；只支持 Interactions API，不支持 generateContent。已加载的工具在对话剩余部分会留在上下文，不能卸下；每次请求仍要重发完整 tools 数组。官方 changelog 有「含所有 Gemini 4 模型」的写法，但专页名单里没有 Neon、Carbon，是否能用要以专页和实测为准
    为什么值得看：这和上面精简 Claude Code 是同一类问题——工具定义把上下文和账单撑大。工作台如果接大量 MCP 或内部工具，可以按「常用的常驻、长尾 defer」来抄，先在文档列出的模型上小范围试

OpenAI 官方宣布 GPT-Live-1.1 已在 API 上线：官方称口音更自然、跨语言更一致，并新增 standby，可在空闲时降低费用；它从 10/15 起已为 ChatGPT Plus 和 Pro 的语音功能提供支持（官方）：standby 适用于 GPT-Live-1 和 1.1。官方模型页写，语音会话按时长计费，活跃 $0.05/分钟，standby $0.02/分钟；后端模型和工具费用另计。官方会话文档写，standby 目前针对 WebRTC：把空闲超时设为 5–60 秒的整数，超时后暂停推理但保持连接，有人说话再恢复；若不设超时，首次唤醒后会一直按活跃计费。麦克风轨道在 standby 期间要保持开启。开发者号还写，1.1 能更可靠地听清字母和数字、执行指令，并把复杂工作流交给后端（开发者号此句被接口截断，完整能力描述以官网为准）（发布帖、standby 说明、已用于 ChatGPT 语音、模型页与价格、会话文档）
    前提或争议：这是官方发布。standby 的低价官方写明适用于 WebRTC 空闲；不要把 SIP 或其他传输也写成已经同样计费
    为什么值得看：若工作台或产品要接语音 agent，这是直接改空闲成本的配置；不设 idle_timeout_s 就会一直按活跃价计
