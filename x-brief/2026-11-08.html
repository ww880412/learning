今日主线
  1. Tibo 称 Codex 所有 Pro 档都没有 5 小时限制，用量按 Plus 的倍数算：Pro 100 是 10 倍、Pro 200 是 20 倍、Pro 500 是 50 倍并可用 ultrafast（OpenAI Codex 负责人个人帖子，未见官方公告）：他 11/8 下午（北京时间）发帖澄清，随后又问「出个 Pro 50 合不合理」，这条拿到近 1 万赞；同一天他还回复说 GPT 6.1 Terra 本来就不是拿来和 Opus 5.5 比的，「我们有别的模型干这个」（Tibo 原帖、Pro 50 提问、Terra 回复）

  2. 马斯克称 Grok Bot「提升 token 效率和让行为更聪明」的修复正在进行；此前他回应额度不够用时反问「一键加量不就行了」（马斯克本人帖子，没说修什么、何时上线；额度缩水是用户体感）：修复帖发于 11/8 21:17（北京时间），3.6 万赞。Gorden Sun 称额度至少砍了 50%–60%，基本不再路由到 Opus 5.5；范凯说他这周几乎没主动用，光是抓 X 新闻、收邮件、待办提醒、X 私信几个定时任务就吃掉 100 美元套餐周额度的 40%，到期准备降到 30 美元档（马斯克 修复帖、一键加量回复、Gorden Sun 原帖、范凯说AI 原帖、吐槽一键加量、Viking 原帖）
    前提或争议：没有官方给出的额度数字；「砍 50%–60%」「不再路由 Opus 5.5」都是用户体感。X 新闻页（Grok 汇总）称马斯克把收紧归因于算力成本；Viking 也说模型像是没有 Opus 5.5 了、上下文变短
    为什么值得看：他的简报等例行任务都跑在 Grok Bot 上，范凯的数字说明定时任务本身就是大头。修复上线前先记下各例行任务的单次消耗，修完再比；工作台也该给每个定时任务单独显示用量
  3. OpenAI 开发者账号只发了一个词「Tomorrow.」，宝玉猜是 GPT-6.2；卡兹克说自己被灰度路由到 GPT-6.2 Sol，审美和防御性问题都有改善（官方预告未说内容；卡兹克为个人实测）：预告发于 11/9 凌晨 4 点（北京时间），附一段视频，8000 多赞（OpenAIDevs 原帖、宝玉 原帖、卡兹克 原帖）

    为什么值得看：如果是 Codex 默认模型更新，他的实现流程会直接受影响；可以提前备好两三个自己仓库里的固定任务，发布当天就对比新旧模型，不看榜
  4. Addy Osmani 长文《你的 coding agent 让你成了管理者》：按影响排序给出带 Agent 的做法，第一条是每个任务都要有能跑出通过/失败的检查，让 Agent 交证据；同一件事纠正两次就写进 CLAUDE.md，两次纠偏失败就清空会话重写提示（Claude Code 团队成员的经验文章）：hook 和 deny 规则只管少数「必须/绝不」的事，其余交给模型判断；无人值守任务开跑前回答五个问题：怎样算完成、怎么自检、边界在哪、轮数或花费上限、产出交给谁批；Agent 数量只按检查能力扩，衡量返工和回滚，不衡量 AI 写了多少代码。宝玉也在用同一招：Agent 修完 bug 必须附截图或录屏给人验收（Addy 原帖、Addy 文章、meng shao 解读、Viking 原帖、AYi 原帖、宝玉 截图验收）
    前提或争议：大部分做法拿 Claude Code 功能举例（/goal、Stop hook、/code-review、/batch、/rewind）；Addy 也写了类比的边界：Agent 不会顶嘴、所有 Agent 是同一种性格、自动记忆只留在一台机器上
    为什么值得看：几乎是一份工作台需求清单：任务模板固定「完成条件 + 验证命令」，长任务启动前强制填那五个问题，后台任务用通知代替轮询、集中一个看板，指标看返工率而不是代码量
  5. Google 开源 Elephant-Goldfish 插件：先让带完整上下文的「大象」Agent 起草规格，再派零上下文的「金鱼」子 Agent 只看规格挑漏洞，人拍板批准规格后才开始写代码；支持 Antigravity、Claude、Codex、ChatGPT（Google Cloud 官方发布）：huangserva 解读为专治「上下文塞满后 Agent 脑补默契」，金鱼会逼出漏写的环境变量、接口兜底类型这类断层（GoogleCloudTech 原帖、Elephant-Goldfish 仓库、huangserva 原帖）
    前提或争议：官方只给了用法，没有效果数据；仓库刚公开，成熟度未知；细节描述来自 huangserva 的解读
    为什么值得看：可以直接抄进工作台的规划阶段：规格写完自动派一个不带对话历史的子 Agent 复读、列疑问，人批准后才放行实现。和 Addy 说的「用第二个会话做计划评审」是同一招
  6. Coinbase CEO Brian Armstrong 公开自己的 Agent 编排：每个方向一个常驻主 Agent，上面再加一个「幕僚长」Agent；所有要他决定或审阅的事进一个按优先级排的队列，产品评审附截图和演示视频，他用语音和快捷键批量清（本人自述，没给效率数字）：系统把他的偏好沉淀成「Brian brain」，目标是每次改动少返工几回；每个改动仍过同样的人工评审和安全检查。elvis 转引说：减少和 Agent 的接触点、加强 Agent 之间的协调，加一个队列和好的记忆系统；他认为 harness 要自己拥有，定期看 trace 调系统提示（Brian Armstrong 原帖、elvis 原帖、自建 harness）
    前提或争议：elvis 说「其他配置都会拖后腿」是他自己 harness 上的测试结论，被追问对比对象时承认别的配置也能用，只是不是最优
    为什么值得看：这就是企业级工作台该长的样子：一个统一的「待决策队列」取代几十个聊天窗口，每条带截图或视频证据，按优先级批量处理。可以先做队列和证据附件，偏好学习放后面
