X 简报 · 11/19（周四）

今日主线
  1. OpenAI 官方介绍 Codex sandbox 与默认 permission profile：以 Git 仓库为工作区时，内置 :workspace 可在仓库内改源码而无需逐次批准，但根目录 .git 和 .codex 只读；允许受用户系统权限限制的广泛读取；默认关网络，命令要上网时可能直接询问用户，或交给 auto-review（官方博客）：OpenAI 开发者号写，改仓库的命令不应自动获得网络权限；Codex 不用另开容器，而是在用户现有环境里用操作系统级沙箱限制文件系统和网络。官方博客（Michael Bolin，2026-11-18）补充：.git / .codex 只读，是为了防止直接改 .codex/config.toml 或 .git/hooks；广泛读权限是为了让编译器和 SDK 能工作，但机器上其他配置里的 API key 仍可能被读到；关网络能挡住一批外传，也会挡住下依赖，常用包仓库域名可以写进 permission profile。官方明确残留风险：agent 仍可能向常被 gitignore 的依赖（例如 node_modules/prettier）注入代码，用户编辑器在沙箱外保存时可能执行。官方把它写成 defense in depth，并称 codex sandbox 可把同一套限制用到自己的工具里（介绍帖、默认 profile、OS 级沙箱、网络与 auto-review、官方文章）
    前提或争议：这是官方说明，不是用户实测。开发者号线程里有两句被接口截断，完整表述以官网为准；官网还指向 Codex security cookbook，本期没有单独打开那份 cookbook
    为什么值得看：这直接改了 Codex 默认能碰什么。工作台如果接 Codex，或自己抄 permission profile，不能把「默认沙箱已开」当成密钥和依赖链已经安全；要把密钥路径和常被忽略的目录单独限制
  2. OpenAI 的 Tibo 解释 GPT-6.2 体感分化：较早给少数人试用后，最近 3–4 天又做了很多改动，他相当确定那些人没有在这几天复测，而且视频是上周拍的；他同时承认沟通风格的反馈，「我们正在处理」（官方）：他另写，这些模型能力很强，但还有若干 rough edges，会慢慢打磨。他引用 OpenAI 官方账号与 AMD 的结果：不到五个月，在 AMD 工程师已优化多年的旗舰 GPU IP 上识别出最高约 14% 的 PPA 改进；同样方法也用于 OpenAI 第一颗自定义推理芯片 Jalapeño，「gains verified」（官方原帖此句被截断）。Greg Brockman 转发第三方 browser_use 榜：GPT-6.2 Sol 在 browser use 上 82%（6.1 Sol 为 81%），便宜 35%，快一倍（12 分钟对 22 分钟），步数少 36%。歸藏自测：Sol UltraFast 剪 8 分钟视频，总耗时 27 分钟，模型响应约 14 分钟，均速 126 token/s，峰值 252 token/s；他一度说会多用 Sol、Astra 先不搞，晚些又说 Astra 在复杂 3D 建模上细节很好，从零在 Blender 里建、几乎没干涉，共约 6 小时（大部分是渲染），花了 8198 万 token（Tibo 解释测评时差、他推荐 Sol UltraFast、沟通风格与 AMD、Brockman 转发、歸藏 UltraFast 实测、歸藏后来的 3D 实测、OpenAI 官方 AMD 帖）
    前提或争议：AMD / Jalapeño 数字是官方自报；browser_use 是第三方榜，由 Brockman 背书，不是 OpenAI 自测；歸藏是个人任务，前后对 Astra 的取舍不完全同一方向。Tibo 还建议有 Pro 200/500 的人试用 6.2 Sol UltraFast。Theo Browne 被 Tibo 引用时说，复测后比第一次好，但他仍认为「方向上非常差」——这是转述，不是关注名单作者原文逐字核对
    为什么值得看：昨天已经写过 6.2 上市、价格和官方承认的「卡住却不说」。今天新加的是：不要把发布前一周的测评当成今天的模型，沟通风格是官方已承认、正在修的问题
  3. OpenAI 官方称：对可以等待的单轮或多轮工作流，GPT-6.2 Astra 或 Sol 相比 Standard 最高可省 40%/token；Responses API background mode 的折扣窗口已公开 beta（官方）：第一次回复可选 2 小时或 8 小时目标窗口；官方开发者号和文档都写，completion_window=2h 比 Standard 少 30%，8h 少 40%。例子是下班前提交会议记录，早上再取 brief。第一次请求设 continuation ID，后续请求复用可提高排队优先级。官方文档还写，折扣适用于符合条件的每次请求（含后续回合），默认窗口 soonest 没有这笔折扣（介绍帖、8 小时例子、2h/8h 折扣、官方文档）
    前提或争议：这是官方定价说明，本期没有关注名单作者的独立复价
    为什么值得看：能隔夜跑的评测、汇总和长任务，可以直接改用 8 小时窗口换四折优惠；工作台如果接 Responses API，要把 continuation ID 和窗口一起复用

    前提或争议：跑分和「每任务成本比 Carbon 低约 32%」是官方引用或官方自报，不是关注名单作者实测。Vals、AA 等是第三方榜，口径以各榜和官方博客为准
    为什么值得看：这是新的中档 Gemini 4 API，价和缓存折扣对 agent 循环很敏感；若在 Antigravity 或自建编排里用，官方已经给出「Neon 做规划、Hydrogen 做执行」这条可抄的分工
  5. Matt Pocock 发出新的 skills 实操视频：称距离上次 “watch me work” 约 6 个月，自己的 skills 仓库已是星星最多的 skills 仓库；视频里用 70 分钟做了一个 2.1 万行的 PR，重点是用 /grill-with-docs 做 DDD、用 /retro 改进代码库，以及如何做 human review（作者自述和演示）：有人问如何在多个项目间共享几乎相同的规则，他建议用 Home Repo，并说从 home repo 拉起 agent，可以按问题域而不是按仓库来组织（视频帖、Home Repo 建议、按问题域组织、他提到的视频）
    前提或争议：「most-starred」是作者自称，不是第三方统计。这是演示和用法建议，不是对照评测
    为什么值得看：可直接看他怎么用 skill 做领域设计和回顾，以及用 Home Repo 把规则从单个仓库里抽出来——这和工作台要维护的项目规则、跨仓共享是同一类问题

  • 【转述】Akshay 对昨天已报的 Google Self-Improvement Memory 论文做了更细转述：只继承进化出来的 harness 代码、不继承「为什么改」的记录，优化器会重做失败实验或拆掉看不懂的修复。SIM 记录修改、预测要修的任务、实际结果、所用模型和基准，并每轮写入优化器 prompt。例子是：有 SIM 时会读懂「禁止过早结束」检查并扩展；无 SIM 时同一检查被改写四次，其中两次是修自己造成的死锁。在 Opus 换到 Gemini 的 workspace 任务上，有 SIM 从同一起点大约多提升 3 倍，10 次独立 coding run 中 9 次领先。昨天简报写的是论文里 10 次编程续跑平均高 2.36 分，这两套数字不是同一口径——转述已有论文，不是新论文——Akshay @akshay_pachaar（原帖、论文） 另见：X 海报 #4
  • 【论文】elvis 介绍 MIT CSAIL 与蒂宾根大学的新论文：给冻结模型计算预算和简单工具，让它编写练习游戏、观看自己的副本游玩，并编辑副本的 prompt 和 skill 文件；它看不到真实任务或验证分数，也没有被教导如何学习。能力强的模型自己形成了学习流程，并在有隐藏机制的留出游戏上提高；不同模型家族还写出了可迁移到外部基准的文本文件。作者认为，不显式放入自我改进循环，并不能阻止有工具的模型自我改进——论文介绍，不是作者复现——elvis @omarsar0（原帖、论文）
