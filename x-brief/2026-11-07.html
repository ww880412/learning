X 简报 · 11/8（周日）

今日主线
  1. Anthropic 工程博客讲清 Claude 的记忆怎么做：会话里写笔记，空闲时 dreaming 对照原始记录纠错、建 wiki，只把精简索引注入每次会话；Claude Code 自动记忆只读 MEMORY.md 前 200 行或 25KB（官方博客 11/6，内部评测数字）：宝可梦实验里 Sonnet 3.7 写了 413 个文件、225 个文件夹只拿 1 枚徽章，Fable 5 只写 9 个文件拿 4 枚；规定「只记失败」反而让 Opus 5、Opus 4.7 丢掉大部分记忆收益。Stainless 约 35 万份内部文件上，dreaming 从 2 轮加到 128 轮，只靠 wiki 的得分从 13% 到 48%；wiki 加搜索从 54% 到 61%（只用搜索 53%），每题省约 2 万 token；多 Agent 共写一张合同表只保住 41/57 个关键事实，改成一份合同一页、一个 Agent 写、逐字引用后 57/57（AnthropicAI 原帖、Anthropic 博客、yibie 原帖、meng shao 原帖、Gorden Sun 原帖）
    前提或争议：都是 Anthropic 自己的内部评测；61% 是评分项覆盖率，不是答对率，省下的 token 也没扣后台建库的算力（meng shao 指出）；单文档就能查到的任务 wiki 没有收益，有一例 wiki 比原文还大。Google Research 的 SLEEP 走另一条路，把知识写进参数（meng shao 原帖）
    为什么值得看：几乎可以原样抄进工作台：记忆目录加一个定时 dreaming 任务，拿原始 transcript 校对笔记；顶层注入层限长，只当索引；只告诉模型记忆是干什么的，不定死写法；多 Agent 共写的表改成「一个对象一页、一个写者」
  2. Tibo 回帖称 Codex 的 Pro 套餐和 Business 100 用量已经翻倍（OpenAI Codex 负责人回复，没搜到正式公告）：起因是用户发现 Tibo 停发重置之后，Codex 额度反而更耐用（Tibo 原帖、Tech_girl 原帖）
    前提或争议：只是一条回帖，没说从哪天生效、是不是临时、其他档位动不动；搜了 Tibo、OpenAI、OpenAIDevs 近两周的帖子，没看到正式说明
    为什么值得看：Codex 是他的主力实现工具之一，额度翻倍会改变「重活给 Codex 还是给云端 Agent」的分配；建议按自己的周用量看一周再调
  3. X 新订阅把 Grok Bot、Grok 和 Cursor 放进同一个每周共享额度池：Grok Bot 跑定时任务也会吃 Cursor 的 Grok 额度；Cursor 里用 Claude、GPT 按 API 价另计；老 Cursor 用户合并后不能撤销（小墨读官方说明后的转述，未核到官方原文）：小墨建议常用 Claude、GPT 的人先别急着切换（小墨同学 原帖）
    前提或争议：作者转述，没有附官方页面链接，这里也没找到原文；同期多人反馈 Grok Bot 周额度缩水，X 新闻页称马斯克把额度收紧归因于服务成本太高（转述）
    为什么值得看：他的例行任务都在 Grok Bot 上，又用 Cursor，两边如果共用一个池，例行任务的频率和模型选择会直接挤掉编程额度。可以先盘点各例行任务每周用量，合并订阅前确认规则
  4. Addy：把 Claude Code 的输出风格切到 Concise，回答更短更直接，需要细节时再追问；在 /config 的 Output style 里选，或在 settings.json 写 "outputStyle": "Concise"（Anthropic 工程师给的用法）：有用户补充桌面版也支持（Addy 原帖、用户回复）
    前提或争议：只改输出长度，不改模型能力；长回答被砍掉的地方，排查问题时可能要追问
    为什么值得看：一行配置就能少读很多字。工作台的 Agent 设置里也可以给「简洁输出」一个开关，默认短、按需展开
  5. Claude Code Projects 在做协作模式：Projects 页面已有「最近动态」汇总各线程，Lydia Hallie 说「还没有多人协作」；同时在做 Duet 邀请和企业版合并多个 Claude 组织（TestingCatalog 爆料，未发布）：项目级概览会显示定时任务和线程，TestingCatalog 认为体验类似 ChatGPT Spaces，Perplexity 也在做类似功能（TestingCatalog 原帖、续帖、Duet 与组织合并）
    前提或争议：只有界面观察和一句员工原话，没有官方发布时间；功能形态以正式发布为准
    为什么值得看：企业级 coding agent 工作台的「团队共享项目、定时任务、线程汇总」正在变成 Claude Code 的标配，他做的工作台要想清楚和这块的差异在哪
  6. Grok Bot 准备上线 Slack 集成：每个 Bot 可以单独连 Slack，在 Slack 里私信或 @ 它，用的是同一套插件、上下文和记忆；预计随 macOS 1.1.0 版本到来（TestingCatalog 爆料，未正式发布）：界面文案原话「You can DM or @ mention X Marketer in Slack」（TestingCatalog 原帖）
    前提或争议：只是测试版界面观察，权限范围、是否以用户身份发言都还不清楚
    为什么值得看：他的简报交付和群协作都走聊天渠道，上线后例行任务可以直接在 Slack 里触发和回帖；接入前要先看清 Bot 在 Slack 里能读哪些频道
  7. Google 统计内部上亿条 Agent 步骤：13% 读文件的会话会看到带工单号的旧 TODO，其中 6% 会去处理那个 bug，83% 的动作开发者根本没要求；绕路的会话平均多走 70% 步骤、多花 77% token（yibie 解读 Google 文章）：41% 追的是已关闭的死工单，57% 是工单还开着、Agent 自己扩大范围。Google 用 Agent 跑「搜注释、核工单、查历史、发评审」四步，6 个月删掉数千条过期引用，人工评审接受率超过 95%（yibie 原帖）
    前提或争议：yibie 转述，Google 原文链接在他的评论区，这里没逐字核对；适合有工单系统的团队，没有工单链接的 TODO 核不了
    为什么值得看：代码库里的旧注释会被 Agent 当成指令。可抄：定期扫 TODO(bug/ 和 FIXME(bug/，对照工单状态清理；新 TODO 必须带工单链接或日期
  8. MaxxBench：把 89 道 DeepSWE 题的说明或初始代码做小改动，原本都在 74% 左右的模型拉开 23 个百分点；Deedy 称只有 Opus 5.5 改题后分数反而更高（作者自建评测）：作者问「是会写代码，还是会做 DeepSWE」；Hamel 认为「刷榜产业链如履薄冰」（loresjpg 原帖、Deedy 原帖、Hamel 原帖）
    前提或争议：作者自建的 89 题，题目改动方式没有第三方复核；「只有 Opus 5.5 变高」是 Deedy 的读法，他自己也说对 Opus 5 了解不多
    为什么值得看：选模型不能只看公开榜。可抄：拿自己仓库的任务做几份「换个文件名、改一句需求」的变体，看分数掉多少
