通往 L4 软件工程 · Itamar
这篇文章讲什么？

各阶段都有 Agent，还不等于软件工厂

作者 Itamar Friedman（Qodo 联合创始人兼 CEO）：从「Agent 参与整个研发流程」到「有了软件工厂」，中间还隔着大量工程工作。

目标是有边界的 L4（一类定义好的工作能自主完成、给出证据、自己处理失败），工程团队要自己搭并拥有这套系统。

Agentic SDLC：规划、实现、审查、测试各阶段都由 Agent 参与的研发流程。

作者认为这段距离正是工程工作现在所在（或正在转去）的地方，也是团队最持久的优势来源，哪怕工厂的大部分是从供应商买的。

中文转述见 @shao__meng 的摘要帖；本页依据作者 X Article 原文。

开篇；X Article「The Path to L4 Software Engineering」

为什么要以工厂为改进单位？

改进单位是整个工厂，不是生成速度

生成一次改动只要几分钟、弄懂它的后果却要几小时时，加速的只是大流程里的一段。

作者的优先级：System > Agents > LLMs；改进一次系统，能惠及之后成千上万次改动。

剩下的工作包括：决定该改什么、守住架构约束、检查下游影响、确认结果对用户有效。

可工程化的环节：需求怎么变成可执行的检查、组织知识怎么送到对的 Agent、改动怎么验证、失败怎么变成下一次的教训。

作者引 OpenAI 的 harness engineering 报告：工程师投入在环境、仓库知识、架构约束和反馈环上。

「Why the factory is the right unit of improvement」
Agentic SDLC：参与每个阶段都有 Agent；人在中间澄清需求、改计划、解读失败测试、判断能否上线
软件工厂：负责围绕工作的生产系统：输入、Context、执行环境、验证、权限、交付机制、反馈
实例：Stripe Minions无人值守的 Agent 把任务做到 CI 通过、PR 待人审；明确保留人工审查
要问的问题系统能否把一个定义好的改动走完授权范围内的生命周期，而不用人反复补判断？
参与和负责差在哪？

Agentic SDLC 讲参与，软件工厂讲负责

一个流程可以几乎全是 Agent 写的代码，效率也很高；这两点都说明不了交付系统有多自主。

作者说 Stripe Minions 是「相当可观的自动化」，同时人工审查被明确保留。

「Agentic SDLC describes participation. A factory defines responsibility.」
L0人执行加传统自动化
L1AI 辅助单项活动有 AI 帮忙，工程师主导
L2人监督Agent 做大块任务；工程师盯着、检查、串起结果
L3Agentic SDLC限定条件下跑完流程；人仍是必需的审批或救场环节
L4亮灯的工厂一类有边界的改动走完授权生命周期，含验证、发布、安全回退
L5黑灯的工厂覆盖全部软件工程工作；仍需目标、授权和问责
借自动驾驶的哪一课？

L4 的能力来自它的运行边界

SAE 定义：L3 在限定条件下自动驾驶，但可能要人接管；L4 在限定条件下不需要人来驾驶以化解风险。

L4 不是什么都做、哪里都做；作者说这套软件分级是他提出的框架，不是行业标准。

「亮灯」指工程师仍拥有工厂的边界和演进。L4 的条件是不需要人及时介入来控制失败。

分级描述的是某个工作流和运行范围，不是整个组织：内部服务的常规改动可以瞄准 L4，支付授权的改动仍由人紧密控制。把整个组织叫「L4」会藏起关键区别。

作者也提到 @DanShapiro 的五级文章是另一种软件自主阶梯。

「The useful lesson from autonomous driving」
往 L4 多走的一步是什么？

先划准入范围，再定可评估的成功

准入规则（哪些工作允许自主执行）要写清仓库、变更类型、依赖、环境、权限和花费上限，以及什么让任务不合格。

常规依赖升级和核心授权模型改动，不该因为同一个 Agent 都能尝试就拿到同样的权限。

ticket 很少是完整规格。相关要求可能在架构决策、事故记录、客户承诺或某个工程师的记忆里。

工厂要拿到这些 Context，并在实现之前暴露歧义，避免实现把一个假设变成系统行为。

「The extra step is engineering the boundary」前半
误解再派一个 Agent，叫它「reviewer」，就是独立验证
实际两个 Agent 可能共享同一个错误假设；独立验证要受保护的验收标准、分开的权限、基于可观察行为的检查
StrongDM 的做法场景放在代码库之外，减少 Agent 满足测试却没交付预期行为的机会
Anthropic 的做法生成器与评估器分开有帮助，但评估器仍要校准，也仍有局限
验证怎样才扛得住？

写代码的 Agent 不能改通过条件

验证必须扛住生成过程的激励：产出改动的 Agent 不应能悄悄重新定义「怎样算通过」。

验证本身也是一个工程系统，也需要被评估。

StrongDM 的工厂写了两条挑衅规则：代码不得由人写，代码不得由人审。作者认为更有启发的是规则周围的机制：场景、验证 harness、外部依赖的行为替身。

@DexHorthy 的「Harness Engineering is not Enough」：通过短任务和几个月里保持代码库可维护是两个目标。作者不把今天的绿测当成工厂在保住明天改系统的能力；架构要有显式约束，连续改动的效果要长期观察。

「The extra step is engineering the boundary」后半
一次改动怎么走完有边界的 L4？

准入、验证、发布、留证据，出事先回到安全状态

补充：模拟器把原文各环节串成一条路径；例子类型来自原文，具体情节是教学示例
活动量Agent 数量、生成的代码行数、无人值守运行的小时数
结果合格工作多常正确完成、还剩多少人工、什么漏过了验证、失败花了多少代价
每次放行的记录需求、通过的检查、相关约束、部署结果、未解决的不确定性
证据来源确定性检查、模拟、对抗测试、模型辅助审查、生产观察
怎么说明一次改动可以放行？

放行要有可查的证据，不要信心声明

没有一种证据能普遍证明正确；合在一起，它们支撑一个具体边界里的一个具体决定。

评价工厂本身也一样：被拒的任务和紧急干预都要算进账里。

「Evidence > Confidence claims」
L4 和「让 Agent 跑一夜」差在哪？

L4 的标志是止损不靠人立刻接手

安全回退可以是：不发布、停止发布、关掉功能、恢复上一版本。

系统可以在到达安全状态之后请人帮忙；控制住失败不依赖人马上重建现场再接手。

作者说这是 L4 类比里他认为最有价值的部分。

回滚不总是可用：破坏性迁移可能让回滚做不到，运行边界要在工厂开工前把这一点算进去。

原文：这是比让 Agent 通宵工作更高的标准。

「Evidence > Confidence claims」后半
作者要避开的旧问题
—名不副实把「各阶段有 Agent」当成「有了软件工厂」
用这套做法时仍会犯的错
1假独立第二个 Agent 叫 reviewer，却和作者 Agent 共享错误假设
2今天的绿测短任务通过，不等于几个月后代码库仍可维护
3报活动量用 Agent 数、代码行数代替结果和失败代价
作者承认仍在的限制
4无普遍证明每种证据都证明不了普遍正确；评估器仍要校准
5回滚有限破坏性迁移可能让回滚做不到
旧问题、仍会犯的错、仍在的限制

绿测和多一个 Agent，都不等于验证过

作者要的不是更多活动，而是能扛住生成激励的验证和能查的证据。

两个 Agent 可能共享同一个错误假设，所以「reviewer」这个名头不带来独立性。

「The extra step…」「Evidence > Confidence claims」
可以买专门的 Agent 和平台：代码审查 Agent、维护 Context、管标准、汇总证据
必须自己拥有组织 Context、架构、验收标准、权限、证据、运行边界；诊断失败并改系统的能力
作者的类比买云服务后，工程师仍要设计架构、连组件、写业务逻辑、运维结果
谁来做工程组织搭工作流；产品团队给领域知识；平台和安全团队给共享设施与控制
买还是自己搭？

能力可以买，工厂得自己搭、自己拥有

作者认为对很多团队，买专门能力是搭工厂的明智做法；买来的是积木，系统要团队自己建、自己运行。

审查质量是要投入和度量的能力：选审查 Agent，要看它能否对照整个系统和组织标准挑战改动。

「Ownership > Implementation」
深入一层

同一个修正反复出现，就该写进系统

作者连到 Kief Morris 的「人在环上」（on the loop）：工程师改进的是产出工作的机制，不只是这一次的改动。

同一条架构修正每次都要人补，说明工厂还没吸收团队知道的东西。

这些知识记录了组织怎么造软件、从失败里学到什么、愿意把哪些决定交出去；作者称之为战略资产。Agent 承担越多实现，拥有这些知识越要紧。

补充（衔接）：这和张立行《Context 与 Loop》里「写进提示，不如写进代码」、Holon 文章的验收防线是同一方向；本文的新角度是按运行边界分级。

「Ownership > Implementation」后半；衔接为补充
作者建议从哪里开始？

从一类工作起步，按证据扩大边界

每次干预都说明缺一项能力或边界不完整：有的该补工具或 Context，有的该继续留在自主运行之外。

作者选有边界的 L4，不选推测性的 L5：它给团队一个具体要建的系统和一个具体的评判标准。

工厂靠已证明的表现扩大范围；后果大或不确定性高的地方保留更窄的限制。

每家公司的选择会不同，因为系统、义务和对失败的容忍度不同。

作者的结论：团队的优势越来越来自这套系统把意图变成软件有多可靠，以及每次结果能多有效地改进下一次运行。
