Agent 时代先抓住 Context 与 Loop

作者张立行（@bylixing）：Context 决定这一次好不好，Loop 决定下一次能不能更好。

目标：调度越来越轻松，不要让自己成为系统的瓶颈。

底稿来自两段合计 80 多分钟的语音分享。作者写：人类读思路和逻辑；执行细节丢给 Agent。

完整版在作者博客；X 上发了同题 Article。

引子；博客标题与开篇
为什么偏偏是这两个词？

Coding 先跑通，因为 Context 与 Loop 齐了

作者列三点：高价值、数据高质量且充分、验证可闭环。第二点对 Context，第三点对 Loop。

这两件事和具体用哪家模型无关；模型变强是供应商的进度。

作者引 Cloudflare：AI 把过去最慢最贵的实现，变成最快最便宜。瓶颈移到两头：给了什么 Context，以及怎么验证做对了。

「一、为什么偏偏是这两个词」
全文主线是什么？

静态预先写好，动态从 Loop 长出来

静态 Context：规则文件、Skill、Memory、工具配置。动态 Context：验证结果、错误复盘，再回流成下一次材料。

有意识地构造 Context，也有意识地构造 Loop。

1预置 prompt各家内置系统提示；闭源基本不能改
2全局规则~/.claude/CLAUDE.md、~/.codex/AGENTS.md
3项目规则仓库根目录 CLAUDE.md / AGENTS.md
4MCP / Skill / Memory外接工具、按需手册、跨会话记忆
?原则每样东西都要回答：它凭什么在这里？
静态 Context 怎么治？

开场进对话的东西，都要能被删掉

作者原则：像珍惜自己的注意力一样，珍惜 Agent 的上下文窗口。

先留住行为轨迹：Claude Code 默认约 30 天后删本地会话，改配置项就能长期保存。

Git 被作者称为 Agent 时代最好的软件：低成本存差异，行为可追溯到当时的 prompt、harness（包在模型外的软件层）和代码。

MCP：有 CLI 就优先用 CLI；Skill：优先吸收，要装就装到项目；Memory：多客户端时不要依赖某一家自带记忆。

「二、静态 Context」地基与分层表
规则怎么分层？

一份底稿，按工具与角色拼接，不按模型分

主脑（拆任务、判断、验收）与执行器（拿任务卡改代码）的 Context 分开构建。

作者给注入量上硬闸：主脑每侧规则不超过 24KB，执行器不超过 12KB。

作者不按模型分规则：工具多、证据难分清是模型还是外壳问题；执行器多跑在 Pi 上，模型轴和外壳轴拆不开。

方向上跟顶级模型团队「大删系统提示」，节奏建议晚约半年：圈外人没有近乎无限的高质量 Token。

Pi：开源 Coding Agent 外壳，系统提示可自控，可接任意模型；作者把杂活优先交给 Pi。

「全局规则」「三、执行层」
Advisor 解决什么？

更强判断力，加上一份干净的独立 Context

两个问题：执行层判断力一般；上下文腐烂（窗口填满后智力下降，作者观察到约四五成就可能陷入局部）。

顾问看不到主脑会话史；最简单的日常版是回退（如 /rewind、/tree）。

作者盲测：两个最终撤回的 PR，截断在收尾前问顾问 9 次，9 次都否掉收尾计划。

抽样 21 次决策请教：10 次直接反对，11 次部分同意并改掉关键前提，完全同意 0 次（多为已经不对劲才送审）。

顾问也会错，意见同样要验证。

「四、Advisor」
一次错误怎么变成下次的 Context？

错误经验证与复盘，写进脚本，而不是只写进提示

补充：模拟器把原文多个坑串成一条路径；数字与结论来自原文
Loop 的标本长什么样？

agent-config 用两个月长成可回流的根仓库

演化三步：规矩进版本库 → 坑汇报回同一处 → 脚本和闸门阻止旧坑复发。

关教训单的标准：这个坑现在还踩得到吗？机制上不可能再发生才关。

每周新开 issue：峰值一周 305 张（8 月底到 9 月初），9 月最后一周回落到 159 张。

作者体感：从前高频人在环内才能维持每天约 40 亿 Token；现在同量级消耗，每天只花一小部分时间。

引子数字；「五、Loop 的标本」
低成本编译、基础测试、lint；几秒内、不花 Token
中成本花 Token 的 Agent 审查、录屏再审前端
高成本人参与；只留给真正要判断的地方
原则能用低一档，就不要升到高一档
假绿跳过当成通过；考卷登录没配好却跑了 111 次
硬规矩先喂已知为「否」的输入，确认检查会变红
验证通道怎么选？

低成本通道先串进门禁，判据本身也要验收

作者：代码廉价，测试高价值；目标能拆成可验收条件，迭代就主要是时间与成本。

选语言用十字坐标：纵轴可自动验证程度，横轴领域生态匹配。

纵轴例：Rust 编译即反馈强；Python 更依赖自补测试。纵轴不是越高越好：Rust 编译吃 CPU 与磁盘。

前端审美等难量化目标，很难形成 Loop。

「六、低成本的验证通道」
作者要避开的旧问题
—见前文上下文塞满无关 Skill；人盯着才转得动
用这套做法时仍会犯的错
1只写提示教训停在规则文件，未升到脚本 / 闸门 / 测试
2假绿判据检查永远不会红，等于没写
3压缩误伤省 Token 工具悄悄丢掉搜索与文件原文
作者承认仍在的限制
4难验证工作前端审美、产品方向等，人仍须留在环内
5硬件堵点并发上来后 CI、磁盘、流量轮流成为瓶颈
旧问题、仍会犯的错、仍在的限制

Loop 能记下这一堑，前提是机制真的挡住了

Anthropic playbook：同一错犯两次就写进 CLAUDE.md；但 Skill 只能减少违规，Hook 才能几乎不可能违规。

xAI Lauren 的强弱序：结构不可能错 > lint > 规则/Skill > 只能人审的风格指南。

「写进提示，不如写进代码」；失效例见五、六、七节
People in the loop每一步人看、人判断、人拍板；循环速度跟人能盯多久绑定
People out of the loop人定义「怎样算对」，必要时出场；派活、执行、验证、复盘在环内自转
少了 Context人得一直补充背景
少了 Loop人得一直检查结果
作者做了什么取舍？

从人在环内，走向人在环外

作者原话：能自动检查对错的工作里，越做越累，说明调度方式有问题。

还没法自动验证的地方，人留在环内是正常的；要把能验证的部分不断剥出来。

「写在最后」
深入一层

瓶颈会从精力转到硬件，再摆回精力

作者常同时调度约 20 个主脑、三五十个执行器；门禁 CI 工位从 6 个扩到 84 个（四台机器）。

这是作者自己的阶段性体感，不是说每个人都会这样切换。

纯 Coding 且不依赖单一平台时，作者认为 Linux 更适合 Agent：配置可改、少需人点「允许」。Mac 更适合偏 Computer Use 的图形界面场景。

ADE / ADLC / harness of harness：名字不同，都是在单个 Agent 外再搭可分工、可查证、可留痕的工作环境。
