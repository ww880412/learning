桌面并行工作区派

桌面并行工作区把并发修改与代码审查接起来

以 T3 Code 为参照，这一派用 Git Worktree 为并行任务自动分出工作区，让开发者能在桌面上查看各路修改并审查代码。

Paradev 从 Superset 更名而来，采用 MIT 许可。任意 CLI Agent 都能分到独立的 Git worktree。开发者可在 Diff/PR 视图检查改动、把行级意见交还给 Agent，再看 CI 结果。内置浏览器会自己找到端口。本地版免费，团队云工作区收费；主平台是 macOS，Linux 尚属实验支持。

官方核对｜更名延续了什么

10 月 26 日的更名公告（27 日更新）说明原产品、账户和工作区都延续。仓库列明 MIT 许可、每任务独立 worktree、订阅自备；当时提供 macOS 版及实验性 Linux x64 AppImage，尚无 Windows 版。行级评论回传、CI 状态、端口探测和收费边界在摘录中仍待逐项确认。更名说明 · 项目仓库

Orca 也以 worktree 隔离任务，采用 MIT 许可。作者称其全平台支持，列出 Windows、Linux 和 macOS，移动端仍在测试。按原文，约 40 种 Agent 配置模板可供调用，操作时可在 Chat UI 与 Terminal 之间切换。

官方核对｜Orca

MIT 仓库和官网支持自带 Claude Code 或 Codex，在各自 worktree 并行。官网展示 iOS/Android companion 及从 Slack、Linear、GitHub 向 Bots 派活。11 月 21 日的 1.4.268 日志增加了 Bot 的执行工具选项。摘录未逐项确认桌面三平台、移动测试阶段或终端与聊天切换。更新日志

原文数的是配置模板。同期 orca.dev 对照表的「27 supported agents」数的是受支持的 Agent。两种计数无法直接换算，27 既不能证实约 40 种模板，也不足以判错。orca-desktop.com 属于另一款产品，其文档不能解释 orca.dev 或 stablyai/orca。Orca 官网 · 项目仓库

Emdash 桌面端采用 Apache-2.0。来自 Linear、GitHub Issues、Jira 或 GitLab 的 Ticket 可以交给本机 Agent，也可经 SSH 派到远端。作者指出，团队的开发重心已移到面向企业协作的 Emdash 2.0。

官方核对｜Classic 与 2.0

11 月 5 日公告开放团队版 2.0 的早期访问。原桌面版改称 Classic，继续开源并获得修复；首页将新开发归到 2.0。全面发布仍待确认。摘录也未逐项核准许可证、工单集成和 SSH 派单；Classic 的能力不能直接算到 2.0 名下。版本公告 · 官网

作者认为 Traycer 的定位最接近 T3 Code：MIT 开源，用户沿用 Claude/Codex/Cursor 订阅，调度多个 Agent 时没有额外抽成。官方工具也能并行使用本地 worktree 并联动手机：Claude Code Desktop 和已纳入 ChatGPT 桌面端的 Codex App 都仅限自家生态。

在作者评价中，Conductor 曾是 macOS 上口碑最好的 worktree 编排工具之一。写作当时，作者称团队宣布加入 Meta、新用户注册已停、云服务已关闭。

官方核对｜Conductor

公告确认加入 Meta。11 月 4 日的 0.93.0 日志说明了把云工作区迁回本地的方法。官网原计划让 Cloud 在 11 月 13 日转为只读、11 月 20 日关闭，本地产品继续开发。两份官网摘录均未核到停止新用户注册的说法。后来追加的继续开发说明指向 Conductor 整体，不能单凭它判断 Cloud 已恢复。当时未尝试注册或连接 Cloud，关停日程的实际执行情况仍未确认。官方公告 · 版本日志

另外三派

远程控制、终端分屏与团队派单各有入口

自托管控制面 / 移动远程派对标 Lody 和 T3 Code 的移动端。作者将 Paseo 列作高人气的 Apache-2.0 项目：开发机常驻 daemon，可从原生桌面端、Web、iOS/Android App 或 CLI 接入。它主打完全自托管、免强制登录且无遥测，可调度 Pi、OpenCode、Codex、Claude Code 及兼容 ACP 的 Agent。

终端原生多路复用派以 Herdr 为参照。对想避开厚重 Chat UI 的用户，cmux 把监督工作留在 macOS 原生终端里；Agent 启动 Subagents 或协作进程时，终端会自动为它们展开分屏窗格。

团队协作 / 看板 / 项目管理派对标 Raft 和 Multica。作者把 MIT 开源的 Paperclip 视为 Multica 最直接的竞品。团队共用任务空间并审查代码，Budgets 还可给任务或 Agent 设费用上限；触线即暂停，以限制 Token 开销。

Nimbalyst 和 AgentsRoom 用 Kanban 卡片表示会话，便于排任务、跟进度。BotBoard 类似 Multica，让团队从同一份 Backlog 调度多个 Agent。作者称 Vibe Kanban 曾是早期最知名的此类工具，官方已宣布结束运营（Sunsetting），后续由开源社区维护。

官方核对｜Vibe Kanban 的三个对象

4 月 10 日公告说运营公司 bloop 关闭，项目交由开源社区维护，仓库也提示收尾。公告给远程服务预留 30 天，随后转为完全本地运行，本地工作区可继续使用。材料未测试观察日的远程端点或本地工作区，也没有衡量社区维护活跃度。停运说明 · 项目仓库

AI 解析补充 · 非作者原文 · 非用户判断｜Emdash 为什么跨派

桌面派看工作区，远程派看接入途径，终端派看界面，团队派看协作对象。Emdash 既提供桌面入口，又按工单组织任务，还可经 SSH 派到远端。四个派名回答的问题不同，要分辨同派内部的工作方式，还得用后面的五维。

AI 解析补充 · 非作者原文 · 非用户判断｜谁给个人工作区派单

作者把 Orca 列入个人桌面并行工具，但团队也能从 Slack、Linear 或 GitHub 给 Bot 派活。同一产品能够同时组织个人并行与团队分工，桌面分类只解释了任务链中的一段。

共同痛点

自带 Agent 后，仍需处理并发、审批与状态跟踪

BYOA（Bring Your Own Agent）是作者归纳的共同架构：这些工具几乎都可接入本机 CLI 和已有订阅，不要求绑定某一模型或自研 Agent。作者把剩下的工程问题分成三类。

AI 解析补充 · 非作者原文 · 非用户判断｜怎样核验「几乎都」

两个官方原生方案只覆盖自家生态。核查 BYOA 时分别记录：能否调用已安装的执行工具、能接哪些供应商、指定订阅能否沿用。看到能启动一个 CLI，只够填第一项。

并发时，独立沙盒或 Git Worktree 可避免一个 Agent 覆盖另一个的工作。离桌后，长任务经常要等人授权或 Review，后台保留会话、手机接手审批便有了用处（Human-in-the-loop）。回看进度时，开发者可直接查看可追踪的任务、Diff、会话或看板状态，省去翻终端日志的工夫。

AI 解析补充 · 非作者原文 · 非用户判断｜隔离和审批各能证明哪一步

设两个 Agent 在各自 worktree 修改同一函数。两份修改都能留下，到合并时仍可能冲突。并行编辑、发现冲突、完成合并并通过 CI，需要分别取证。

从功能推到适用场景，隐含了几个假设：入口反映主要工作习惯，个人与团队需求容易区分，提供某个功能就能完成相应流程。看到手机客户端后，还要检查它能否收到权限请求、人能否在手机批准、获批后原会话能否接着运行。

五维比较

同一款工具，换个比较维度就有不同的邻居

作者比较了 5 个维度。先看交互：习惯对话可看 Traycer、Paseo 和 T3 Code；按终端进程分屏看 cmux 和 Herdr；按工单或看板推进有 Emdash、Multica 和 Paperclip；把 Agent 当 Slack 频道成员则对应 Lody 和 Raft。

再看使用者。Orca、cmux、Paseo、Herdr 和 T3 Code 偏个人，重启动速度和本地操作体验。Paradev (Team)、Lody、Paperclip、Raft 和 Multica 偏团队，要处理任务分配、成本/预算审计，也要支持 Skill 共享。

第三个维度是 UI 可塑性。作者把 Herdr 评为独一档：其中的 Agent 可以改侧栏、开面板，其他传统 GUI 或 TUI 的布局基本固定。

第四看部署。Lody、T3 Code 和 Paseo 从移动端连本地 Daemon；Emdash 和 Herdr 可通过 SSH 连后台 Server；Paradev、Paperclip 和 Multica 对应自托管服务端或云端。代码放在家中或云上的 Linux 服务器时，作者认为 Paseo、Herdr、Emdash 以及支持 Docker/Helm 的 Multica 用起来更顺手。接下来的第 5 项关注任务启动之后的工程环节。

第 5 项看工程闭环。cmux、Lody 和 T3 Code 侧重启动 Agent、随时交互。Paperclip、Multica 和 Paradev 属于较重的一组，覆盖范围延伸到 PR Review、CI 反馈、按时触发 Autopilot 或费用熔断。

AI 解析补充 · 非作者原文 · 非用户判断｜从功能到评价，用了什么标准

Paradev 特别注明 Team，受众还取决于产品形态。Herdr 的侧栏可由运行中的 Agent 改动，是具体功能描述；评为独一档则需要横向比较。远程部署更顺手也是作者的判断。重度闭环列的是整组工具涉及的环节，原文没有逐款验证每项能力。

闭环多完整，取决于把哪些步骤算进去；谁是最直接的竞品，取决于按任务管理还是部署方式划市场。口碑与人气需要用户样本，位置是否独特需要系统比较，单款官网无法单独证实这些评价。

官方核对｜其余项目的证据范围

Paseo 的无遥测和免登录、Herdr 的动态 UI、cmux 自动分屏、Paperclip 的预算暂停、Multica 的 Docker/Helm、Traycer 的订阅与收费，以及官方原生方案的集成和移动联动等，均按原文描述。随附材料没有逐项核对，本页未实测；缺证据不能直接判错。

选型参考

作者按工作习惯给出候选工具

个人本地多开时，作者列出 T3 Code；需要跨平台时列 Orca；想在同一处做完 PR/Review 时列 Paradev。

以终端为主或做远程开发，作者列 Herdr（SSH 会话持久化、UI 可编程）与 cmux（macOS 原生终端）。从手机遥控自家机器、又看重隐私和自托管时，作者列 Lody 与 Paseo。

团队要像给成员派活一样管理 Agent，作者按现有协作方式细分：沿用 Linear/Jira 工单流程，可看 Multica 或带预算熔断的开源项目 Paperclip；沿用 Slack 式频道沟通，可看 Raft。

AI 解析补充 · 非作者原文 · 非用户判断｜候选清单是怎样推出来的

先按职责划定赛道：执行工具之上还有人派单、跟进的管理层。再按代表产品的入口和卖点画出四派。它们共同处理并发、审批和状态跟踪，所以手机、终端与看板可以放在一起比较。接着用五维拆开同派差异：桌面工具可能侧重启动，也可能把审查意见送回；团队可能沿工单交接，也可能在频道派活。文末才把场景对应到候选。

例如，把 PR 某一行的意见直接交回 Agent 修改，解释了作者为何在重视审查的分支列出 Paradev。要比较谁做得最好，还需要相同任务下的耗时、成功率和成本；原文没有这些数据。

AI 解析补充 · 非作者原文 · 非用户判断｜状态词指向哪个对象

读到「目前」「已关停」「支持」，记下版本、服务范围、观察日期及验证方式。Conductor 本地继续开发可与 Cloud 的关闭计划并存；Emdash Classic 持续修复可与新开发转向 2.0 并存。Paradev 则说明改名后账户和工作区仍可延续。

AI 解析补充 · 非作者原文 · 非用户判断｜四则核验练习

1. 重画 Paradev 的审查流程。 从启动 Agent 开始，依次列出独立修改、查看 Diff、收到 PR 行级评论、交回 Agent 修改、查看 CI。每一步旁留三栏，分别填原文怎样描述、官方摘录支持什么、还需如何运行验证。

2. 拆开 Conductor 的状态句。 给加入 Meta、新用户注册、Cloud 服务、本地开发各留一行。逐行填公告日期、适用对象、公告原意、实际验证情况。找出关闭计划与后来追加的开发说明，把它们放回各自适用的行。

3. 给 Orca 做两次分类。 画出从 Slack 派单到独立 worktree 执行的过程。先按人从哪里下任务分类，再按代码在哪里并行执行分类，写下两次分类各解释了哪一步。

4. 给 Orca 的两个数字建记录。 将约 40 种配置模板与 27 个受支持 Agent 各写一行，分别填产品身份、版本与日期、计数对象、能否逐项去重。材料没交代的格子留空，最后写出还差什么证据才能比较。
