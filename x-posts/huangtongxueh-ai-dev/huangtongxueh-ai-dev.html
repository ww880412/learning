少写死工作流，多给 Agent 上下文、环境和判断依据

模型能力增强后，一些原本被认为有用的约束和工作流（规定 Agent 每一步做什么的固定步骤），正在变成模型的噪声。

作者对 Harness 的理解：正确的上下文 + 能执行任务的环境 + 判断结果的依据。

作者入职约两个月，做 Agent 开发，同时维护后端业务。工具分工：Codex + GPT-5.6 Sol 写代码；Astra 做规划；pi + DeepSeek V4 Flash 做简单需求；Claude 5 Fable 做对抗性审查和代码审查。

需求对齐怎么做？

追问到不改变方向为止，结论写进文件

材料常常互相矛盾：PRD 没更新，会上补了限制，聊天里改了优先级。

作者自己对需求的理解，也可能包含一些没有说出来的假设。

停止条件：剩下的问题不会显著改变实现方向和验收结果，就开始开发。

CONTEXT.md（对齐结论文件）记录问题、范围、关键决策和验收标准。后面实现和审查的 Agent 共享这份文件，不用重读全部对话。

作者不要求提前规划所有细节，否则对齐本身又会变成一套重的工作流。有些问题他当场答，有些要回头找产品确认。

「二、我的日常开发工作流」第 1–4 段及配图
一个增量怎么走完全程？

每个小增量都走一遍：对齐、实现、审查、端到端测试、小 MR

端到端测试为什么能拦住问题？

Agent 从真实入口跑到结果，自己找证据

测试写得多，上线仍会出错；缺的是让 Agent 在自测阶段跑真实环境。

Agent 能查库表、查日志，也能连接机器排查问题。

  • 被测产品本身是 Agent 时，流程跑通还不够，还要检查答案质量（Agent Eval，原文点到为止）。
  • 四件事：一键起测试环境、造数据、明确账号权限、可清理重置；用浏览器、API 或 CLI 跑真实流程；只读数据库 MCP 查落库，日志 Skill 和 Trace 查链路；稳定操作写成脚本，入口和排障写成 Skill。
  • 能工具化的做成 MCP 或 CLI，可复用的步骤写成 Skill，最后统一成一个测试 CLI。
  • 浏览器自动化：作者推荐 ego lite，配 pi + DeepSeek V4 Flash。

一句短 Prompt 为什么有用？

说出方法名，模型就按学过的做法分析

这些方法在论文、代码和设计文档里高度标准化，模型训练时见过很多。

一句组合 Prompt 指定五个动作：重新定义问题；攻击假设；验证贡献；删除复杂度；整理系统边界。

作者的组合句：「从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。」

作者原话：它们不是魔法咒语。说出方法名之后，还要补上当前任务真正必要的约束。

「我常用的 Prompt」及配图
实例：消融实验怎么用？

系统变快了，不代表每项改动都有用

模型从 Baseline 起，比较逐步叠加的组合：只加索引、索引 + 缓存、三项全加。

原文的例子：最后可能发现，剩下两个复杂方案只贡献了 20ms。

这样能看清哪些代码值得保留，哪些复杂度可能没有必要。

「消融实验」一段
普通问法帮我看看这个技术方案有没有问题。
换成对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。
方案：引入分布式锁，解决重复请求普通问法 → 模型讨论锁的超时时间怎么设
对抗性审查 → 模型追问重复请求真的需要互斥吗？接口幂等能不能解决？锁服务挂了怎么办？锁过期了业务没执行完怎么办？
实例：换一句话，模型关注什么？

让模型推翻方案，而不是替方案找理由

普通问法让模型在方案内部调细节。

对抗性审查让模型先找能推翻核心假设的反例。

作者说这类 Prompt 特别适合方案评审和代码审查。

同类方法：奥卡姆剃刀。例：Agent 设计了「Kafka + Redis + 分布式锁 + 状态机 + 定时补偿」，用奥卡姆剃刀重审后，它很多时候会发现单库写入时一个事务加唯一索引就够了。

作者常用 ponytail Skill 清理过度设计，因为 GPT-5.6 Sol 很多时候会过度设计。

作者做了什么取舍？

不逐行读代码，靠小 MR 和端到端测试换来

审查顺序：先看验收标准，再看端到端测试结果，最后沿业务路径看高风险部分。

代价：开发者仍要对业务需求负责，高风险部分必须亲自看。

原文：业务需求的第一责任人仍然是开发者。如果不做审查，在大型系统里很容易出问题。作者的说法：你也不希望半夜被叫起来 On-call，最后发现是 AI 写的代码出了问题。

「二」末段、「四、怎么 Review AI 写的代码」
深入一层：下一步改哪里？

下一步该提速的是审查，不是写代码

Agent 可同时推进多个任务；只让它多写，待审代码会积压。

作者接下来想改进的：让重复问题在交到他手里之前，就被发现和修复。

工作流要定期做减法：Astra 更新后，作者删了 AGENTS.md 里过严的约束。

这是作者的下一步目标，不是已经做到的结果。人只集中判断：需求有没有理解对、关键业务逻辑是否成立、还有哪些风险没验证。

MR 多时可以建 Review Bot，把 Git 变更和预设的审查步骤结合起来。它的价值看能否减少有效问题的遗漏和人工负担，不看它评论了多少条。

「四」第 4 条、「五、一些总结和思考」
1沉淀一个步骤重复超过三次，就让 Codex 整理成 Skill
2复用自测里反复做的操作整理成 CLI、脚本和 Skill，交给同事复用
3学习AI 减少了亲自踩坑的机会；每天留一部分时间学习和复盘
4第一步挑一条最常做的自测路径，让 Agent 独立跑通、保留证据，再把有效步骤沉淀下来
