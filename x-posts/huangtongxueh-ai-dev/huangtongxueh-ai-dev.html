  • 弊端一：Token 消耗得很快。
  • 弊端二：上下文已经够了，模型仍沿流程往下走。
  • 模型变强后，一些约束变成了噪声。OpenAI 发布 Astra 时写过博客，讲怎样清理不必要的 Skill 和系统提示词。

工具分工：不同任务用不同模型

原文 · 一、我目前的工具分工

作者按任务分配模型。

  • 写代码交给 Codex。
  • 规划交给 Astra。
  • 简单需求用便宜快速的组合。
  • 审查交给另一家的模型 Claude 5 Fable。

常用的 7 类 Skill

原文 · 一、我常用的 Skill
  • grill 把目标、约束和取舍问清楚，写进 ADR 或 CONTEXT.md。它能挖出前期没想到的问题。
  • implement 配合 grill 用。
  • ponytail 作者常用，因为 GPT-5.6 Sol 常常过度设计。
  • handoff 一般从 Codex 交接给 Claude Code 或 pi agent。
  • 建议：一个流程重复超过三次，就让 Codex 整理成 Skill。

短 Prompt 是模型的「思维快捷键」

原文 · 一、我常用的 Prompt

作者很少自己写大段 Prompt。需要长 Prompt 时，让 Codex 生成。比如让 Codex 写一份交接 Prompt，交给 GPT Pro 做方案设计。

短 Prompt 有时「一句话顶几千句话」。

它们不是魔法咒语，是人类知识里高度标准化的方法论。

第一性原理：不要沿既定方案优化，重新问该怎么解

原文 · 一、我常用的 Prompt

原文 Prompt：

不要基于“加 Redis 缓存”这个既定方案继续设计。从第一性原理分析这个接口为什么慢，以及最小必要的解决方案。

适合你怀疑「题目本身可能就问错了」的时候。

对抗性审查：不帮方案找理由，想办法证明它是错的

原文 · 一、我常用的 Prompt

原文 Prompt：

对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。

普通问法是「帮我看看这个技术方案有没有问题」。这类 Prompt 适合方案评审和 Code Review。

消融实验：系统变好了，不代表每样东西都有用

原文 · 一、我常用的 Prompt

原文 Prompt：

给这三个优化设计消融实验，判断真正的收益来自哪里。

例子：加索引、Redis 缓存、批量查询后，800ms 降到 100ms。消融后可能发现只加索引就降到 120ms，另外两个只贡献 20ms。

奥卡姆剃刀：效果差不多时，选假设更少的方案

原文 · 一、我常用的 Prompt

原文 Prompt：

用奥卡姆剃刀重新审查这个设计，在满足需求的前提下，删除所有非必要机制。

模型容易为了「完整」过度设计。所以这句话对 Coding Agent 尤其有用。

高内聚低耦合：重新检查代码的职责和边界

原文 · 一、我常用的 Prompt

原文 Prompt：

按高内聚、低耦合原则审查 OrderService 的职责边界，不要为了拆而拆。

模型会问：哪些逻辑属于订单领域？哪些应该通过稳定接口交给其他模块？它激活的不是「拆文件」，是模块化、信息隐藏、依赖方向的判断。

几十个字，指定五种认知动作

原文 · 一、我常用的 Prompt
从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。

作者的看法：与其给模型写死整套流程，不如告诉它用什么方式思考，再补上必要的约束。

需求对齐：问到不影响方向就停

原文 · 二、日常工作流
  • 材料往往不完整、不一致。
  • Agent 结合团队 Wiki 和现有代码理解材料，再连续追问目标、边界和取舍。
  • 有些问题当场答，有些要找产品或同学确认。
  • 不要求提前规划所有细节，否则对齐又变成重流程。
  • Spec 记录问题、范围、关键决策和验收标准。后面的 Agent 共享这份上下文。

实现：简单直接做，复杂再并行

原文 · 二、日常工作流
  • 只有能独立推进的部分，才交给 subagent 在不同 worktree 并行开发。
  • 编码 Agent 先自测。它认为可交付时，再按复杂度引入其他 Agent 做交叉对抗性审查。
  • 问题统一反馈给 Codex 修复并重新验证。
  • 人工 Review 前先跑端到端测试。
  • 作者不逐行读代码，看测试结果和核心业务逻辑。前提是每个 MR 足够小。

测试多不等于放心：缺的是环境

原文 · 三、Agent 友好的端到端测试
  • AI 很擅长写测试，常给一个 Bugfix 写几百行。
  • 核心问题：Agent 没有端到端测试环境，编码和自测时发现不了问题。
  • 作者的环境里，Agent 能查库表、查日志、连机器排查。
  • 做法：能工具化的做成 MCP 或 CLI；可复用的流程写成 Skill。
  • 前期花功夫，但能加快开发，减少返工和线上问题。

搭建 E2E 环境的四件事

原文 · 三、Agent 友好的端到端测试
  1. 熟悉环境：一键启动、造测试数据、版本/账号/权限、清理与重置。
  2. 操作业务系统：浏览器、API 或 CLI 跑真实流程。
  3. 查库表和日志：只读数据库 MCP；日志 Skill + Trace。
  4. 复用繁琐流程：稳定操作写脚本，入口和排障写 Skill。

四个有效做法：工具取证，契约判对错

原文 · 三、Agent 友好的端到端测试
  1. 浏览器自动化：推荐开源浏览器 ego lite；搭配 pi agent + DeepSeek V4 Flash 跑得快。
  2. 统一测试 CLI：环境检查、数据准备、场景执行、结果查询、清理。
  3. 工具服务于验收：预期结果来自业务契约，不能把系统返回当正确答案。
  4. 产品是 Agent 时：还要检查答案质量，即 Agent Eval（原文不展开）。

复杂业务里，系统可能返回一个看似合理、其实不符合需求的结果。

Review AI 代码：开发者仍是第一责任人

原文 · 四、怎么 Review AI 写的代码

不做 Review，大型系统容易出问题。你也不想半夜被叫起来 On-call。

  • 不能只看测试通过了多少。
  • 模式稳定的 CRUD 可以少看，作者现在已经不看了。
  • Review Bot 和直接调 pi agent / Claude Code 做对抗审查不同：它专门服务 MR。

最大的瓶颈是 Review 速度

原文 · 五、总结和思考
  • Agent 能同时推进多个任务。人理解业务、确认交付的速度不会成倍增加。
  • 只让它写更多，只会积压更多待审代码。
  • 改进方向：类型检查、测试、业务断言能发现的问题，让 Agent 自己处理。
  • 人只判断：需求理解对不对、关键逻辑是否成立、还有哪些风险没验证。
  • Review Bot 的价值看是否减少遗漏和人工负担，不看评论条数。

Harness = 上下文 + 环境 + 判断依据；定期做减法

原文 · 五、总结和思考
  • 工作流要定期做减法。有些步骤是在弥补旧模型的短板。Astra 更新后，作者删了 AGENTS.md 里一些过严的约束。
  • 局限：代码和测试可能一起误解需求；E2E 只覆盖选定环境和场景，生产的流量、并发、数据分布仍可能出问题。
  • AI 少了亲自踩坑的机会，作者每天留时间学习和复盘。
  • 建议：挑一条最常做的自测路径，让 Agent 独立跑通、保留证据，再沉淀下来。
