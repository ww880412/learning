1条件写在哪？

Agent 要等 CI 跑完，“等什么”写在哪里？等待程序能读到哪些数据？

等待条件写成一段 JS，挂在原 Session 上；Host 在本机反复求值，条件为真时只往原 Session 的队列放一条续跑输入。ctx.read 可读 6 种资源：session、session.group、github.pullRequests、github.workflowRuns、provider.capacity、events。注册即开始检查，默认每 30 秒一次，最小 1 秒。

出处：原文「核心架构与运作流」第 1 节、原表 1；README.md L66（间隔）；README.md L82–87（资源表）

2检查的预算

一次条件检查最多能花多少时间和调用？一直出错会怎样？

每次检查有硬预算：30 秒超时、最多 32 次读取 / 请求 / 命令调用、4 路并发、单次操作 128 KiB。ctx.fetch 只做 GET / HEAD，响应体上限 64 KiB。连续 5 次检查出错，这个等待以 failed 结束。

出处：原文第 1 节；README.md L97–99；context/fetch.ts L16（64 KiB）

3重启不重做

条件已经成立，Host 却重启了：会重跑条件吗？会把 prompt 再发一遍吗？

等待、结果、动作回执和证据都存进本机的 SQLite Ledger。匹配即定局：匹配结果、证据和续跑身份一起原子提交，之后程序不再执行，重启后按同一张回执投递。动作 / Session / Turn 的映射先落盘再执行，确认丢失就对账，不重发。

出处：原文第 2 节；README.md L24（ledger 只在本机）；README.md L115（匹配结果不再求值）；workspace-legacy.ts L79（.sqlite 文件）

4投递前复核

等待期间 PR 被重新 push，或用户按了 Stop，续跑还会发出去吗？

匹配和投递之间有一道复核：准入时重查授权、Session 状态和 Host 捕获的源证据，HEAD 变化或 CI 重跑会让旧证据失效。Session 被 Stop 时检查照做，续跑转为 blocked（原因 target_stopped），不计为检查错误，只有用户显式恢复才解除。Session 忙则入队。

出处：原文第 3、4 节；README.md L116–124；session-actions-legacy.ts L235

5三个内置策略

Lody 自带哪几种自动续跑？默认是开着的吗？模型过载会重试几次？

三个内置 Session 策略：额度恢复 recoverCapacity、合并后归档 archiveAfterMerge、闲置压缩 compactWhenIdle，全部默认关闭，用 lody automation configure 打开。模型过载最多重试 3 次，间隔递增 5 / 10 / 20 秒。

出处：原文第 5 节、原代码 2；README.md L142（默认关闭）；README.md L168–169（重试）；conditions.ts L74–76（开关名）

总结

这篇解决的问题：Agent 碰上挂起、限流、等 CI 这类要等外部事件的时刻，怎样先睡下，等事件到了再可靠地回到原 Session 接着干，而不是靠人盯着。

前提：作者认为不必在核心里写死 GitHub、PR 这类业务概念，也不必另起一套 BPMN / DAG 工作流引擎；续跑的准入、排队和执行仍归既有的 Session 与 Inbox。
