#1

GitHub：用 Copilot 做 Plan / Build / Verify / Observe，而不是只加速写代码

未确认：1.2 billion 次提交和 400% 是 GitHub 自述；441% 来自文中引用的 Faros AI 研究，本期未核原文。限制：文中的能力（会话跨端续上、云端沙箱、Dreaming、Agent Merge、AI Scan、package firewall 等）都是 GitHub Copilot / GitHub 平台功能，迁移到其他工作台要对着各自产品另做对照。

有效的 agentic 工程要把计划、实现、验证和上线后观察连成一条流程，而不是只加快写代码；前提是人先审并批准实现计划，把改动拆成可单独评审的小 PR，并把例行检查放在人工评审之前。

  • Plan：在团队已有的 Slack / Teams 里用 Copilot 把分散上下文收拢，把达成一致的需求写成带验收标准的 GitHub Issues；复杂工作用 Plan Mode 比较方案，审并批准计划后再交给 Copilot 实现。
  • Build 与 Verify：用隔离的仓库副本并行推进不同任务；仓库指令记录约定和验证命令，Dreaming 根据会话和 PR 反馈提议更新记忆、指令或 Skill。评审前用更小的堆叠 PR，并让 Code Quality、按改动深度匹配的代码评审、安全扫描等例行检查先跑完。
  • 用在工作台：Observe 阶段把观测数据和工程上下文放在一起，让 Copilot 起草带证据和回归测试的后续 Issue，再把教训写回记忆和评审指引。GitHub 称 October 有一周超过 1.2 billion 次提交、同比高 400% 以上；Faros AI 研究称 AI 采用从低到高时，PR 停留在评审的时间长了 441%。

#2

作者的做法：导出 Bot 规则，对照官方文档修剪互相矛盾的指令

未确认：12 MIL 词、30% 重复、4 次重叠巡检、10 条里 6 条管其他 Bot、合并权限和时令偏差等，都是作者在自己 Grok Bot 团队上的自报，未见原始导出文件。限制：作者用的是 Claude Code + Fable 5.2 high；换模型或平台时，对照的必须是目标平台自己的官方文档。

作者的做法是把每个 Bot 的指令、规则、例程和记忆导出成一个 markdown，交给另一个模型对照该平台官方文档来找矛盾和重复，人挑选后再写回去；前提是要按这个 Bot 真正怎么工作来评判，而不是按 Claude 的默认习惯，案例数字是作者自报。

  • 先请 Bot 把全部指令、规则、例程和记忆导出成一个 md；再交给 Claude Code 的 Fable 5.2 high，要求对照该平台官方文档（作者写明这和 Claude agent 的最佳实践不同）找破碎、不一致、低效、不再需要或缺失的部分。
  • 作者自报的发现：几乎每次纠正都变成一条新规则（只加不替换）；一个 Bot 的例程提示词合计 12 MIL 词，约 30% 是重复的标准文本；同一文件里有互相矛盾的规则；幕僚长下午跑 4 次重叠巡检，10 条例程里有 6 条是在管其他 Bot；其他 AI 仍读到「工程负责人不能合并」，而作者两周前已授权他独自合并；美国时令切换后一批日程差了一小时却没人发现。
  • 用在工作台：人先挑选再让模型给每个 Bot 写一份 md，由 Bot 重写自己的例程、Skill 和记忆；可选再导出一次做核对。放置习惯：限制放 allow rules，流程放 skills，长参考放文件，短事实放记忆，例程提示词保持短。

#3

Anthropic 官方：Fable 5.2 提示指南，先定 effort，再按观察到的行为加系统提示

未确认：约一半、30%、不到 10%、约 75%、70% 到 80% 等，都是 Anthropic 自述的内部或回放测试，不是第三方评测。限制：加 finishing 文案后，列出剩余工作然后停下的结束方式大多还在；加所有权那句后，模型可能做没人要求的修改，PR 摘要还可能漏掉小改动，要对照 diff。

给 Claude Fable 5.2 写提示词，要先把 effort 显式设为 high 并在 medium、xhigh 上用自己的评测校准，再按实际看到的行为一条一条加系统提示并测量效果和 token；前提是这些推荐写法来自 Anthropic 在自己测试里的观察，数字是官方口径，改 system 或工具说明只能开新对话。

  • API 默认 effort 是 high；low 适合明确任务和高通量子 agent，medium 适合交互写代码和日常知识工作，high 适合难的编程、研究和长时间无人值守，xhigh 要先测到收益再用，max 留给科学和数学这类开放题。从 medium 到 high 在 Anthropic 跟踪的多数编程和知识评测上分数更高，也更费 token 和时间；high 以上收益不稳定，依赖任务。不要把在 Fable 5.1 或 Opus 5.5 上调好的档位直接搬过来。
  • 如果它在 long、多步任务里提前结束（列出剩下的工作、提出继续，或在超时这类普通障碍上停下，low 和 medium 更常见），把官方 “Finishing work” 文案加进系统提示：普通障碍要先诊断再自己想办法推进，有人明确设定的硬障碍要停下并说明；这是起点，需要按自己的场景改。Anthropic 在 medium 档回放编码产品会话时，加了类似文本后，带着本可继续的未完成工作就结束的会话大约少了一半，输出 token 大约增加 30%。因为模型更少来问，有风险或不可逆的操作仍要自己保留确认步骤。
  • 用在工作台：若希望它整理结构，写明它是代码库的所有者和长期维护者；Anthropic 在小型编码任务测试里，没有这句时不到 10% 的运行会合并重复代码，有这句大约 75%，输出 token 大约增加 70% 到 80%，也可能改到没人要求的行为。不想大改就不要加这句；只写 “No drive-by refactors…” 挡不住它。按官方顺序：先显式设 high 并评测 medium/xhigh，再检查从旧模型搬来的提示词，再跑最长任务记录提前结束、乱请示、沉默、过度委派或该重构却只在原结构上打补丁的情况，然后对看到的每一种行为单独加文案并测量。

#4

XERJ Reader-1：模型只写公式，符号引擎按原文用词算出答案

未确认：$0.01 / 1M 输入 token、输出免费、约 1.2–1.6 秒和 3.3 秒、200,000 次问题、$1.00 试用余额，以及“我们所知这类 API 里最低价”，都是厂商 2026 年 11 月的口径和自测，比价页本期未附。限制：预览需等候名单，没有准确率数字，模型还可能改，预览没有可用性承诺和合规认证。

XERJ Reader-1 让模型只写指向原文用词的公式，由独立的符号引擎算出数字，答案可以像表格公式一样复查；前提是它还在等候名单预览，可验证不等于正确，扫描件要先转成文字，十页合同一次问不完，行动前要对照引用在原文里的位置。

  • 神经部分只负责读文档和问题并写出公式，算术交给符号引擎用十进制和真实日历执行。文档里的数字和日期必须是公式引用的原词；模型自己写值只有三种可见情况：指向判定句的是/否、从问题选项里做选择、以及从问题里抄来的常数（例如 “times 12” 里的 12）。
  • 购电协议修正案的例子：问题是签字后多少天新价格生效，原文没有直接写出这个天数。模型写出引用这两处日期的 SUB 公式，符号引擎算出 161。API 还有 execute 调用，可以不经过模型、按保存的公式再跑一遍。公式也可以拒绝：一份没有月费的服务协议被问月费时，返回无值且状态为 “Not in the document”。
  • 用在工作台：需要能站得住的数字时，不要让生成模型直接写答案，而要留下可复查的公式和原文位置。作者记录过一次错误：问 12 月费率时公式引用了 1 月那一行，引擎照算，引用位置把错误暴露出来。置信分高也不能排除错误。

#5

Alex Albert 的做法：新模型到了，用同一条提示词把全部项目审计一遍

未确认：这是作者（Alex Albert）的个人习惯推荐，帖中没有给出他在多少个项目上怎么用、改对了多少的数据。

作者的做法是每次有新模型，就对全部项目跑同一条提示词：读完整项目，找出损坏、不一致、低效或不再需要的地方；只改有把握的，其余列给人审。

  • 提示词原文是：Read this entire project and find everything that’s broken, inconsistent, inefficient, or no longer needed. Fix what you’re sure about and list the rest for me to review.
  • 触发条件是每一次有新模型时，而不是偶尔想到再做；范围是作者的全部项目，不是单个仓库。
  • 用在工作台：把“只改有把握的，其余列给人审”写成审计关卡，避免新模型一上来就大面积改没人确认过的代码。

#6

Grok Bot 1.0：团队共享同一个 Bot，进会议前要人批准，教给团队的知识要先审再入库

老项目未确认：发布页里“更快更可靠”“更高效、更省资源”等没有给出具体数字。限制：本期原文只附了 1.0 发布页、11/11 的 v1.0.1（含 1.0.0）更新日志和会议文档；Tailscale、网页隐藏指令检测、审批卡 30 分钟过期等更早的更新日志条目未附，不能写成 1.0 这次新加的能力。

这次新在哪：2026-11-11 官方发布 1.0，并把会议接入、Microsoft Teams 集成、shared connector、以及队友所教内容须经 Review learnings 审批写进 v1.0.1 更新日志。产品此前已以 Team Bot 等形式在测试和逐步更新。

Grok Bot 1.0 让同一个 Team Bot 进 Slack、Microsoft Teams 和视频会议，并在共享空间里先问再做敏感操作、公开频道先检查是否合适；前提是 Team Bot 只在 Team 和 Enterprise 套餐，会议只在 Team、Enterprise 和 Ultra，企业版要管理员打开会议；别人教给 Team Bot 的内容要等 owner 或 Manager 在 Review learnings 里批准才入库。

  • 1.0 官方发布强调三件事：把 Bot 分享给团队并带进 Slack / Teams / 视频通话；Bot 可以主动认领和跟进未完成的工作，决策仍要找人；浏览和写文档、做演示更稳，也更省资源。共享可以按人、按组，而不必把 Bot 开给整个团队。
  • 加入会议的步骤：把 Google Meet、Zoom 或 Microsoft Teams 链接贴进对话并请它加入做记录；Bot 出示卡片，人批准后，会议主持人再放行。它在会议聊天里回答（Zoom 私聊就私聊回复），结束后在对话里发摘要和待办，有 Pages 时会把更长报告放到页面上。会议用的是发起人的设置。Disable Interactivity 可以让它只听不答。它不会在会议里分享你的凭据；有人要它拿出被扣下的内容时，它会告诉你是谁在问并征求你同意再发。
  • 用在工作台：Changelog v1.0.1 写明，队友教给 Team Bot 的内容会停在 Review learnings，要等 owner 或 Manager 批准。Owner 和 Manager 只有在团队管理员打开 Allow Shared Logins 后，才能把自己的应用登录分享为 shared connector。企业管理员在团队看板 Grok Bot 页的 Bot Capabilities 里开关所有人的会议；关掉后 Bot 不能加入或阅读会议。
