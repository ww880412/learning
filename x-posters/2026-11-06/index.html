#1

Anthropic Managed Agents「Dreaming」：用动态工作流把会话蒸馏成可挂载 Wiki 记忆

发现帖写「300 多万 token」，官方 cookbook 对应是 eleven 个 transcript / 283 KB / $0.36 / 约两分半钟。限制：本图只讲 cookbook「Dreaming with a dynamic workflow」到 Load your sessions（含成本与前置），不含完整跑梦代码与 nightly 脚本全文

官方 cookbook（Brad Abrams）的做法：在 Managed Agents 里用 dynamic workflow 回看历史会话，写成带 _index.md 的 wiki 记忆库供下次只读挂载；示例 eleven 个 transcript（283 KB）默认约两分半钟、$0.36。

  • 流程三步：导出已结束会话为 transcript → lead 写 workflow 并启动（每文件一个 analyzer，再 organizer 一次）→ 业务 agent 只读挂载 memory store
  • 示例成本：eleven 个合成 transcript 共 283 KB，默认设置约两分半钟、列表价 $0.36；预算上限默认 BUDGET_USD=$40，先估再跑
  • 模型默认：lead 用 Claude Sonnet 5.5，analyzer / organizer 用 Claude Haiku 5.5；图中 alt 文也写可用 dreaming_nightly.py 与 cron 凌晨更新

#2

T3 Code 底层架构（老项目）：执行留在原环境，Orchestrator V2 只决事件不做 I/O

老项目架构配图未 OCR；仓库创建日来自 GitHub API（源文件未写 created_at）。限制：本图只讲官方 Architecture 章，不含 Context Handoff、Connection runtime、Provider、T3 Connect 全文

这次新在哪：仓库约 2026-02 创建（>3 个月）；本次是 11-05 架构帖，按官方 docs/internals 拆 Ownership / Orchestrator V2 / EventSink / Checkpoint

meow 结合官方源码/文档的拆解：T3 Code 不自研 Coding Agent，而是在 Claude Code / Codex 等之上做统一控制层；执行始终在 workspace 所属环境，客户端只通过鉴权 RPC 遥控。

  • 所有权边界：Provider 进程、终端、Git、项目文件归 server；共享连接与领域状态在 packages/client-runtime；远程客户端不得用自己的文件系统、凭证或机器状态顶替环境侧
  • Orchestrator V2（Orchestrator.ts）串行命令、只决定事件；EventSink 在同一数据库事务里提交事件、投影、command receipt 和 outbox；EffectWorker 事后做副作用，回执只表示意图已提交
  • 事件日志约保留一天供重连回放与 command-id 重试；Checkpoint 用隐藏 Git refs 抓工作区快照，不往用户分支加 commit

作者 Lieflat 的开源 skill：用两轮对照语料（共 1169 篇、约 520 万汉字）筛出 100 多项指标，先跑脚本+语义检测出报告，你回复接受范围后才改写并复测。

  • 语料：第一轮 629 篇（283 万字），第二轮 540 篇同题配对（256 万字）；脚本层约 90 项可算指标，语义层跑了 50.7 万次判断
  • 工作流：scripts/detect.py 只报告不改写 → 语义候选判读 → 等用户回复 → 按 SKILL.md 最小改写 → report.py 出前后对比
  • 防过度改写：最小改动、信息守恒、不制造参差、结构不动；报告分级 A/B/C/H/X/F，X 级（配对复测否决的）永不改

#6

Stanford CS329Z 第13讲：Agent 评测基准怎么设计，分数怎样才可信

未确认：中文笔记由 meng shao 整理；幻灯片图示布局经 pdftotext 有损。本图重点讲评测框架，不展开各基准刷榜数字

讲义（Diyi Yang / Michael Ryan / John Yang）的框架：基准 = 任务定义 + 评测规则；Agent 评测是「任务+可操作环境」上的多轮行动-观察，输出是轨迹和被改过的环境，不是一次文本回答。

  • 任务定义三件：问题描述、环境（初始资源）、判分；评测规则含跑几次、何时停、推理强度/温度、统一框架还是自带、工具与上网、是否同时报成本/轮数/token
  • 好基准七项：有挑战、真实、有区分度、容易运行（讲义标准是同学一个下午跑通）、容易验证、可解释、耐用；标准之间会冲突，基准要当软件持续维护
  • 可信分数四条：公平（框架/预算/权限一致，有偏离就说明）、可复现、透明（报次数、误差、成本、排除任务）、诚实（不在测试集调参、不只报最好的一次）

「指标一旦变成目标，就不再是好指标。」—— CS329Z L13 / 古德哈特定律，原帖
