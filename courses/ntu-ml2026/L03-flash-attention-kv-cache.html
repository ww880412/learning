GPU 上时间花在哪？

瓶颈常在仓库和工作台之间搬资料

资料只能搬「刚好放得上工作台」的量；上了工作台，运算一瞬间完成。

长度 L 是十万、百万时，连一个位置的 L 个注意力权重都放不上工作台。

  • 讲者声明：这是简化说法，不精确，也不只适用于 GPU（影片 1 07:03）。
  • 直接实作 softmax 要先求最大值 Amax 再算分母，同一批 key 要从仓库读好几次（课件 p17）。
inference.pdf p9–17；影片 1 07:03–15:02
# 一个 chunk 一个 chunk 读（课件 p22–27 整理）
D = 目前见过的最大值；S = 目前的分母
for 第 k 个 chunk:
    D_new = max(D, 这个 chunk 的最大值)
    S = S * exp(D - D_new)      # 修正旧的分母
    S = S + Σ exp(A_i - D_new)
    D = D_new
# 读到最后一个 chunk，D 就是 Amax，S 也对了
机制 1：不知道最大值怎么办？

先假设最大值，看到更大的再修正

第一块先把 D_1 当 Amax 算 S_1；下一块发现 D_2 更大，就把 S_1 乘上一个修正项。

讲者：修正时不用回头看过去的数值，这是 Flash Attention 的核心技巧。

inference.pdf p22–27；影片 1 23:00–29:01
1块chunk 1：读 K、V；用 D_1、S_1 算出 O_1（权重其实不对）
2块chunk 2：读 K、V；用 D_2、S_2 修正 O_1，加上本块，得 O_2
…块chunk k：每一块都修正上一块的结果
B块最后一块：O_B 就是正确的注意力输出
机制 2：为什么能一次读完？

直接累积输出，注意力权重从不存下

Flash Attention 在读 K 的同一时间读 V，边算边累积输出 O，每块都修正前面的误差。

讲者：完整的注意力权重从来没被真正算出来，但最后的加权和是对的。

inference.pdf p27；影片 1 31:01–39:01

机制 3：Decode 时什么可以不重算？

每个 token 的 key 和 value 算一次就存下

Decode 每一步只多一个 token；前面 token 的 K、V 不会变，存在仓库里。

query 只有现在这个位置用得到，所以 Q 不存。

失败：KV Cache 的代价是什么？

KV Cache 用记忆换时间，仓库会被吃光

每层、每个 head 都要存一组 key 和 value，所以每个 token 占很多空间。

讲者：一张 A100 只够存约 10 万 token，而很多时候需要的上下文远超过 10 万。

inference.pdf p35；影片 2 05:04–07:01
共享MQA：所有 query 共用一组 K、V；GQA：分组共用（Llama、Gemma）
压缩MLA（DeepSeek）：把 K、V 压成低维向量
缩小范围Sliding Window（Mistral 7B、GPT-OSS）；Streaming LLM 加看最前面几个 token
丢弃Pruning：一直没人注意的 K、V 丢掉（Scissorhands、H2O）
取舍：怎么让 KV Cache 变小？

省 KV Cache 的方法多半要改注意力

共享、压缩、缩小范围、丢弃四类，都在减少要存的 K、V。

课件总表：Flash Attention 和 KV Cache 不改注意力、不需训练；MQA、GQA、MLA 要改注意力也要训练。

  • 课件总表对 Sliding Window 和 Pruning 的代价都写「可能明显伤害模型能力」（p55）。
  • Pruning：压缩 5 倍、丢掉 80% 的 K、V，很多任务表现差不多；但后来文献指出难任务会变差（影片 2 26:00）。
  • Streaming LLM：只用 sliding window 时，长度超过 window 表现瞬间变差；多看前几个 token 就好很多（影片 2 21:00）。
