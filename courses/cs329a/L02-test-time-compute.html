CS329A 第 2 讲：推理时算力扩展——多采样、怎么挑、怎么组合

这一讲只讲一件事：不改模型参数，靠推理时多花算力把模型做强。先看 Large Language Monkeys：重复采样让弱模型超过强模型，coverage 随样本数呈幂律，前提是有一条「难题长尾」；再看为什么验证是瓶颈（多数投票和奖励模型都抓不住罕见的正确答案）；然后是 Snell 等人的「顺序修改 vs 并行采样」与过程奖励模型引导的搜索；最后是讲者实验室的 Archon：把生成、融合、评审、排序、验证、单元测试这些推理时操作像神经网络一样一层层叠起来，用贝叶斯优化自动搜架构。本页依据官网课表与录像英文字幕（约 63 分钟）。

口述 00:05–02:01：讲者先回顾大模型发展的三个阶段：预训练最耗时，可能要几个月、大量 GPU，数据以万亿（trillions）token 计；微调用的数据少几个数量级，历来算力消耗也小；第三个阶段就是推理时扩展——不改参数、不微调，让模型变得更好用。第一篇是 Large Language Monkeys：同一道题不只问一次，而是反复问，10 次、100 次乃至更多。

口述 00:05–05:01

多采样再挑对的，Llama 3 也能超过 GPT-4o

口述 02:01–04:00：重复采样的好处是能把较弱的模型变强：像 Llama 3-8b 或 70b，单次尝试不如 GPT-4o，但多采样、再从候选里挑出正确的，就能明显超过更大的闭源模型，难的数学、代码、问答题上都是如此。讲者说，模型其实知道答案，只是第一次没告诉我们。这种范式在几乎所有试过的领域都有效，包括模仿软件工程师改代码、提交补丁的 SWE-bench。

口述 03:01–05:01：在 SWE-bench 上，横轴样本数从 1 到 1,000，纵轴 coverage（至少一个样本解出的题目比例）。讲者记得是 DeepSeek-V3 在 1,000 个样本后能超过 Claude 3.5 和 o1 preview，解出更多软件工程题。有单元测试来挑出正确样本时，这就成了端到端自动化地把开源模型做强的办法。

原文 讲者口述 00:05–05:01
口述 04:00–13:03

coverage 随样本数呈幂律，原因是题集里有一条难题长尾

口述 04:00–06:03：上一讲的预训练规模定律说明，增加数据、算力、参数能可预测地降低测试损失。Large Language Monkeys 证明推理时也能定义类似的规律：coverage 与并行采样数之间的关系服从一种指数化的幂律（讲者原话 exponential power law）。

口述 06:03–08:02：从 Llama 3（8B 等）到 Gemma、Pythia，参数从 70 million 到 70 billion，预测的幂律曲线大多都紧贴实际 coverage；也就是说，可以预测要达到某个 coverage 需要多少样本。连 70 million 参数的小模型也有这种规律，而且跨领域成立。

口述 07:06–10:00：为什么是幂律有点反直觉：单题如果 pass@1 是 p，那么 k 次至少一次正确的概率 pass@k = 1 −（1 − p）的 k 次方，单题是指数规律。要让整个题集合起来呈幂律，研究发现充分必要条件是存在一条难题长尾。

口述 10:00–12:00：实测也满足这个条件：大部分题较简单、pass@1 就能解；越难的题 pass@1 越低，数量呈长尾分布，所以才看到这样的规模定律。对工程的含义是：以前公司在预训练上花数亿乃至数十亿美元，微调少得多，单次推理几乎不花钱；现在可以在推理上花算力来提升能力。

口述 12:00–13:03：推理算力还可以离线花：放 agent 去解题、一直生成 token、不断提升答案质量。但重复采样离不开自动验证——样本一多，得知道哪些是对的、怎么挑。有些领域验证比别的容易。

原文 讲者口述 04:00–13:03
口述 12:00–20:01

有完美验证器时很好办；没有时，多数投票和奖励模型都抓不住罕见的正确答案

口述 12:00–14:01：容易验证的例子：数学可以逐步检查；代码可以写单元测试，而写测试有时比写整个程序简单，可以由人来写当验证器。讲者特别提到她实验室的方向「AI as a compiler」：用 LLM 把 PyTorch 源码生成更底层、面向硬件优化的 CUDA 代码。

口述 14:01–16:01：这类任务天然可验证：对任意输入比较两份代码的输出是否一致即可。在 CUDA 生成基准 KernelBench 上同样看到 coverage 随样本数稳步提升，因为有默认的完美验证器。凡是两种语言之间的翻译（Python 或 C++ 移植到 Java 等）都类似，等价性好测。没有验证器的领域，多数投票、基于模型的排序器这类 best-of-n 方法与真实 coverage 之间差距很大，多数投票在 10 或 50 个样本后就基本不再上升。

口述 16:01–18:01：多数投票就是选出现次数最多的答案；coverage 相当于假设有完美选择器。两者的差距在难题上更明显，比如 MATH 比 GSM8K 难。用奖励模型（给每个答案打分的 LLM）选最高分，或组合几种工具，差距依然很大——这就是「生成–验证差距」（generation verification gap）。下周一（第 3 讲）专讲奖励模型和验证器。

口述 18:01–20:01：多数投票为什么不行：最难的题在 1,000 或 10,000 个样本里可能只被解出一两次、三次，正确答案太罕见，投票抓不住。即使容易些的题集多数投票大多管用，最难的那部分题正确答案出现频率仍很低，所以验证上很难找到它们。

口述 19:00–27:01

学生的思路：验证器质量、先自学再采样、多个验证器投票

口述 19:00–23:01：讲者给两分钟讨论题。学生的收获：有好验证器时采样能大幅提高准确率，验证器质量非常关键。也有学生提出让模型修改自己的解、用知识图谱加 RAG 先查资料以兼顾准确率和时间（字幕多处 [INAUDIBLE]，细节听不清）。

口述 22:01–25:05：有学生提出「自学」：先让模型探索领域、积累见解，再进入并行采样。讲者说提升测试时扩展不只重复采样，还有自学、搜索、工具使用，后面都会讲。还有人提到验证不完全准确的领域，比如验证本身是物理或分子动力学模拟，讲者认为可以用模拟、其他工具或另一个模型来过滤错误答案，可以做成课程项目；这里每题 10,000 个样本的数据集已放在 Hugging Face 上，供想缩小生成–验证差距的人使用。

口述 25:05–26:00：问能否生成很多验证器（比如 10,000 个）再对它们的结果投票。讲者说这是很有意思的研究问题，周一会讲她们的 Weaver：对验证器做弱监督集成，不是 1,000 个，而是 10 或 20 个；但计算成本很高。

口述 26:00–27:01：问 coverage 是否真实（测试通过但答案其实不对）。讲者说数学题她们人工抽查过，大约在 90% 以上（字幕此处为「90s, 7%, 8%」，具体数字听不清）；但单元测试覆盖不全时确实会失效，所以验证器质量很重要。

原文 讲者口述 19:00–27:01
口述 27:01–42:08

简单题多做顺序修改，难题更依赖大模型：推理算力不能完全替代预训练

口述 27:01–29:03：第二篇是 Snell 等人关于「最优地扩展测试时算力，可能比扩大参数更有效」的论文（标题见阅读清单）。扩展推理算力有两条路：并行采样（一题生成多个答案）和顺序修改（先写出初步步骤，再从不同角度反复检查，直到有把握才输出）。这里先假设顺序修改靠我们自己提示；如今的推理模型训练后会自己这样修改。另一条路是改进怎么选答案。

口述 29:03–31:00：选答案可以用结果奖励模型（ORM，对最终答案打分），也可以用过程奖励模型（PRM，对解题的每一步打分）。best-of-n 加验证器最简单：并行生成，用 ORM 选最高分。也可以把奖励模型放进搜索里：比如每一层预算 4 个样本，用 PRM 给每一步打分。

口述 31:00–34:00：设阈值选前两个继续展开，这就是用 PRM 引导的 beam search。PRM 一般也是微调出来的，给定问题和这一步，打一个 0 到 1 之间的分；在目标任务的子集上训练 PRM 对该任务帮助最大，但它基于语言模型，跨任务也有一定泛化。打分单位不是 token 而是「步」，可以定义为有意义的一段或一句。把 ORM 和并行、顺序修改结合起来效果更好，比如做两条修改链得到两个最终答案，再用 PRM 或 ORM 选好的那个。

口述 34:00–36:00：有很多现成的 PRM 可以拿来引导自己任务的搜索，也可以用自己的数据训练 PRM 和 ORM。论文用的是 MATH 数据集（约 12k 训练题、500 道测试题）和 PaLM 模型。为了比较不同扩展方式，论文按每题的 pass@1 把题目分成五档难度，再看哪种方式对难题、易题更好。

口述 36:00–38:02：图中比较了多数投票、ORM、PRM 和精心组合几种方式的准确率随生成预算的变化；怎么混搭顺序修改与并行扩展、让每个准确率下花的算力最少，仍是开放研究。按难度分档看，第 5 档最难、准确率最低，第 1 档最容易；对容易的题，顺序 token 远多于并行的配比准确率最高。

口述 38:02–42:08：讲者认为至今成立的观察是：对容易和中等难度的题，增加推理算力可能比扩大预训练更划算；但对最难的题，预训练更多、更大的模型更好，即使推理预算很大也是如此。她实验室也看到：小的开源模型加上更多推理算力越来越有用，但非常难的题仍是前沿大模型更强。预训练只做一次，推理扩展每次运行都要花；而且不是谁都能预训练大模型，所以这个结论很有意义——预训练仍有必要，更好的模型仍然更强。学生问图中比值为 1 是什么意思，讲者说那是预训练算力与推理算力之比，不是一对一的对应。

口述 42:08–46:00

没有通用答案，组合顺序和并行通常更好

口述 42:08–46:00：第二轮讨论。学生问树搜索算不算两者的混合：讲者说是，没有通用答案，但普遍看法是组合两者比单用好，前面的 beam search 就是例子，还能复用已算的部分。有学生认为越难的题越需要并行地多找可行解，或在思维链里逐步验证、剪掉违规的分支，讲者认为这种直觉合理。核心问题是：把生成的 token 当作提升答案质量的旋钮，怎么分配、怎么引导模型生成。

口述 46:00–63:00

把融合、评审、排序、验证一层层叠起来，用贝叶斯优化搜出架构，开源模型组合也能超过前沿模型

口述 46:00–49:02：第三篇是讲者实验室的 Archon。问题是：怎么混搭各种推理时方法，优化「能力（正确率）对成本」的前沿，不浪费 token。输入包括要优化的目标基准、推理预算、可用的 LLM（可以混用不同模型）和一组推理时技术，再由一个推理时架构搜索优化器（字幕写作「itest」）输出把技术与模型组合起来的架构。第一种操作是生成，即采样，一次 n 个就是 n 个不同回答。

口述 49:02–51:00：融合（fusion）：把问题和 K 个回答都给 LLM，让它综合成一个回答，这属于在并行样本之后做顺序更新。评审（critic）：指出各回答的优缺点。排序（ranker）：在提示里让模型按质量给回答排序。验证器：返回回答的同时说明推理理由。讲者强调这些全是提示出来的，没有为此专门训练模型。

口述 51:00–54:00：某个问答推理基准上的结果（左图，单一模型，样本数 1 到 10）：随机选最差；让模型排序选第一更好；Oracle 选择（假设有完美验证器挑最好的那个）又更好；而融合竟然能超过 Oracle 选择；先选前五个再融合（purple 线）最好，说明先过滤再融合更有效。

口述 53:03–55:01：右图换成不同模型各生成一个回答（10 就是 10 个模型各答一次）。随机结果变差，因为左图用的模型是其中较好的，但各方法的先后关系不变。

口述 55:01–57:00：还有单元测试生成与评估：让模型为代码或数学推理题生成单元测试；更「疯狂」的是不真的运行测试，而是让模型判断一个答案能否通过测试。例子是括号是否平衡：遇到右括号要和最近一个未匹配的左括号对上，不平衡就应输出 no；也可以让模型再生成测试代码。

口述 57:00–60:00：搜出来的架构相当复杂：生成、评审、排序、多个融合器，再继续评审、排序。为缩小搜索空间先做了离线预处理，比如发现「生成–评审–排序–融合」这个顺序很好。目标是在给定推理预算下最大化准确率。编码题上的最优架构是：大量生成、生成单元测试再评估。有趣的是，叠更多层推理时技术（变深）能提高准确率，比如多层融合加最后一个融合层，在很多任务上明显好于最好的模型只用一次、或用 8 次加一层融合——就像深度学习里加层模型会变好。

口述 60:00–62:02：搜索空间加了约束：评审总要在排序器或融合器之前（本地测试发现这样更好），单元测试生成器后面必须跟评估器；用贝叶斯优化来搜，有很多好的开源工具可用。图中显示 Archon 搜索多少种配置后得到最终架构，目标可以是可用模型、推理预算等；Archon 最后只输出一个回答，相当于在优化最终的 pass@1。

口述 61:01–63:00：只用开源模型时也能做得很好；Archon 既可以针对单一任务优化，也可以训练成通用的，通用版在这些任务上也好于前沿模型：在指令遵循、推理、数学和编程题上，pass@1 平均比 GPT-4o（字幕写作 GPT-4.0）或 Claude 3.5 Sonnet 高 14.1%——推理时架构的效果能超出单个模型。最后留了几道思考题，因为超时没有讨论。
