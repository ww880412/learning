L15 · Compaction 与 Prompt Caching：窗口装不下时怎么办，重发整段对话凭什么划算

harness 每一轮都把整段对话重发给模型。这引出今天两个问题：对话装不进窗口时怎么办（第 1 部分，compaction：让模型写一份总结，再从总结重新开始），以及每次都把整段处理一遍、谁来买单（第 2 部分，prompt caching：服务商把已处理过的前缀存起来，下一个请求逐字节匹配上就从缓存读）。两部分最后汇到一处：compaction 也是一次 harness 事先规划好的缓存重置。

讲者备注：今天讲 harness 发给模型的那段对话：装不下时会发生什么，以及是什么让重发它变得负担得起。

讲者备注：从 L07 讲过的开始。每一轮 harness 构造一个请求发给模型，请求 1 装着 harness 写的系统提示，然后是你的消息。整讲的配色固定：琥珀色是 harness，玫瑰色是你，蓝色是模型，绿色是你的电脑，灰色是混合。

模型在请求之间什么都不保留，所以请求 2 就是请求 1 再加上模型的工具调用和你电脑返回的结果；请求 3 是请求 2 再加一对调用和结果。harness 每次都重发整段对话，于是有了今天两个问题：装不下了怎么办？这是第 1 部分。每次都要把它全处理一遍，谁来付钱？这是第 2 部分。

讲者备注：两部分。先是 compaction：对话装不进窗口时 harness 做什么；课间之后是 prompt caching：是什么让每一轮重发整段对话变得负担得起；最后答疑。

第 4–6 页

四种处理满窗口的办法，只有最后一种请模型帮忙

讲者备注：第一部分，compaction。

讲者备注：这是一个 1 million（100 万）token 的窗口，空的。前沿模型现在能读这么多，听起来什么都装得下。每个请求都从系统提示开始，然后是你的任务，比如修一个很慢的上传。

然后是干活：工具调用、结果和回复。模型一个文件接一个文件地读，每个结果都留在对话里，因为 harness 会重发全部。一整天的长时间工作连 100 万 token 也能填满，然后下一个请求就放不下了。早在那之前，L14 已经讲过长对话的代价。

讲者备注：harness 有四种办法处理满窗口。可以报错停下，这是 API 自己的行为：超过窗口的请求被拒绝，会话结束。可以丢掉最早的消息：简单，但最早的那条是你的任务，模型就忘了自己被要求做什么。

可以清掉旧的工具结果：工具输出是编码会话的大头，模型用过之后大多就过时了，所以 harness 把每个旧结果换成一个短占位符。

也可以总结后重新开始：保留系统提示、一份总结和最新一轮。前三种只靠 harness 自己；这一种请模型帮忙，它就叫 compaction。

第 7–9 页

总结是下一个请求对之前工作的全部了解

讲者备注：一步一步看一次 compaction。左边是当前对话：系统提示、你的任务、文件读取、回复、你的下一条消息。harness 把一条总结指令追加到对话末尾，而不是另建一个新请求；它在窗口满之前就这么做，因为这个请求本身也要空间。选择「追加」这一点在第 2 部分还会再起作用。

模型拿到全部内容，写出一份总结，harness 用它开始新对话。

harness 补上其余部分：同样的系统提示、逐字保留的最新几条消息、一条关于之前读过哪些文件的说明，以及你的下一条消息——正是触发这次 compaction 的那条。那条说明告诉模型它之前打开过哪些文件，好让它再读一遍。此后每个请求里都不再有旧对话。

讲者备注：这份总结就是下一个请求对之前工作的全部了解，所以 harness 的总结提示会要求留下任务继续所需的东西。第一，你发过的每条消息，这样像「绝不碰生产配置」这样的规则在 compaction 后仍然有效。

第二，定下了什么，以及要紧的代码：修复放在上传的重试循环里。第三，下一步，取自最新几条消息，让新对话接着做同一个任务、不跑偏。大部分工具输出被丢掉：文件还在磁盘上，模型可以再读。

讲者备注：那之后模型知道什么？compaction 之前，它知道要改的确切那一行；总结必须短，于是把它约成「修复在上传代码里某处」。compaction 之后，模型知道位置但不知道哪一行，只好再读一遍文件。找回一个确切细节要花一次读取，而没人再去读的细节就丢了。

第 10–11 页

要长期有效的规则放进文件，而不是聊天里

讲者备注：那什么能活下来？又是新对话：指令、总结、最近的消息；旁边是你的电脑，有些东西从对话之外回来。指令文件从磁盘重读：harness 把 AGENTS.md 这类文件放进每个请求，不管有没有 compaction，因为它们住在对话之外。

模型能再读的文件：需要确切那一行时，模型请求那个文件，harness 从磁盘读给它。

聊天里打的规则可能活不下来。总结会尽量保留你的消息，但一条必须持续有效的规则应该放进文件。这就是 L10 讲的指令的四个家：AGENTS.md 在每个请求里都会被读，一条聊天消息只活到对话结束。

讲者备注：这应该眼熟。L14 里，subagent 把一份报告交回主对话；compaction 是同一种交接，只是模型交给它自己：较早的对话把一份总结交给较晚的对话。两者都会丢掉确切细节，所以读一份总结，要像读 subagent 的报告那样读。

第 13–15 页

服务商保留已处理的前缀，下一个请求从缓存读

讲者备注：第二部分，prompt caching。

讲者备注：第 1 部分把对话保持在窗口之内，第 2 部分讲账单。又是请求 1：系统提示和你的消息，之后每个请求加一次调用和一个结果。一直到请求 8：每个请求都是上一个再多一点，服务商在吐出一个字之前要把其中每个 token 都过一遍模型。所以系统提示和你的消息在每个请求里都被再处理一遍，到请求 8 已经 8 次。在长会话上，这些重复的工作就是大部分成本。

讲者备注：又是三个请求：请求 1 是系统提示和你的消息，请求 2 和 3 各加一次工具调用和一个结果。解决办法是让服务商保留它的工作：请求 1 写入缓存，服务商把处理过的开头存几分钟。harness 标出缓存到哪里，模型从不知道。

请求 2 一开始就是一字不差的请求 1，所以那一部分从缓存读，而不是重新处理，只有新的结尾要处理。请求 3 同样从缓存读出请求 2 的全部。整个机制就这些。

原文 Part 2: Prompt caching · The cost of resending · What the cache keeps
第 16–17 页

必须逐字节相同的前缀；读缓存不到原价的十分之一

讲者备注：匹配必须是精确的。服务商按顺序读一个请求：tools、系统提示、消息。下一个请求的开头若与之前某个请求逐字节相同，这段确切前缀就从缓存读。tools 里改了一个字节，tools 和它后面的一切都未命中，即使其余部分完全相同。

讲者备注：和原价的普通输入相比，写入缓存贵四分之一，从缓存读只要十分之一或更少。长会话的大部分输入都从缓存读，所以大部分都便宜。

它能活多久：默认 5 分钟，每次读取都会重新计时，这种条目写入贵四分之一。harness 也可以付两倍写入一个能活一小时的条目——当你离开超过 5 分钟时就值得。

原文 How the cache matches · What the cache costs
第 18–19 页

变得最少的放最前，新东西放最后

讲者备注：因为匹配从最前面开始，harness 把变化最少的放在最前：先 tools，再系统提示——每个会话都一样，所以里面不写你的文件夹、你的名字或日期。

然后是 AGENTS.md 这类指令文件，同一个项目内一样；然后是 skills 和日期，同一个会话内一样——日期每天都变，所以放得靠后；然后是每一轮都在增长的对话。Claude Code 就按这些层排它的请求，Anthropic 说整个 harness 都是围绕 prompt caching 搭起来的。

讲者备注：缓存解释了一个你现在在任何 harness 里都能认出的习惯。请求的开头——tools、系统提示和到目前为止的对话——从缓存读，所以新东西放在末尾。一条提醒：磁盘上的文件变了或者模式切换了，harness 在下一条消息里加一条提醒，而不是去改系统提示。

一个新的工具结果：哪怕是模型在会话中途才找到的工具，也作为末尾的一个结果到来，所以开头的工具列表从不改变。一个被加载的 skill：L10 的三层——skill 的名字和描述在每个请求里，它的正文只在模型请求时作为末尾的一个工具结果到来。

原文 Request order · Adding to the end
第 20–21 页

compaction 是 harness 事先规划好的重写：开头不变，只为新对话付钱

讲者备注：那什么会重置缓存？改了一个工具定义：什么都读不到，tools 在最前，那里改一个字节就全部未命中。换一个模型：也什么都读不到，每个模型有自己的缓存，所以会话中途换模型要为整段对话重新付钱。

新开的 subagent 冷启动：它有自己的系统提示和空对话，没有什么能匹配父级的前缀。fork 读父级的缓存，因为它的开头与父级的系统提示、tools 和历史完全一致——这就是 L14 发现 fork 比新开的 subagent 启动更便宜的原因。

讲者备注：compaction 是最后一种重置，也是 harness 事先规划的那种。之前，对话以 tools 和系统提示开头；总结请求就是同一段对话末尾追加总结指令，所以全部从缓存读——这就是「追加」的回报。

下一个请求保留 tools 和系统提示，开始新对话；总结和最近消息是新的，所以写入缓存。tools 和系统提示没变，仍然从缓存读。compaction 是一次 harness 事先规划好的重写：它保持开头不变，只为新对话付钱。

第 22–23 页

缓存奖励只追加的 harness；每改一次过去都要重新付钱

讲者备注：harness 在窗口满之前就压缩，因为总结也需要空间。总结留下决定、丢掉细节，所以必须精确的东西应该放在文件里。

缓存奖励只追加的 harness：稳定的部分放前面，新东西放末尾。每改一次过去都要再付一次：一个改动过的工具、一个不同的模型、一份总结。

讲者备注：Aider 只总结已经完成的轮次。你们要搭的循环跑在一轮之内，所以它的消息从不被总结，并随每个工具轮次增长。每个工具轮次都应该追加：把调用和结果加到消息末尾，永远不要重建已有的部分，缓存才能发挥作用。（这里的「循环」指本周 Lab 05 Building on Codex 的作业，据课程大纲推断，补充）
