讲者备注：定义就这么一句。文件夹里最多三类东西：指令，放在 SKILL.md 里，每个 skill 都有；资源，指令可能让模型去读的文件，比如模板、清单、更长的解释；脚本，当某一步每次都该产出同样结果时 agent 可以运行的代码。

图注是要记住的部分：skill 里的一切都是写给模型读的，没有 API、没有函数签名。skill 的读者是模型，就像 README 的读者是下一个工程师。

讲者备注：这是 elephant skill 现在的真实样子。一个以 skill 命名的文件夹，里面一份必需的 SKILL.md；文件顶部几行 YAML frontmatter，其余是写给模型读的 Markdown 指令。

其余都是可选的，文件夹名是约定：references 放只有 SKILL.md 叫模型去读时才读的材料（这里是设计文档每一节该写什么、各自会怎样写坏）；assets 放 skill 用在产出里、而不是读来当指导的文件（这里是空白设计文档和空白台账）；evals 放十二个请求，六个应该加载这个 skill、六个是不该加载的近似请求，用来测试 description。scripts 会放 agent 运行而非阅读的代码；elephant 没有，因为设计对话里不该有确定性的东西，但另外三个 EGM skill 有。

文件夹放在哪决定谁能用：Claude Code 在 .claude/skills 里找，家目录里放个人的、项目里放共享的；Codex 在 .agents/skills 里找。没有运行时、没有注册表、没有 SDK——会写 README 就会写 skill，这是它传播开的一大原因。

第 8 页

description 决定何时，正文决定怎么做

# Elephant: grow the design before you grow the code

正文的标题依次是：Elephant 的总标题（先长设计，再长代码）；EGM 操作反射（共享前言）；硬规则；工作流，含第 2 步「No Code」规则（访谈）、第 3 步谄媚防御（sycophant defense）、第 5 步逐节构建设计文档——起草每一节前先读 references/design-doc-sections.md 里对应条目；反模式；以及这个 skill 为什么存在。

只列标题，外加把模型引向 references/ 的那一行。

讲者备注：frontmatter 下面就是正文，只是 Markdown 指令。读起来像写给同事的 runbook：整个会话都成立的反射；永不违反的硬规则（比如这次会话不写代码）；带清单的编号工作流；要避免的错误；以及这个 skill 为什么存在——模型知道规则的用意时，遵守得更好。

看第 5 步下面缩进的那行：正文指向 references 里的一个文件，模型到那一步才读那份指南。skill 可以把细节藏在自己内部，就像 description 藏起整个正文。这个想法留到课间之后。

description 决定何时（when），正文决定怎么做（how）。

讲者备注：所以 description 就是触发器。写含糊了，skill 永远不触发，或在错的请求上触发；写好了，用户一说「let's plan this」，agent 就会自己拿起这个方法，没人需要敲斜杠命令。写 skill 的功夫大多在这一段：第三人称、它做什么、何时用、人们真正会说的词。

讲者备注：elephant 的指令还能放在哪？四个地方。系统提示，或 harness 贴进去的项目文件（AGENTS.md、CLAUDE.md），不管相关与否都进每个请求。

工具：L07 讲过工具定义也以 JSON schema 的形式出现在每个请求里，但工具是 harness 执行的动作，「先设计再写代码」不是动作，而是一种工作方式。skill：方法只在任务需要时才随请求一起走。

还有 Hackathon 1 上多数人用的那种：你自己的脑子——每次会话把方法重新敲进对话，每次略有不同，当晚还忘一半。课程设计文档称 skill 为「portable context plus a trigger」，这是要记住的一句。

skill 与工具的区别

原文 · Skill versus tool
原表 2 · 工具与 skill 的对比
ToolSkill
What it isA functionInstructions
Who actsThe harness runs itThe model follows it
In the requestFull schema, alwaysDescription, then body
What comes backA resultA way of working
出处：EECS 498 AASE L10 课件 · 幻灯片第 11 页 · Skill versus tool

工具做事；skill 改变模型决定做什么的方式。

讲者备注：两者容易混，所以并排放。工具是函数，L07 见过：名字、描述、参数的 JSON schema；模型发出调用，harness 运行真实代码——读文件、跑命令；回来的是结果（一条 tool 消息），模型据此推理。

skill 是指令，用的时候什么都不执行；模型读了它，变的是模型在这个任务余下部分的行为——它开始访谈你，而不是写代码。代价也不同：每个工具的完整 schema 都随每个请求走，因为模型得知道参数才能调用；skill 只以 description 出现，直到模型要正文。

两者有两处交汇：一，skill 的指令通常告诉模型用哪些工具、何时用，所以 skill 往往是一套用好工具的方法；二（留给课间）：模型总得以某种方式拿到正文。讲者问：如果什么都不执行，skill 的正文怎么进入对话？给讲者的提示：收一两个猜测，不揭晓，这是课间题的第二问。

出处：EECS 498 AASE L10 课件 · 幻灯片第 15 页 · Rensin's article in three parts

作者 Dave Rensin，Google 杰出工程师（Distinguished Engineer），文章发在 drensin.medium.com。

讲者备注：Rensin 过去几年主导 Google 内部「用好 AI」的推动，文章是他的心得。第一部分「工具不是玩具」：先把模型当审问者用，再当研究员用；在要产出之前先和它约定验收标准；然后带着这两样在一个新会话里跑真正的查询。他的说法是：多数人在外包自己的判断，还管这叫生产力。

第二部分就是今天要讲的模型。第三部分「我们现在都是管理者」：你会像经理管人一样管 agent——定结果、划权限、说清何时上报，然后放心地把目光移开。他建议去上一门新任经理课程，而且不是开玩笑。

读过的人会注意到，第一部分已经是整个想法的缩影：审问、定义完成、再开新会话；第二部分把它放大到一个功能。

Design is the new code（设计就是新的代码）。

讲者备注：这是他的论点。设计文档才是要紧的产物，代码在它下游，越来越多是生成的、越来越不透明。文档对了，代码可以重新生成；文档错了，再好的代码也救不了你。这话大家听过一个版本：L04 是规格驱动开发，Apply 构建有一半分数看规格和设计；EGM 是让设计好到足以承担这份分量的方法。

讲者备注：Elephant 是一个上下文很多的长会话，设计在这里长出来。讲者的版本有四条规则。不写代码——一个函数、一段伪代码都不写，直到设计文档通过课间后会看到的 Goldfish 测试。

先访谈：模型在提出任何东西之前先问你问题，这是 Rensin 的审问者想法。模型先起草、你来反驳，skill 称之为谄媚防御：如果你先提，模型倾向于同意你；如果它必须在听到你的方案之前先拿出自己的，你得到的是真正的第二意见。产出是一份四节的文档。

讲者备注：问题，用三到五句平实的话——说不了这么短，就还没理解它。技术方案，在方块图的层面，尽量少用行话。

Request n+1：system 不变，tools 不变；user、那次调用，然后是 tool：elephant 的 SKILL.md 正文；回答是向用户提一个问题。

讲者备注：这是用 L07 的术语画出的两个请求。Request n 的请求带着索引；用户说要给 taskr 规划一个 priority 参数，模型把它和 elephant 的 description 匹配，回答不是给用户的文本，而是一次工具调用。load_skill 是个代称：Claude Code 里这个工具叫 Skill；没有它的 harness 里，可以简单到对 SKILL.md 路径做一次 read_file。

原文 · Three Goldfish reviewers

A：理解（Comprehension），把它讲回来。

B：批评（Critic），找出缺口。

C：就绪（Readiness），我能照此构建吗？

三者并行运行，它们的报告驱动下一轮修改。

讲者备注：Rensin 描述的是一条 Goldfish；讲者的 skill 同时跑三条，各有分工、各在自己的新上下文里。A 理解：读文档、把系统讲回来，讲错了说明文档不清楚，而不是读者的问题。
