原文 Lecture 07 开场 · Inside the call: messages, streams, and tool calls · Three parts
第 5–10 页 · ENDPOINT.md

请求对象就是程序和模型之间的全部接口——而且没有会话字段

讲者：这一半是按字节经过的顺序读 ENDPOINT.md，也就是学生本周的 build。提示：不在分隔页停，直接进请求对象。

POST {base_url}/chat/completions

上面是第一行：POST {base_url}/chat/completions。请求体是一个 JSON："model": "qwen3.5:9b"；messages 是一个列表，依次是 system、user、assistant、user 四条，每条有 role 和 content；最后 "stream": true。

这就是你的程序和模型之间的全部接口。一次 HTTP POST，一个 JSON 对象。

model 是服务器认得的标识符，原样发送。你在 Aider 配置里敲的 ollama_chat/ 前缀是 Aider 的路由，不是模型名字，你的规格在配置一节也这样写。

messages 就是 Lab01 那个栈编成的列表：系统提示词是第一条；你选的文件（F3）放在某条消息里面——看这个对象，根本没有放文件的字段，没别处可放；历史是此前每一轮完整的对话；你最新的消息在最后。

幻灯片上没有的一点：Authorization: Bearer 只在设置了 api_key 时才发。没有 key 就完全不带这个头，而不是带一个空的，因为 Ollama 会拒绝空头；这个 key 也永远不出现在错误信息、日志或提交里。

讲者停顿：看看这个对象里没有什么——有样东西你们被告知过两次，这里却没有，是什么？提示：在最后一行停住，让全场回答再翻页。

没有 session 字段，没有地方放记忆。没有会话 ID、没有 cookie、没有指向上一轮的句柄。Lab01 说过什么都不会被记住，连续性靠 harness 重发——原因就在这里：这不是谁做的政策决定，而是请求里根本没有放记忆的位置。

模型对过去十轮知道的一切都在这个列表里，因为是你放进去的。这正是 F1 有预算规则的原因：列表只会变长。你的程序裁掉旧轮次或换成摘要时，是在发送前编辑这个列表，另一端既不会察觉也不在乎。讲者提示：这是要停下来的一页。

最小集之外的三个字段

原文 · Three more request fields

temperature：L02 讲的采样步骤，做成了一个旋钮（dial）。

max_tokens：回复长度上限，也是测试的好帮手。

tools：今天的后半部分。

不发 temperature，服务器会自己选，而它选的不是零。

讲者：刚才是最小对象，再加三个字段，之前都没在课上出现过。temperature 就是 L02 的采样步骤加了旋钮：L02 说模型对整个词表算出一个分布再从中采样，这个数在采样前缩放分布——接近零时最可能的 token 几乎每次都赢，调高则尾部更常被选中。

不发它，服务器就用默认值，而默认值不是零。第 7 周的评测 harness 会尽量要 temperature 为零，好让同一任务跑三次的差异来自任务而不是骰子；但即使为零，也不是每个服务器上都完全一致。Stage 1 不要求发它，设计文档要写明你发不发。

max_tokens 给回复设上限，是让测试确定的廉价办法，两页之后讲者就用它故意弄坏一样东西。tools 是今天的后半部分。

「兼容」承诺了什么

原文 · What "compatible" promises

Ollama、llama.cpp、vLLM 以及每个厂商：用的是同一个对象（same object）。

没有人正式批准过（ratified）它，是一家厂商的 API 胜出了。

它在推理、工具、用量这些地方会磨损（frays）。

ENDPOINT.md 划了线：只做文本 chat completions，别的不做。

讲者：用一段话说明这为什么能行。Ollama 接受这个对象，llama.cpp 的服务器、vLLM 和每家商业厂商也都接受。没人批准过——一家厂商的 HTTP API 成了大家照抄的形状，而这个形状现在比那家厂商还值钱。这就是 L01 能说「模型是一行配置」并且是认真的。

它在边缘会磨损，今天每条边都会碰到：模型的推理放在哪，各服务器不同；工具调用是整块到还是碎片到，各服务器不同；流里有没有用量，取决于一个服务器发明、别人照抄的字段。ENDPOINT.md 的线是：只做文本 chat completions，越过这条线，需要的是在服务前加一个代理，而不是改你的代码。

被截断的回复

原文 · A truncated reply 
"message": {
  "role": "assistant",

现场 · max_tokens 8：同一个请求、上限设为 8 个 token。返回的 content 是空字符串，reasoning 只有半句话，finish_reason 是 "length"。

内容为空，但模型并不是什么都没说。

讲者执行第 2 条命令。content 是空字符串，reasoning 字段正好 8 个 token 长——模型不是没话说，而是服务器在它思考到一半时切断了。一个读到 content 为空、就告诉用户「模型没有答案」的程序，读错了这个回复。

再想象截断发生在 400 个 token 而不是 8 个：文本看起来像写完了，甚至可能含有一个看似完整的编辑块，因为结束标记很短，模型很可能已经写到那了。把它应用上的程序，干的事比打印一条错误消息糟糕得多。

ENDPOINT.md 规定截断要产生一个明确的应用错误，这个字段就是你知道的途径；内容过滤、格式错误的事件、HTTP 失败、没结束就断掉的流也一样。讲者提示：第 2 个现场环节，这个很稳定。

你的估算器要对照的数字

原文 · The number your estimator is graded against

回复里的 usage：prompt_tokens 31、completion_tokens 465、total_tokens 496。

/tokens 是预测，这个字段是实数（counted）。

发一次、比一比、校准（calibrate）一下，一个下午的事。

F1 允许估算粗糙，但不允许不校准。

讲者：服务器替你数好了——进 31 个 token、出 465 个。你的 /tokens 显示的是估算，F1 允许它粗糙，固定的「字符/每 token」比例也行，只要是确定的。这个字段是检验估算的基准：发一次请求，把 prompt_tokens 和 /tokens 的预测比一下，调整比例——这就是全部校准，一个下午的活，不是一个项目。

ENDPOINT.md 让你往高估，原因在四页之后。讲者在这个模型上实测（2026-09-22）：空的 user 消息耗 10 个 prompt token，「Hi」11 个，「Explain TCP in detail.」16 个，同一句写两遍 21 个——所以 16 个里 6 个是字，10 个是固定底数，即聊天模板在模型看到任何东西之前，为每条消息加上的角色标记和轮次分隔符。

这个底数是按字符估算的估算器看不到的：它只数字符串，不数脚手架，所以每次请求都会少算，而且误差随历史增长——又一个往高估的理由。讲者把这点留在口袋里而不放上幻灯片，因为总有人会问。

第 17–22 页 · The stream

一句话的回复拆成 516 个事件，没结束就断的流要当作什么都没发生

讲者：分隔页——stream: true，Stage 1 永远是这样。提示：运行手册第 3 条命令在下一页，让它滚动。

现场 · 同一个问题，改成流式：返回的是一行行 data: 事件。第一个 delta 带 role 和一段推理「Thinking」，接着是一个个只有推理碎片的 delta，然后是 content 碎片（如「 server」），再是一个空 delta 带着 "finish_reason":"stop"，最后是 data: [DONE]。

一句话，516 个事件，大多数根本不带文字。

讲者：ENDPOINT.md 规定 Stage 1 永远流式，F1 规定回复随分块到达而打印，所以同一个问题再问一次，开流式（执行第 3 条命令，让它滚）。回来的不是一个 JSON 对象，而是 Server-Sent Events：每个事件一行 data:，事件之间空一行，信封还是那个，只是 message 的位置换成了 delta。

展示计数：五百一十六个事件，就为一句话，大多数带的是一段推理碎片和空 content。你的回复是所有 content delta 由你拼接起来的结果；模型是按顺序写的，但除了结束原因和那个哨兵（sentinel），没有任何东西告诉你顺序是完整的。

讲者提示：第 3 个现场环节，当着学生用 grep -c 计数；滚回顶部看开头的 delta，滚到底部看 [DONE]。幻灯片上的开头 delta 带着 role、空 content 和推理「Thinking」：要说 role 才是要紧的部分，推理碎片只是这个模型的习性；别说它是空的，幻灯片显示它不是。

流失败时的规则

原文 · The failed-stream rule
原表 6 · F1 的失败流规则：每个动词的理由
Your programBecause
Records no assistant turnThe next request would carry a reply it never finished
Treats nothing as an editF5 and F6 rest on the proposal being complete
Says so, stays usableThe user has to be able to retry
出处：EECS 498 AASE L07 课件 · 幻灯片第 21 页 · The failed-stream rule

这是契约里唯一有安全后果的一条。讲者：所以 F1 说——不记录助手轮次，其中任何东西都不当作编辑，告诉用户，保持可用；ENDPOINT.md 称它是契约里唯一有安全后果的条款，下面说每个动词为什么在那。

不记录助手轮次：如果那段没写完的回复进了历史，下一次请求就带着模型从没写完的文字，模型会接着它往下写，之后每一次请求也是。不当作编辑：F5 和 F6 的全部保证是「没有完整展示的完整提议就什么都不写」，而你无法知道它是否完整。保持可用：用户必须能重试。

这是周四讲的 F6.6，从另一面遇上它：周四是用户在批准提示处按 Ctrl-C、什么都没写；这里是网络断了，你的程序欠的是完全一样的东西。

没人报告的截断

原文 · The truncation nobody reports

Ollama 默认只保留 4k 个 token 的上下文（Ollama keeps 4k）。

超过之后：没有错误、没有 length、没有任何消息（no error）。

它丢掉开头（start）部分——你的系统提示词、你的第一个文件。

把它调到 32k；你的 24000 预算放得下，还给回复留了空间。

讲者：再说一个，这个让学生损失过好几周。Ollama 默认保留四千 token 的上下文窗口，除非你另行设置；发一个更长的请求，它不返回 length、不报错、一声不吭，直接丢掉提示词开头、回答剩下的部分——而提示词的开头就是系统提示词和第一个选中的文件。

于是模型不再用你的编辑格式，因为它根本没看到说明；或者它编出一个函数，那函数在它没拿到的那部分文件里。这看起来和一个笨模型一模一样——L02 警告过这个症状，这是它的成因之一，而且是配置错误。
