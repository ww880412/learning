要做的是你自己的结对编程助手：在终端里围绕你选的文件聊天（terminal chat）；模型提议编辑，你批准（you approve）；每个被批准的改动成为一次提交（commit）。

讲者备注：这是整门课建立的转变。手写代码已经少了，逐行阅读也少了——没人能逐行跟上一个模型，这也不是目标；目标是知道代码做了哪些决定、是否做了你想要的。「是模型写的」仍然不能回答评分表的任何一行。所以工程工作转移了：转到计划、提示词，最重要的是理解返回的东西——代码，以及代码周围模型说自己做了什么的那些文字。

你脑子里装着什么

原文 · What you hold in your head

设计以及它为什么这样（design）；你在 build 里进行到哪了。

什么是真正验证过的（verified）；什么只是模型声称的（claimed）。

模型在会话之间一样都不保留。

讲者备注：每次会话，模型都从你给它的文件开始。记得「裁剪策略上周二定的」「第 3 个增量做了一半」「all tests pass 是模型说的、不是 bin/test 说的」，是你。最后两条是危险的一对：验证过的和声称的在聊天窗口里看起来一模一样，把它们分开是你的工作——而且只在你脑子里做，除非你给它找个更好的地方存放。

讲者备注：参照点是项目状态的关键词，而且很密——「F6」用两个字符承载一整个功能，说给桌对面的人或写进提示词都行，harness 也能解析它，不必把整段话贴进去。代码是你自己写的时候，东西的名字住在代码里，你可以去看；当模型根据你的计划和提示词写代码时，名字必须住在模型、评分者和你都能指到的地方，否则每一方都在解读一句话。在上下文预算之下，这种压缩不是整洁问题，而是让对话装得下。

会话里的决定编号

原文 · Decision codes in a session

示例（讲者准备这一讲时的会话）：模型在写幻灯片前列出决定——D1 现场演示用一个仓库里的 Claude Code；D2 审批层移出这一讲；D3 READ 和 RUN 用自造的标记，不用 F5 的；D4 工具调用的推导用幻灯片而不是现场写代码；D5 课间讨论改成讨论题；后面还有 D6 到 D18。

讲者备注：这是照着用 Claude Code 准备这一讲的过程做的。会话事先约定：模型一旦给出三个以上的决定、选项或发现，每个都配一个短编号——D 是决定、O 是选项、Q 是问题，真实的表一直排到 D18。要指出模型本身什么都没变，只是约定文件里一行字让它给东西编号；回报在下一页。

按编号回答

原文 · Answering by code

你：「D1 yes. D3 yes. D4 no, do READ live. D5 yes.」

模型：D1、D3、D5 保留；D4 改为 READ 现场做、RUN 仍放幻灯片；D2 还没回答，要不要移出？

你：「D2 yes.」十八个决定里的五个，两行搞定。

讲者备注：没有编号，第一句回复会是一段话——「我同意演示的想法和标记，但读文件那部分我更想现场做……」——模型得猜每个分句针对哪个提议。有了编号，每个分句只落在一个决定上，模型的回答也能用同样的方式核对；它甚至发现了 D2 没被回答。这就是小尺度上的合作关系：模型用名字呈现，你用名字回答，中间什么都不会丢。

项目包留给你起的名字

原文 · Names the packet leaves to you

SPEC 给 7 个功能（features）起了名字。

你给自己的验收标准（criteria）起名字。

你的每个名字都追溯（traces）到一个功能。

评分表原话：「复述 SPEC.md 第 4 节不得分。」

讲者备注：这就是项目包不那么具体的原因。SPEC.md 停在功能层面；token 估算器、裁剪策略、分隔符、自己的提交怎么标记、每条错误信息说什么——这些都是决定，DESIGN-GUIDE 第 1 节要求每个都写成一条有自己稳定 ID 的验收标准，并映射到它服务的功能；评分表把这种映射叫可追溯（traceable），给 10 分。格式由学生定，像用 F6-3 表示「过期预览被拒绝」就行；要紧的是它短、永不改义，并出现在设计、增量 spec、测试名和提交里。

人对模型：按名字下指令

原文 · Prompting by name

By paraphrase（转述）：「把审批那块弄得更安全点」。

By name（按名字）：specs/03，只做 task 2；交付 F6-3；让 test_stale_preview_refused 通过；只改 preview.py。

讲者备注：左边交给模型一句要解读的话，它会解读，并挑一个它自己理解的「更安全」。右边交给它一个增量、一个任务边界、一条标准、一个判定是否完成的测试、以及它可以动的文件——每一个都是模型能在上下文文件里解析的名字，也都是学生事后能检查的东西。转述需求的提示词会偏离需求，而模型察觉不到；ID 不会漂移。

模型对人：要它用你的名字回答

原文 · Asking for answers in your names

你在评审前问：这次改动交付了哪些标准？你跑了什么？哪些没验证？

模型按格式报告：Delivers F6-3；Touched assistant/preview.py；Ran nothing；Unverified：F6-3 在真实目标仓库上的表现。

讲者备注：名字两个方向都管用。理解模型输出的大部分工作，是把它「做了什么」和它「说自己做了什么」分开；要它用你的术语报告，这种区分就成了一张清单，而不是一次阅读理解。「Ran: nothing」就是你要找的那一行——不问的话，它会是一段说「这个改动正确处理了过期预览」的话。然后去核对：名字让声称变得可检查，但不会让它们变成真的。

一行说清项目状态

原文 · Project state in one line

例：specs/03 · F6-3 done · F6-4 red: test_write_failure_restores

这一行可以用作：发给课程组或邻座（neighbor）的一条消息；一个新会话（session）的第一行；一条提交（commit）信息。

讲者备注：这一行完整说明了项目在哪，而且没有一处是转述。office hours 的助教知道该打开什么；新的 Aider 或 Claude Code 会话知道该加载什么；提交历史读起来是一份决定记录。这也回答了「你脑子里装着什么」：用这些术语写下来，它就不再只住在你脑子里。

名字怎么失效

原文 · How names fail

转述（paraphrase）替代了 ID：提示词写「那条裁剪规则」，模型就自己挑一条。

模型编造（invents）ID：模型很乐意引用根本不存在的 F6-7。只用能解析到文件里某一行的名字。

被点名的文件不在上下文里（not in context）：名字只和它解析到的东西一样好；SYSTEM.md 没加载，「section 6」就是猜。检查会话能看到什么。

名字中途改义（meaning）：做到一半给标准重新编号，会弄坏所有引用过它们的测试名和提交。加新 ID，不复用旧 ID。

现场演示：仓库里的 Claude Code

原文 · Claude Code in a repository

演示三步：按参照点（reference）点名任务；要它用这些名字（names）报告；逐条核对（Check）声称。

原文 Reference points
第 24–32 页 · From edit blocks to tool calls

你的程序已经有一条命令，再加两条，就看出了工具调用的形状

程序已有的唯一命令（SPEC.md F5）：模型针对 greet.py 输出一个 SEARCH/REPLACE 编辑块——SEARCH 段是原文 print("Hello")，REPLACE 段是 print("Hi")。

这是模型输出的文字；你的代码解析它，在你说 yes 之后执行。

讲者备注：反过来看它——模型写文字，程序找到一个认得的标记，取出参数，征得同意后在现实世界里用它们做事。这就是一条命令，学生的程序恰好有一条；这一讲剩下的问题是：加第二条会怎样。

模型需要一个文件时

原文 · When the model needs a file

你问 greet() 为什么打印两次；模型说没有调用它的 main.py 看不出来；你敲 /add main.py，再说「再看一下」。

模型知道自己需要什么，只有你能去拿。

讲者备注：这在 Aider 里经常发生，在学生的程序里也会。模型看到一个文件、推理、说出下一步要什么；Aider 不能自己读文件，它可以提议加一个，但仍要你说 yes 并重发。学生的 Stage 1 程序更严格：只有 /add 能把文件放到模型面前。所以这段对话里人没有做任何思考——模型说出了文件名，人只是把它敲回去。

为什么不让它读

原文 · Why not let it read

理由三条：读不改变磁盘（disk）上的任何东西；你只是在传话（relaying）；它已经说得出要哪个文件（names the file）。

所以给它一个开口要的办法。

讲者备注：先认真对待反对意见——我们故意让用户选文件，是为了让上下文小、让用户掌控，这些理由是真的。但读是最安全的动作：磁盘不变，没有什么要撤销。如果模型已经能说出文件名，让人把名字抄进 /add 只是多一步，没有多一点判断。所以让它开口要，就像它已经在开口要一次编辑那样。

READ 命令

原文 · A READ command

模型先说一句「改之前我得看看测试」，然后输出一个 READ 块，里面是 tests/test_cli.py，以 END 结束。

你的代码读这个文件，把内容送回去。

讲者备注：同样的思路，换个标记——模型要文件，harness 读出来放进下一条消息。和 /add 比：/add 是用户在选，READ 是模型在选，因为它刚才看到了什么。这不在 Stage 1 的 spec 里，这里的标记是为这一讲自造的；要点是需要的东西少得惊人。

RUN 命令

原文 · A RUN command

模型说「先跑一下测试集」，输出一个 RUN 块，里面是 bin/test。

你的代码运行它，把输出送回去。

讲者备注：再来一次——模型要一条命令，harness 运行并返回它打印的东西。要点出：这是第一条改变机器而不只是改文件的命令，git 撤销不了它，最后会回到这一点。

三条命令的分发器

原文 · A dispatcher for three commands 
for block in parse_blocks(reply):
    if block.kind == "EDIT":

上面摘的是分发器的开头两行。完整代码：对 parse_blocks(reply) 解析出的每个块，EDIT 走 propose_edit(path, search, replace)，READ 走 read_file(path)，RUN 走 run_command(command)，每个分支最后都把 result 作为一条 user 消息追加进 messages。讲者备注：逐行讲——一个解析器，每条命令一个分支，每个分支以同样方式结束：结果回到对话里。

问全场第四条命令会是什么：搜索、列目录、抓取 URL——每一个都是又一个 elif。让他们自己注意到所有分支长得一样。

工具调用长什么样

原文 · The shape of a tool call 
{"tool_calls": [

上面是 JSON 的第一行；后面列出同样三条调用：read_file（path 为 tests/test_cli.py）、run_command（command 为 bin/test）、edit_file（path、search、replace）。同样三条命令，不用自定义格式就能解析。

讲者备注：同一张表写成 JSON。格式化的活由端点做，harness 拿到的是一个可以遍历的列表，而不是要扫描标记的文本。别的都没变：分发器还是那个按名字分支的 if/elif；而一旦命令只是表里的名字，加一条就是加一行，所以工具调用能扩展到函数能做的任何事。

模型从不执行任何东西，它只是请求。讲者说这是这一部分要带走的句子：模型输出文字，每一次读、每一条命令、每一次写都由学生写的代码执行，而那段代码可以拒绝。

一个 while 循环替掉人，就得到 agent

加了 READ 和 RUN 但别的不变时，一次会话是这样：你问 bin/test 为什么失败；模型要 READ 测试文件；你贴内容说「继续」；模型要 RUN bin/test；你贴输出说「继续」；模型给出 SEARCH/REPLACE 改 greet.py。

每一句「继续」，都是你在充当循环。

讲者备注：模型请求，harness 执行，然后得有个人把结果送回去、说继续。那个人没做任何思考，他是一个带键盘的循环——所以把他自动化。

自己挑下一步的循环

原文 · The loop that picks its step 
while True:
    reply = model.call(messages, tools=TOOLS)

上面是循环的开头两行。之后：如果回复里没有 tool_calls，就返回文本（模型做完了）；否则对每个调用执行 execute(call)（注释写着「你的代码，你的规则」），把结果追加进 messages，再转一圈。

讲者备注：六行，「继续」就没了。里面没有一处说读哪个文件、下一步是什么、何时停——三者都由模型根据用户只敲过一次的请求提供。这就是一个 agent：四页前的分发器，把人换成了 while True。

循环前后变了什么

原文 · Before and after the loop

模型仍然只写文字（text）。

每个动作（action）仍由你的代码执行。

模型现在挑选下一步（picks）。

只有最后一行变了。讲者备注：循环看起来像交出控制权，其实窄得多——模型仍然只产出文字，每次读、跑、改仍是学生写的代码，那段代码可以拒绝；唯一移动的是「下一步由谁决定」：在 Stage 1 程序里是人，在循环里是模型。

循环还缺什么

原文 · What the loop still needs

迭代次数和 token 的上限（cap）。

重复调用的检测器（detector）。

循环中途可以干净地打断（interrupt）。

run_command 之前要有批准（Approval）。

撤销能覆盖文件，覆盖不了 shell。

讲者备注：一个跑到模型说完成为止的循环，有时永远不会完成——同样的调用、同样的参数，一直重复；或者它认为自己完成了其实没有。所以停止条件要变成代码，而不是用户按的一个键。RUN 是学生的安全网盖不住的命令：/undo 是 git 操作，git 撤销不了 rm -rf、装包、或仓库外的任何东西。Stage 1 程序在写文件前已经会问，agent 在跑命令前也必须问。这是 Analyze 的内容，今天到此为止。
