第 4–9 页 · IDKs

同一个任务，含糊的提示词让模型猜每个细节，IDK 写法什么都不用猜

讲者备注：IDK 是 Information Dense Keywords 的缩写，要大声说一次——学生没见过这个词，而它马上会出现在每一页上。

含糊的写法

原文 · Vague

含糊版：「再加一种输出数据的方式」。结果是模型要猜每一个细节。

IDK 写法

原文 · IDK-rich

IDK 版：CREATE output_format.py with format_as_html(...) -> str；UPDATE main.py: ADD html to --output-format choices。没有留下要猜的东西，通常一次就对。

讲者备注：同一个代码库、同一份上下文、同一个任务的两种提示词。先读含糊的那个，列出模型要猜什么——可能输出文本文件而不是 HTML、可能不改 CLI、可能在该写函数的地方写一个 print()，任何一个猜测都可能错。再看右边什么都不用猜的那个。要讲透的一句：这就是「换着词反复重跑的提示词」和「第一次就命中的提示词」之间的差别。

动作词汇：四对八个动词

原文 · The vocabulary

CREATE · ADD：CREATE 生成原本不存在的东西，ADD 往已有的东西里追加。

UPDATE · REPLACE：UPDATE 原地修改，REPLACE 整个换掉实现。

DELETE · REMOVE：DELETE 删掉整个东西，REMOVE 只删一行或一个参数。

MOVE · MIRROR：MOVE 把代码挪位置，MIRROR 把一个模式照搬到新文件。

成对才是重点：ADD ≠ CREATE。备注：四对八个动词，读成对的，不逐个下定义。CREATE 和 ADD 是最要紧的一对（所以幻灯片上它是琥珀色卡片）：ADD 追加到已存在的东西上，CREATE 新生成；选错一个，模型就做错事。

写法模板：[ACTION] [LOCATION]: [DETAIL]——动作、位置、细节。备注三个词：可重复、紧凑、可预测。

模板用起来

原文 · Pattern in practice

三个例子：CREATE main.py，内含 analyze_transcript(filepath: str) -> TranscriptAnalysis；UPDATE output_format.py: ADD format_as_yaml()，放在 format_as_json() 之后；DELETE main.py: REMOVE 没再用到的 print_debug() 函数。

讲者备注：把三个例子当指令读，而不是当幻灯片上的文字。重点是成本——这种写法比写一段话更短而不是更长，而且通常一次命中，省掉三轮来回。

为什么 IDK 管用：回到 L02

原文 · Narrow the sampling distribution

含糊的提示词 → 分布宽 → 模型挑训练数据里的先验（training-prior）。

精确的提示词 → 分布窄 → 模型挑你说的那个（narrow）。

IDK 管用靠的是机制，不是英语流利度（not English fluency）。

备注：这页呼应 L02，防止 IDK 听起来像一种文风偏好。自回归采样下，含糊的提示词让分布很宽，模型就挑训练数据里最常见的补全；精确的提示词把分布收窄，模型挑的是符合你约束的那个。最后一条要直说：IDK 起作用是因为机制，不是因为模型更懂英语。

第 10–11 页 · Prompt Levels

中层是甜区，而甜区跟着模型移动

讲者备注：分隔页，说出 high、mid、low 就往下翻。

在哪一层下指令

原文 · Where to operate

High：「Make it better.」自然，但有风险。

Mid · 甜区（sweet spot）：「UPDATE chart.py: word_count_bar_chart()」，再加上效果：前四分之一标绿（top quartile green）、降序排列。点名文件和函数，说清要的效果。

Low：「Line 47, replace X with Y.」啰嗦，人变成了打字员（typist）。

甜区随模型移动：前沿模型容忍更高的层级，4B 需要更多细节。备注：甜区那格用琥珀色，是这页的重点；图注就是校准点——不给学生一个固定层级，而是让他们养成习惯，留意今天手上的模型需要哪一层。

第 12–15 页 · Plan = Prompt

瓶颈已经从「AI 懂不懂我」移到「我能不能说清楚」

讲者备注：分隔页，点名就翻，论证在下一页，不要在这里开讲。

瓶颈移动了

原文 · The bottleneck has shifted

2024：AI 能不能理解我想要什么？

2026：我能不能说清楚我想要什么（can I specify）？

输出质量的上限是计划（plan）的质量。

AI 是执行者（executor），你是架构师（architect）。

规格含糊时，人类承包商会提问；LLM 只会猜。

讲者备注：整个论证分五次点击——2024 年问的是 AI 能不能理解你，2026 年问的是你能不能说清自己要什么。第四条是主张：AI 是执行者，你是架构师，做计划才是工程工作。第五条是给它定价的不对称：人类承包商拿到含糊的规格会问澄清问题，LLM 不会，它直接猜——所以含糊在这里的代价比和人合作时更高，写一份精确的 spec 不是额外工作，它就是工作本身。下一页的结论句留到下一页说。

The spec IS the prompt. spec 不是你在写提示词之前先产出的一份文档，spec 就是那条指令。备注：说完就停，让这句话停留一会儿。

什么时候写 spec

原文 · When to use a spec

写（Yes）：协调改动 3 个以上文件、步骤相互依赖、需要可复现、从零搭建（from scratch）、要存档。

不写（No）：单个 bug 修复、一个函数的重构、「顺手也把 X 改了」这类附带改动。

判断规则：如果你会给人类承包商写一份设计文档，就写 spec。备注：这页用了两种语义色——翠绿表示适用、玫红表示不适用，是全讲唯一值得用色的一页；图注就是规则，说完让学生在课间去用。

第 16–18 页 · taskr

挑一个改动，写成 ACTION LOCATION: DETAIL，再找它能命中的最高层级

taskr 是学生一直在用的任务管理器：task.py 是记录，store.py 是磁盘上的 JSON，cli.py 是命令；目前只能 add 和 list。

taskr done 3——把任务标为完成。

taskr rm 3——删除一个任务。

taskr list --tag work——按标签筛选。

taskr add "..." --due fri——加截止日期，并在列表里显示。

taskr list --json——机器可读的输出。

挑一个，或者自带一个；不管哪种，都要点名文件和函数。

讲者备注：给五个选项是因为「想一个改动」是冷启动，而课间只有五分钟，不能让人花两分钟选题。五个选项故意大小不一，这正是校准点：done 要动全部三个文件，因为任务还没有 done 字段，高层级提示词在这里会失效；list --json 只是一个函数，而且 to_dict() 已经存在，所以更高的层级也能成功。需要时直说：「我能写多高」取决于这次改动有多少已经躺在代码库里。

Chat break · 5 min：拿一个你想对 taskr 做的改动，写成 ACTION LOCATION: DETAIL，再找出仍能一次命中的最高层级。

讲者备注：0:35 是固定休息点，完整题目在 overview.md 的 chat_break 字段。特意选 taskr：做了两周 aider-practice，每个人都熟悉 cli.py、store.py、task.py，也已经拿模型在它们上面校准过，没人会卡在陌生代码上——五分钟的课间消化不了这个。推学生去找仍然有效的最高层级，而不是最保险的；0:39 时值得公开追问「是什么让你的线移动了」，答案几乎总是模型。今晚就能在 Aider 里跑，这正是用 taskr 而不是虚构例子的原因。

第 19–23 页 · Spec Anatomy

一个 Markdown 文件，五段：两层目标、实现说明、首尾上下文、有序任务

讲者备注：分隔页，五个部分，翻页。

spec 文档的结构

原文 · Spec document

High-Level Objective：概括地说「做什么」和「为什么」。

Mid-Level Objectives：3–5 个可衡量的结果。

Implementation Notes：依赖、规范、约束。

Context：开始时和结束时的文件。

Ordered Low-Level Tasks：用 IDK 写、按依赖排序的任务。

讲者备注：这是地图，一次点一节，点名就走，后面三页展开。值得大声说：这是一个 Markdown 文件，不是工具也不是表单，今天用任何编辑器都能写。

第 1–3 节：目标与说明

原文 · Objectives and notes

High-level：一句话讲为什么。例：「给文字稿分析命令行工具加上词频可视化和结构化文件输出」。

Mid-level：三到五个结果，每个都能独立验证。例：图表函数、输出格式化函数、两个新的 CLI 参数。

Notes：用 matplotlib（已经是依赖）；遵循项目里的既有模式；每个新函数写简短注释。

目标说「做完长什么样」，说明写「模型不许猜的东西」。备注：Notes 是放工程判断的地方——任何你会在 code review 里纠正的东西，提前写在这里，省掉一轮评审。

第 4 节：上下文（最常被跳过的一节）

原文 · Context: beginning + ending

Beginning context：src/main.py；src/data_types.py (read-only)；pyproject.toml (read-only)。

Ending context：src/main.py (updated)；src/chart.py (new file)；src/output_format.py (new file)。

作用：消除歧义，模型确切知道范围（in scope）是什么。

讲者备注：这是最常被省略、也最重要的一节。开始上下文是模型可以读和改的文件，结束上下文是完成后应该存在的文件；新文件标 (new file)，不许动的标 (read-only)。这一节阻止模型闯进你从没打算让它打开的文件——这就是它存在的理由。

第 5 节：有序任务会叠加

原文 · Compounding sequence

Task 1：CREATE output_format.py，含 format_as_text/json/md/yaml。

Task 2：CREATE chart.py，含 create_bar/pie/line_chart，颜色规则 top green、bottom red。

Task 3：UPDATE main.py: ADD --chart, --output-format，并调用新函数（call new fns）。

Task 3 能引用 Task 1 的产出，因为 Task 1 先跑。讲者备注：按顺序读三个任务再读图注——Task 3 可以引用 format_as_json()，是因为 Task 1 已经跑过；顺序承载了依赖，模型就不用自己推断。这一点只在这页讲，没有单独一页。收尾类比学生已有的习惯：先写类型，再写用它们的函数，最后写调用点。

第 24–26 页 · Architect Mode

一个角色出计划、一个角色改代码，计划停下来等你读

讲者备注过渡：五个部分讲完了，现在看一份五部分齐全的 spec 在笔记本上的模型里从头跑到尾；常见错误放在演示之后讲，这里不预告。

Aider 的 Architect Mode

原文 · Architect Mode in Aider 
aider --architect \
      --model ollama_chat/qwen3.5:9b \

上面摘的是幻灯片启动命令的前两行（第三行是 --editor-model，完整命令见课件）：--architect 打开 Architect Mode，--model 和 --editor-model 分别指定两个角色用的模型，这里都是 qwen3.5:9b。

Architect：用文字起草计划。

Editor：把计划变成编辑。

auto-accept-architect: false：计划会停下来，读它。

两个位置用同一个模型。演示的配置文件已把三项都设好，所以屏幕上只会看到 aider src/main.py src/arg_parse.py。

讲者备注：在学生形成误解之前纠正——是两个角色，不是两个模型。两个位置用同一个模型没问题，在笔记本上通常正是你想要的；小模型做一件事明显比同时做两件好，这就是全部收益。9B 当 architect、4B 当 editor 值得试一次，但不是必需。

备注要讲透第三条：aider-practice 第 6 节故意把它设为 false，计划停下来等你。此时磁盘上还什么都没有，这是整个流程里发现「模型误解了你」最便宜的地方。顺带提一句：计划、执行、检查是一个循环，学生第 5 周会写一个。

现场演示：看它跑

原文 · Watch it run

① 屏幕上打开 spec.md，逐一过五个部分。

② aider src/main.py src/arg_parse.py——Architect Mode，不带参数（no flags）。

③ 粘贴 spec，architect 用文字写出计划。

④ 把计划（plan）念出来，然后按 y。此时磁盘上还什么都没有。

⑤ 四个文件：output_format.py、chart.py 新建；arg_parse.py、main.py 更新。

⑥ 运行 uv run main transcript.txt --chart bar --output-format json。

讲者备注：六次点击，第 4 步是关键节拍，不能删。启动任何东西之前先展示 spec、过一遍五部分，否则全场只是看输出滚动、不知道要求了什么。把 Aider 的横幅和另一块屏幕上的 spec 对照着读：两个文件可编辑、五个只读，这正是学生想跳过的 Context 一节；Aider 会照着执行 (read-only)，它不是写给自己看的备忘。

第 4 步时磁盘上什么都没有：如果它误解了你，代价是一次按键；改完之后再发现，代价是一次 /undo 加四分钟模型时间。如果 Aider 问「Add file to the chat?」，回答 S——默认是 Yes，而 Yes 会重跑 architect、计划就丢了。卡住就切到录屏，不要当着全场调 Python；完整流程见 assets/demo-runbook.md。

评分者看到什么

原文 · What graders see

Vague MLOs：中层目标含糊，「make it better」混了进来。

Missing context section：没写上下文一节，模型去动了不该动的文件。
