AI Coding 深水区 · 主线 3 分数不可信，问题在题集
重平台：107 天、十七万行留下两个分数，没有变成任何一次改动
小实验：16 次跑数、一天跑完改掉了一个至今在用的检索策略
小实验的结论不再让 agent 先读路由文档再跳转，改成直接 grep 知识库
效果（原文数字）寻路步数从 12 步降到 2 步
这条主线讲什么？

差别不在工程量，在判据能不能执行

判据（凭什么说这次做得对）能执行，结论才能变成一次提交。

作者的结论：评测的核心工作是构建题集，不是搭平台。

第三部分（一）前半
病因一：判据不能执行

主指标落到了一个几乎不一致的裁判上

先用参考实现逐行比对：agent 换一种合理架构，就被判「重大偏离」；改成 checklist 后，主指标落在 LLM 的语义判断上。

Kappa 0.10 到 0.21 在统计学上叫「几乎不存在一致性」。

同一个代码库里早就写着答案：说明文档解释过为什么不给需求和架构文档打分——「LLM 打分误差大于信号」。作者说这个判断对代码同样成立，只是当时没人想到。

病因二到四

平台越重，越追不上被评的 agent

前三个病因是技术性的，第四个不是：agent 的迭代速度是这个领域最快的变量。

平台越重，想往里改一个方案就越难。

方案三月底就成型：pass@k 与 pass^k、能力评测和回归评测两套题库、编辑振荡检测、越界修改检测、文件命中率；四天后有了第一笔代码。到六月审计时 pass@k 还挂在「待改进」，重复跑数一次没跑成——光维持流水线就占满了手。

作者把它和前言删 spec 联系起来：值钱的是想清楚，不是承载它的载体。

第三部分（一）「第二」至末段
V1 为什么卡死？

召回率跌到 40%，病根在评分器

改 skill 改不动，就该怀疑分数本身。

每模块只挖 5 条，召回率按 20% 一跳；之前「单点回归 → 定向改 skill」一半是在追噪声。

V1 两条轨道：闸门漏斗（照 Meta TestGen-LLM：lint 干净、能跑、连跑三次稳定、覆盖率达标）；挖空回填（召回率就是分数）。

第一天立下的纪律：考卷和答案独立存仓（考卷不能和课本放一起）；插件、业务代码、测试框架版本和模型全部锁死在一个配置文件；主指标全部确定性判分。

同一批跑数里一个模块跌 40 个百分点，另一个涨 20 个。作者：错误的评测信号比没有更危险。

第三部分（二）
有顶会论文支撑的三个方法全站得住
唯一自研的挖空回填恰恰塌掉
构造效度研究模糊测试工具杀死了 100% 的人工注入 bug，却没发现任何一个真实 bug
挖空回填的两个毛病考「猜我删了什么」是合成任务；召回率能靠全量上报刷满，没有惩罚
调研查出了什么？

唯一没有业界对标的方法，恰好塌了

五十多篇论文和基准过了一遍：SWE-Bench、Meta TestGen-LLM、TestGenEval、SWT-Bench。

V2 的主张：判据必须是执行结果，不能是合成清单。

不再问「你找没找到我藏的东西」，改问「你写的测试实际能发现多少 bug」。

Anthropic 的 Demystifying evals for AI agents 把判分器分成基于代码、基于模型、人工三类，指出基于代码的客观、可复现、易调试；作者说这和他们「确定性判分」的纪律是同一个结论。

第三部分（三）
V2 用什么当主指标？

覆盖率能刷，杀变异体必须有真断言

变异体是故意埋进业务代码的单点 bug；测试在变异后的代码上失败，算杀死。

五道闸门：有产出 → lint 干净 → 能跑 → 连跑三次稳定 → 杀死多少变异体；最后一道才是真正的区分闸。

算子例子：比较符翻转、and/or 互换、删掉 or 0 这类兜底、把状态写入整句注释掉。后四种直接取自他们的代码评审 checklist——项目真实 bug 的分类学。

前四道闸门沿用 Meta TestGen-LLM 的范式。

第三部分（四）前半
动手：一份 AI 写的测试怎么过五道闸门？

测试全绿还不够，要看它杀死了多少变异体

V2 选题三层 + 硬门槛
1场景定业务代表性：发奖、任务、活动、成就、排行榜、聊天
2原型定失效模式覆盖：校验闸门、资源结算、时间窗口、状态机、兼容兜底、遍历聚合
3四轴定难度配平：分支复杂度、依赖构造成本、副作用、函数可见性
✓硬门槛函数体 15~80 行；分支密度不低于 3；依赖可 mock；可变异点不少于 6 个
×不入题并发和性能——单测考不了
变异体埋在哪？

选什么函数，就是在考什么能力

埋什么、埋在哪，才是整套评测真正费工夫的地方。

V1 按「长相」选函数，偏科纯计算函数，成绩虚高。

V1 的三个后果：偏科纯计算函数（LLM 最擅长的题型）；现成用例全是 AI 生成的，「对标人写测试」不成立；没考虑代码活跃度，一个函数被重构，挂在它上面的 12 个变异体一次团灭。

原文说硬门槛共六道，每条都写明教训来源；原文列出的是本卡这几条，外加「并发和性能不入题」。

第三部分（四）后半
出题链上人和机器各站在哪？

机器取素材，人复核事实、定政策

检索交给 agent：叫 check_ 的可能是纯转发，叫 update_ 的反而是真校验，规则匹配不出来。

agent 报「文件近一年改了 48 次」，落到候选函数上其实一年不超过 1 次：它交付的事实常常失真。

「什么算真 bug」只有人能定。等价变异（改了代码但行为不变的伪 bug）的两条政策：日志差异不算可观测；可杀性以自然构造为准。作者说这两条是纯粹的价值判断，机器只能在拍板之后照着执行。

同一道题答三遍取平均。

验证者自己也会错
1LLM 初审and/or 翻转后短路保护失效、运行时报错其实可观测——判错三个；多分支条件只分析一支

✓终裁184 个变异体：172 个可杀入题，12 个等价剔除；以人工复核那层为准
三级验证为什么不能倒过来？

LLM 审查省机时，执行验证定生死

顺序：sonnet 初审剔掉明显等价的 → 参照测试执行验证定生死 → 人工只复核两边不一致的。

每一条判定都带 LLM 初评和人工复核两层留痕。

开考前用 deepseek-v4-pro 把 16 道题各跑一遍校准区分度：击杀率跨度 12% 到 100%，宏平均 61%——题不太难也不太简单，才敢开考。

第三部分（五）后半
数据推翻了什么？

精心设计的原型分类，预测不了成绩

真正决定分数的，是杀死它需不需要构造缺省值、边界值、状态型输入。

作者认为：一套自认为合理的分类学被自己的数据推翻，是评测最该产出的东西。

跑数纪律：16 题 × 3 遍 = 48 次跑数、约 19 小时机时；只看均值；参照 Anthropic 约 6 个百分点的基础设施噪声，差距小于 3 个百分点不下方向性结论，3 到 6 标「可能显著」，超过 6 才拿来改 skill。

五类通病：不测缺省兜底（最大一簇）、不测边界相等值、只断言返回值不查状态写入、不踩非法入参、不枚举模式常量。作者坦言这些方向出题时就想到了，数据的作用是排轻重。

用考题练考题：照存活变异体改 skill 再用同一批题跑，提升一定被高估；要么只改不含函数名的通用规则并披露，要么留出集。

统计 agent 有没有自己跑测试，只认会话记录里的工具调用，不认文字自述。他们自己的命令配置声明剔除了 Task 工具，实际工具列表里它还在。

取舍：业务团队要不要做评测？

题集是本体，但保值不等于现在就该投

跑数、判分、报告是一堆脚本；凡是能脚本化的环节，都不值得当成工程去建设。

设计评测前先想清楚目的：目的决定要回答什么问题，也决定哪些可以不答。

例：评审指出缺少裸模型基线。目的是向别人证明插件价值，缺基线是硬伤；目的是优化 agent，多跑一个基线没有任何输入。

作者引用姚顺雨《The Second Half》：AI 下半场重心从「解决问题」转向「定义问题」。作者的说法：出题就是定义问题。

作者的话（他说可能得罪人）：不做评测一样能优化 agent，评测的成本业务团队很难扛。
