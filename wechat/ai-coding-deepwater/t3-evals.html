开头

测试 agent 能干活了，下一个问题是：它写的测试能不能抓错，能不能量出来

经过前两部分，AI 这一侧算是立住了：测试 agent 可以干活，编排的问题也追到了 runtime。这一部分回答下一个问题：它写的测试到底能不能查出错，这件事能不能量化。

作者说，评测人人都说该做，讲怎么做的少，算过账的更少。接着摆出两次推导：一次撞墙，一次走通。两次投入差了两三个数量级，教训却落在同一处。

（一）先说撞墙的那次

十七万行的评测平台，只留下两个没用上的分数

作者先肯定：要做评测这个判断本身没错。当时 agent 能力在涨，涨多少、弱在哪全凭感觉；不能度量就无从迭代，团队都这么认为，作者自己也投了赞成票。错的是做成了什么样子。

  • 规模：三月底到七月中共 107 天，评测目录增加了十七万行，其中三万多行是题集的参考实现。
  • 建成的东西：一条六段流水线，第一段搭隔离环境，最后一段上传 trace；分四层加权打分；网页平台前端 React、后端 FastAPI，还做了登录鉴权；为了看 trace，自己架了六个容器，即 Langfuse 加它依赖的 PostgreSQL、ClickHouse、MinIO、Redis；跑完自动推送企业微信，总分不到 90 就触发七类根因归因。
  • 题集：25 道真实需求。每题的「答案」是人写的百分制评分表，标准用自然语言写成，例如某个请求从同步返回改为异步过滤后返回，做到给 12 分，做到一部分给一半。是否做到，由 LLM 逐项判断。
  • 结果：仓库里查得到的完整跑数总共两次，前后相隔一天，分数是 69.9（D）、51.9（F）。这两次都少了四层评分里的一整层，报告末尾写着归因摘要生成失败。二十天后，这两份日志被当作冗余清理掉了。

病因一：判据不能执行

判据就是「凭什么说这次做对了」。作者说复盘后问题出在四个地方，前三个是技术性的，第四个不是。第一个是判据不能执行：起初把人写的参考实现当标准答案，一行行比文件和函数的覆盖情况；之后换成按 checklist 一项项打分，主指标于是全压在 LLM 的语义判断上。后来做方法论审计时，这笔账才算清楚。四层评分里最确定的那层是跑冻结单测，可 25 道题里有 22 道根本没有这层；缺了这层，确定性判分的比重由 65% 降到 40%，LLM 判分的分量涨到 60%。也就是说，主指标交给了一个一致性系数（Cohen's Kappa）在 0.10～0.21 之间的裁判，这个区间在统计学上叫「几乎不存在一致性」。

事后回看，同一个代码库里早有答案：有份说明文档写过需求和架构文档为什么不打分，理由是「LLM 打分误差大于信号」。作者说，这个判断在当时没错，只是没人想到它放到代码上也成立。

病因二到四

判分器自己有 bug：一份跑数因为清单提取格式错了，得 0 分；格式修好，同一份日志重判得 98 分。同一份产物前后差 98 分，说明那时的分数还不能当信号用。

光是维持流水线就是一份全职工作。平台的运维文档几乎只记录了它自身的故障：日志管道死锁，任务一直挂着「执行中」；后台进程因 SIGTTIN 信号停住 23 分钟；子进程成了僵尸；端到端单测卡住；子 agent 找不到插件。作者强调这不怪谁不上心：要让一条跨进程、跨容器、还得驱动另一个 agent 的流水线稳住，工程难度本来就高，只是难点全在评测目标之外。

考卷追不上考生：107 天里，评测目录搬家三次，判分办法也换过三回：先跑单测，后来比对参考实现，最后按清单打分；被评的开发流程也在变，评测还在按旧流程出题时，被评的命令已经并进了另一个命令。平台越重，追被评对象越慢，而 agent 恰恰是这个领域里变得最快的东西。

作者记得一个细节：评测代码拆出去单独成仓那天，平台的使用说明页还在更新，设计文档状态写着「已实施，持续迭代中」。当时没人觉得该停下，包括作者自己。

同期的小实验：成本低得不成比例，16 次跑数改掉一个策略

重平台

107 天、十七万行，留下的两个分数没有变成任何一次改动。

小实验

8 道题、两种检索方案各跑一遍，共 16 次跑数，一天跑完；结论直接变成一次提交，至今在生产中使用。

小实验要回答的是：知识库该怎么让 agent 检索。做法是做个 A/B：8 道题、两种方案各跑一遍，一共 16 次跑数。留下的只有会话记录和一份分析。结论：agent 不必先看路由文档、再跳过去，直接 grep 知识库就行，寻路从 12 步缩到 2 步。作者总结，16 次跑数胜过十七万行，不是因为规模，而是判对错的依据能直接运行出来，结论也能落成一次代码提交。

方案早就想清楚了，落不进重平台

方案其实很早就成形了。三月底整理思路时已经写好：用 pass@k 和 pass^k 两种口径；题库分成能力评测和回归评测两套（补充释义：一套考能力、一套防退步）；编辑振荡检测（同一个文件的同一区域被改超过两次）；越界修改检测（拿实际改动的文件去对照架构文档规定要改的文件）；文件命中率（访问过的文件中，该访问的占几成）。这些细到可以动手，第一笔代码在四天后提交。可到了六月审计方法论时，pass@k 还挂在待改进里，重复跑数一次也没跑成。作者说，不是没人想做，而是当时光让流水线不停摆就把人手占满了。作者加粗的一句是「平台越重，想往里改一个方案就越难」：想清楚一件事，一次思考就够；要把它塞进十七万行的系统，完全是另一码事。

作者认为这和前言里删掉 spec 是同一件事：值钱的是把问题想透，而不是承载它的载体；文档如此，平台也如此。有了这次教训，给测试线做评测时团队定下规矩：平台代码一行不写，手里只有题集、配置、脚本和跑数记录。

（二）测试线的第一版方案

V1 某个模块的召回率从 100% 跌到 40%，改两轮 skill 都不动：问题在评分器

要评的东西很明确：AI 写出来的测试到底有没有用。V1 分两条轨道：

闸门漏斗：沿用 Meta 论文 TestGen-LLM 的思路，AI 写出的测试要一关关过：静态检查无问题、跑得起来、三次结果一致、覆盖率够。

挖空回填：测试资产里有几条条目被故意删掉；agent 要做覆盖审计，找回几成就得几成分（召回率）。

从第一天就定下几条规矩：考卷和答案单独放一个仓库，被评 agent 的环境里看不到，作者加粗的说法是「考卷不能和课本放一起」；插件版本、业务代码版本、测试框架版本和模型都写死在同一份配置中；主指标一律用确定的方式判分，让代码运行结果当裁判，不让 AI 互相打分。

方案跑起来了，「跑数、看分、针对性改 skill、再跑」的闭环也转起来了。直到一个数字卡住了一切：某个模块审计召回率由 100% 掉到 40%，skill 改了两轮，数字一动不动。改不动 skill，就该怀疑分数。拆开评分器复盘，发现两个问题：

评分器量错了东西。它逐个文件核对，删掉的条目必须出现在原文件里才算数。会话里却写得很清楚：agent 找到了，不过放进了同一模块的别的文件。评分器把「放错文件」记成「没找到」，所以 40% 量的是「文件划分与标准答案是否一致」，不是「能否发现覆盖遗漏」。改 skill 救不回来，病根在评分器。

只跑一次，追的是噪声。同批数据中，有的模块掉了 40 个百分点，有的涨了 20 个，方向对不上。每个模块只删 5 个条目，召回率一跳就是 20%，±1 条的随机波动和真退步根本分不开。之前「看到单点退步就改 skill」的迭代，一半在追噪声。

作者的教训：评测本身也是软件，同样会出 bug；评测给出错误信号，比不给信号还危险，会让人去修根本不存在的问题。同样的坑这是第二回：重平台倒在解析判分格式上，这回倒在按文件计分上。上一篇针对覆盖率说过的话，这次落到了评测自己头上。

（三）带着问题做调研

业界调研的结论：有论文支撑的三个方法都站得住，自研的挖空回填塌了

数字不可信，下一步不是修数字，而是回去补课，查清 V1 的死因。团队翻了五十多篇论文和基准，按原文的顺序：SWE-Bench 一系怎样构造任务、防污染（补充释义：防题目事先泄露）；Meta TestGen-LLM 怎样设闸门；TestGenEval 怎样计算变异分数；SWT-Bench 怎么做 Fail-to-Pass（补充释义：测试先在旧代码上失败、修复后通过）。再用这些标准反过来量自己：四个核心方法中，三个有顶级会议论文直接撑腰，全都成立；唯一自研、业界没有对标的挖空回填，恰恰站不住。

作者说它塌得不冤。调研中找到一项构造效度研究（补充释义：看题目到底考没考到想考的能力）：在某个实验里，模糊测试工具把人工植入的 bug 百分之百（100%）都抓到了，真实 bug 却一个也没发现。人造的缺陷往往比真实的好找。挖空回填考的是「能不能猜出我故意删掉什么」，本质是合成题；召回率还能靠什么都报上来刷满，没有任何惩罚。两头都站不住。

V2 的核心主张：判对错要看代码运行的结果，而不是一张人造的清单。问法从「我藏起来的你找到没有」换成「你的测试真能逮住几个 bug」。

后来 Anthropic 发了一篇讲 agent 评测的文章（Demystifying evals for AI agents），把判分器分成三类：基于代码的、基于模型的、人工的；并指出基于代码的好处是客观、可复现、易调试。作者说团队第一天定的「确定性判分、不靠 AI 互相打分」与它结论一致。

（四）V2

V2 用变异击杀率当主指标：测试必须真的抓住埋进去的 bug

V2 的主指标是变异击杀率，这直接回答了本部分开头的问题。AI 写的测试要过五道闸门：

  1. 有产出。
  2. lint 干净。
  3. 能跑通。
  4. 连跑三次结果稳定（前四道沿用 Meta 的做法）。
  5. 能杀死多少变异体：真正拉开差距的是这一道。

覆盖率为何不行？有组实测数据（出自 TestGenEval）：GPT-4o 写出的测试，覆盖率 35.2%，变异分数却只有 18.8%。不写断言也能把覆盖率刷上去，杀变异体却非有真断言不可。

变异体，就是故意往业务代码里塞的一个小 bug，比如：比较符翻转（把比较符号反过来）；and/or 互换；删掉 or 0 这类兜底（默认值）；把写状态的整句注释掉。测试在改坏的代码上报错，叫杀死；仍旧通过，就是断言没看住这一处。后四种方式出自团队的代码评审清单，清单归纳的是本项目真实出过的 bug，照着它埋，才像真实事故。

选什么函数，就是在考什么能力

作者说，整套评测最花工夫的，是决定在哪些函数里埋、埋什么：挑了哪些函数当考题，也就定下了要考 agent 的哪些能力。V1 选了十个函数，看的是外形（行数、if 个数、模块分散程度），还得挑本来就有用例的。结果有三：偏向纯计算函数，那正是 LLM 的强项，分数偏高；已有用例都出自 AI，并无人工标准答案，「和人写的测试比」就成了空话；没考虑代码改得勤不勤，函数一重构，它身上 12 个变异体全部报废。

V2 选题分三层：

  • 场景（V2 的第一层）保证题目像真实业务，分发奖、任务、活动、成就、排行榜、聊天六大类。
  • 原型保证各种出错方式都考到，共六种：校验闸门、资源结算、时间窗口、状态机、兼容兜底、遍历聚合，同样取自评审清单。
  • 四个难度轴用来配平难度：分支复杂度、依赖构造成本、副作用、函数可见性。

另有六道硬门槛，每条都注明出自哪次教训，例如：函数长度在 15~80 行之间（短了没地方埋 bug，长了写单测太贵）；分支密度至少 3；依赖可 mock（能用替身替换）；可变异点不少于 6 个。并发、性能这两类不出题，单元测试测不了。

（五）出题这条链上，人和机器各站在哪

出题链上：agent 取素材，人定价值，执行结果定生死

作者说，建题集是作者做过的最干净的一次人机分工。整条链路如下：

  1. 人给出方案。
  2. 派出六个子 agent（sonnet 模型），每个负责一个场景，从业务代码里找素材：先用知识库的文件地图圈定范围，再进代码核实，逐条回答硬门槛，共交回 34 个候选。
  3. 人来定稿：按场景、原型、mock 轻重三维配平，从 34 个里挑出 16 个，每个落选的理由都记了下来。
  4. 脚本造变异体，按算子轮流分配名额，让各类失效模式机会均等。
  5. 三级验证：sonnet 先剔掉明显等价的；用参照测试实际执行来定生死；人只复核两边结论不一致的。
  6. 由 deepseek-v4-pro 答题，每题答三遍取平均。

为什么检索交给 agent 而不用脚本？名叫 check_ 的函数可能只是转发，名叫 update_ 的反而在做真校验；「这个函数能不能考出能力」靠规则匹配判断不了。但人要复核它带回的事实：比如 agent 报告某文件过去一年改过 48 次，可具体到候选的那个函数，一年不超过 1 次：它统计的是整个文件。作者说这再次印证前言：AI 做功能没问题，给出的「事实」却经常走样，因此定稿前要再按函数逐个核一遍。

什么算真 bug，只有人能定。最难缠的是等价变异：代码动了，行为却一点没变，这种假 bug 进了分母就谁也杀不掉，每个考生都吃亏。难点不在识别，而在定义。团队定下两条口径：一是只有日志不同不算「看得见」，不然会催生专门检查日志的测试，那不是想考的本事；二是看正常方式能不能构造出杀死它的输入，入参和缺省字段可以构造（这算自然构造），可如果必须把环境常量换成错误类型、或者传进毫无意义的值才能杀掉，就判为等价。作者说这是纯粹的价值判断，脚本替不了，机器只能在拍板后执行。

验证者自己也会错，所以顺序不能倒。模型初审犯过三种错。其一，把 and、or 对调后，短路保护其实失效了，运行时报错其实可观测，它判错了三个。其二，条件有好几个分支，它只看了一个。其三，一行里有两个同样的符号，它给的理由指的是另一个；结论虽然碰巧没错，记录却是错的，所以提示词规定必须用列号指明变异位置。参照测试也会错：有一次全量验证，8 个变异体没杀掉，查下来 5 个怪参照测试本身：在 pcall 闭包里声明的局部变量，到闭包外再读始终是 nil，断言值碰巧和预期一样时就会假 PASS（误判通过），这一整类变异都漏了。改好后这 5 个都被杀掉，真正等价的只有 3 个，而且光看语法根本认不出。

作者的结论：模型审查节省机器时间，最终死活由实际执行决定。最后 184 个变异体全部定案：172 个确认能被杀死，收进题库；12 个等价，剔除。每个判定都留有模型初判和人工复核两份记录，以人工为准。

正式开考前，先用答题模型 deepseek-v4-pro 把 16 道题各做一次，看题目能不能拉开差距：击杀率最低 12%、最高 100%，宏平均 61%，难易适中，才正式开考。

（六）跑数纪律，和对评测自己的评测

只看均值，差距小于 3 个百分点不下方向性结论

正式跑数：16 道题，每题跑三遍，共 48 次跑数，约 19 小时机器时间。统计规矩照业界：只看均值不看单次。Anthropic 测过，单是基础设施带来的波动就约有 6 个百分点，据此分三档：

  1. 差距小于 3 个百分点：不下方向性结论。
  2. 3 到 6 个百分点：标「可能显著」。
  3. 超过 6 个百分点：才能当改 skill 的依据。

这条规矩是 V1 的教训逼出来的，所以写死在跑数程序里：默认跑三遍，只跑一遍的模式只能用来空跑试流程。

跑数可信还有一个细节：判断 agent 是否亲自跑过测试，看的是会话里真实发生的工具调用，它嘴上怎么说不算数。这条规矩连团队自己也照样适用：命令配置里声明已经去掉 Task 工具，实际工具列表里它还在。声明和事实不符，自家也会发生。

跑完后团队还评审了评测本身。最犀利的一条：参评的 agent 每次都装着全套测试 skill，没有「不装 skill 的模型」作对照，所以说不清插件究竟有没有用。作者认为这条批评成不成立，取决于目的：若要对外证明插件有价值，少了对照组（基线）就是硬伤；目的是优化，找短板、指导下一步，就不必回答，多跑基线对优化没有输入。所以设计评测前要先想清楚目的，它决定要回答什么、可以不答什么。

（七）五类短板，和一个被数据推翻的分类学

真正值钱的是失败归因，以及被数据推翻的那套分类

分数本身不是最值钱的，失败归因才是。把没被杀死的变异体聚类，得到五类通病：

  1. 不测缺省兜底（最大的一类）。
  2. 不测边界相等值：不等式恰好相等的那个点没人测。
  3. 只断言返回值，不查状态有没有写进去。
  4. 不踩非法入参：不去试传进错误参数会怎样。
  5. 不枚举模式常量：有几种模式就该逐个测，却没测全。

每一类都能直接变成测试 skill 的通用规则，例如：每个「x or default」写一条字段缺失的用例；每个不等式写一条正好相等的用例；有状态写入的函数，调用两次并读回断言。

作者老实承认：这些方向作者在出题时就想到了。挑选失效原型、设计变异方式，其实就是在问「AI 写测试最常漏掉什么」。数据做的事，是把这些判断量化成清单，排出哪块短板更严重；方向是作者自己想出来的。

数据告诉作者的、作者自己想不到的是：那套精心设计的原型分类，根本预测不了得分。同为「校验闸门」，两题分别是 91% 和 14%；同为「时间窗口」，分别是 91% 和 12%，高低差到了头。左右分数的其实是：要杀死这个变异体，杀死它需不需要构造缺省值、边界值、状态型输入。往后定难度、做配平，都要按这一点。作者认为，自认为合理的分类被自己的数据推翻，正是评测最该产出的东西，比任何分数都值钱。

还要警惕一点：16 道题身兼两职，既用来校准，也是正式考卷。如果照着没杀死的变异体去调 skill，然后拿同样的题再考，涨分一定虚高。办法有两个：只做通用改动（不出现具体函数名），并在报告中写明；或者预留几道题完全不拿来调，作为留出集。作者管这叫「用考题练考题」，说这是做评测最容易骗自己的环节，而且机器不会提醒你。

（八）推到最后，两件事确定了

题集才是本体；评测能帮忙，但先算清成本和目的

第一件：评测的核心是构建题集。不是搭平台，也不是搭流程。回头看，方案每一次变好，都是题目变好：挖空清单被否掉；选题从看外形变成三层考纲；变异体三级验证；开考前校准区分度。跑数、判分、出报告这些流程始终只是一堆脚本；它们的价值全在确定性，而确定性不需要架构。开头那套平台的十七万行，几乎都花在了这类环节上。

作者引了姚顺雨在 The Second Half 一文中的看法：AI 进入下半场后，重点从解决问题移到定义问题，做评估比做训练要紧。出题，正是在定义问题。工程实践推出的「题集是本体」，和研究视角的判断是一回事。

第二件：评测有用，但成本业务团队很难扛。作者自知这话不中听：评测的确有助于改进，但不做评测也一样能把 agent 调好。好处是实打实的，五类短板条条能写成 skill 规则，分类被推翻更是意外收获；可评测里成本最高的那部分产出，和认真分析问题本身就能得到的东西高度重合。成本摆在那里：校准一轮花了 500 多元、10 多个小时；正式 48 次跑数约耗 19 小时机器时间；出题更贵，单是 token 就用了几千美元，人力也没因为有 AI 帮忙而省下来。

作者提醒要分开看两个问题：「是不是常」说的是资产保值，「值不值得做」说的是投入产出。题集确实是「常」：从真 bug 改造来的变异体、按真实事故分类学定的考纲、三级验证流水线、两条政策口径，不管换哪个模型都能接着用。但「保值」不等于「现在就该投」。什么时候值得做评测？一是两套方案要做代价很高的取舍，二是得向外人证明改进确有其事。平时迭代，靠真实需求反复跑、靠会话分析定位短板就够了，第一部分正是这么做的。继续读主线 4
