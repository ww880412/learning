AI Coding 深水区 · 主线 1 提示词的尽头是基础设施
这条主线讲什么？

提示词只能叮嘱，框架能取消一类错误

提示词的边际收益会耗尽：注意点越多，模型注意力越碎，主任务越差。

两个例子的解法都不在 agent 层，在 agent 底下的框架层。

第一部分「本部分要点」、（三）
1背景项目技术栈特殊，专门开发了端到端测试框架；内部用了数月、成熟后才交给 AI
2打磨测试 agent 的提示词和流程编排又打磨了数月
3瓶颈怎么调提示词，都调不出初期那种立竿见影的效果
4第一反应措辞再强硬、规则再细、例子再多给一个——撞了很久的墙
5转折用自研会话分析工具 tracesift 把所有测试会话摊开分析
为什么要往下沉？

提示词调了数月，撞上边际收益的墙

分析完会话才看清：剩下的问题在提示词和流程层面根本解不掉。

先看会话证据，再决定在哪一层解决。

第一部分 开头
提示词层反复强调「setup/teardown 必须成对出现」；AI 仍有约一半概率漏掉 teardown，用例互相污染
框架层声明式 mock + 自动还原：mock 声明出来，用例结束框架自动还原
常规思路加 lint hook；但规则式 lint 很难查出来，AI 也仍有概率绕过
结果AI 在这里几乎不再犯错
例一：mock 还原

框架自动还原 mock，AI 不再漏 teardown

作者的类比：就像自动 GC 一样。

写测试要同时顾的点太多；用框架消掉一整类错误，等于把 AI 的注意力还给主任务。

第一部分（一）
超时那一刻，框架反向探测各服务的队列和限频登记表
1还在排队按现场分类
2出队未回包出队了，但业务代码没回包
3被限频丢掉在分发层被限频丢掉 → 下一步：检查前置请求是否用完了限频配额
4回包没人接回包到了，但当时没人接
代码执行路径：链路最后执行到的那几行原样贴进报错，末行标箭头
例二：trace 链路分析

超时报错直接给出原因和卡住的那一行

裸超时只能告诉你「没等到回包」；AI 要读大量代码追调用链，常常耗时极长、上下文过载。

每一类后面跟的不是现象描述，是下一步动作，连该看哪个配置字段都点出来。

第一部分（二）
报错通道 = 提示词注入通道可以返回任何 AI 需要的信息；时机精准，正好在 AI 卡住的那一刻到达
被删掉的告警AI 等一个不在协议表里的协议名，就提醒一句
删掉的理由（写在文档里）协议表按线上流量生成，冷门协议本来收不全，登陆窗口期的协议全都不在表里
结果告警信噪比很差，还会把 AI 带偏
报错通道还能做什么？

报错通道是提示词通道，带偏的反馈更糟

作者的说法：最好的提示词，是恰到好处的反馈。

注入的信息不是越多越好；会带错方向的反馈，比没有反馈更糟。

第一部分（二）后半
写在提示词里越厚，模型要同时记住的事越多，越笨
写进框架越厚，模型越省心，主任务反而更强
ut-tester（测试 skill）SKILL.md 四百多行；2 月到 6 月每月都在加，7 月之后几乎停了——加不下去了
ut 框架6 月框架侧的提交大约是 skill 的四倍
打补丁的规则「严禁 mock ss，只有一种正确写法」
八天后对着仓库里 529 个存量单测发现，这条从落笔那天就和事实相反
harness 越厚，agent 越笨吗？

写进提示词越厚越笨，写进框架越厚越强

领域里稳定的事实、能力边界要写，但写在提示词里有上限：再厚，厚的是模型的工作记忆。

打补丁这一档尤其不要写：它生来就在拿有限规则覆盖无限问题。

纪律的消失：自动还原上线前，会改脏环境的用例必须排到最后跑，跑完还得重启服务。自动还原和静态闸门到位后，交接文档写下这条纪律「自此作废」。

ut-tester 最后一次实质改动，标题是「对齐 UT 框架近期改动」。

验证是第三件事，发生在产出之后：核测试能不能抓 bug、报告有没有撒谎（见主线 3、主线 5）。

作者的判断：生产级 agent 建设最终都归到基础设施；框架设计、编译原理、协议栈这些硬功夫不会过时。

第一部分（三）（四）
那是不是什么都该往下沉？

判据是事实才硬拦截，代理指标只提醒

同一个 hook 拦截器里的两条规则，待遇完全不同。

读过不等于遵守，没扫到也不等于没读过。

第二条还翻过一次车：主会话累积了所有历史 Read，会把「已读」这个状态污染给之后的每一个子 agent（结论留在代码注释里）。

作者说这和前言的尺子是同一把：前言分「交给机器还是留给人」，这里分「做成机制还是留在提示词」。

第一部分（五）
假测试AI 把被测函数的内部逻辑抄出来，用本地变量重算一遍再断言：断言全过，覆盖率零
硬失败脚本报告成功、报告文件也生成了，但覆盖率 0/0 行 → 直接判失败
ut-lint 两条易误报规则始终没改成阻断；reviewer 提示词要求每条结果读源码二次确认，写明理由
误报的真实代价为了过 lint 把 helper 拆开内联
下沉时还要注意什么？

信号要从外部取，误报会逼出更差的代码

假测试提示词防不住，因为 AI 自查也会认为自己做对了。

门禁误报的后果不是浪费一次提醒，是逼着人和 AI 为了过检查把代码写得更差。

第一部分（五）「一是」「二是」
一件不太顺利的事

能不能往下沉，取决于底座给不给接口

Claude Code 和 codebuddy 的 hook 协议里，SubagentStop 不支持往上下文里注入内容；作者要的是提示，协议只给阻断。

改进方向（还没落地）：脱离 agent 框架，CI 也一起受益。

作者说这条路比 hook 更彻底：同一套规则，从「叮嘱模型去跑」变成「环境里跑测试就会跑」。

衔接主线 2：能不能往下沉，一半不由作者说了算——这就引出编排和 runtime 的问题。
