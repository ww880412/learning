把判据变成每天在跑的流程：平台承载的是嵌套的环

AI 一次写出的东西靠不住，人一次盯住的注意力也靠不住；可靠性只能靠多层彼此独立的检查环叠出来。

开头

推导的起点：两个「单次不可靠」

前四部分讲了让 AI 扛得住、量得出好坏、人退到哪里。最后一部分要把「机器提供事实、人做判断」从一句口号，做成每天都在运转的研发体系，这也是前言里那个平台的来历。

作者先声明：平台仍在建设，这里讲的是思路而不是竣工报告。这么重的平台该由业务团队自己建吗，会不会被中台一下替掉，这是它最常被质疑的一点，答案留到最后一节。先给结论：平台承载的不是一堆功能，而是由人、agent、资产交织成、转速不同的嵌套环。

不可靠一：AI 的单次产出

前言说过，出错的总数取决于累计产量，而不是单次准确率。一次会话写得再漂亮，也别指望零缺陷。

不可靠二：人的单次注意

这一条更难承认。代码不是自己写的，大量细节在人的视野之外；长会话里注意力会疲惫、走样，判断质量随产出量一路下滑。

作者的比喻：指望人在一个环里从头盯到尾，和指望 AI 在一个环里一口气写对，是同一种碰运气。

（一）环为什么要嵌套

不是「再认真查一遍」，而是多道独立检查叠加

两个不可靠放在一起，结论不是更用心地检查一次，而是让好几道相互独立的检查叠出可靠性。

团队把环分大小两层。小环是一次会话里的开发和自测：AI 写、AI 自己跑、人在会话里看着。会话一结束就进大环：agent 自动评审代码、过各种清单和静态检查、跑更完整的测试。既不能指望小环里写出完美代码，也不能指望会话里的人一直盯得住。

大环要站得住，靠两个设计：

  1. 每个环独立：评审由轮询提交来触发，跟会话无关；测试由平台自己的容器重跑，跟生产方的自我汇报无关。触发源和被验对象没有因果牵连，环得出的才是新信息，而不是把上一环的话再念一遍。
  2. 把注意力问题拆开：长会话需要持续又发散的注意，这正是人最弱的；多个环把同一件事分到不同场景、不同时间点触发，每次主题单一、关注点集中，效率完全不一样。同一个问题被不同角度的环一再提出，比被盯一次更容易暴露和修好。

环里还有一种不耗人注意力的角色：闸门，即确定性的规则和清单。它们只把例外递给人，所以越多越好。唯一的要求沿用主线 1 的标准：判据是事实就硬拦，是代理指标就只提醒。常规情况被闸门消化掉，人只处理例外，环才转得起来。

（二）环的接口：只许传事实

三个机制，都长在测试用例这条环上

环一多，问题就落到接口：环之间交接什么？作者定了一条铁律，只交接事实，不交接声明。接口上混进一次声明，下游每个环都在核验一个假东西。这条规矩落成三个机制，都从测试用例这条最先转满一整圈的环里长出来。

机制一：生成方不当写入方

生成侧只交候选，写仓库的权力全部收归平台。平台是唯一的写入方，每个受管的仓库排一条串行队列。作者的分工是：AI 管快，人管对。

流程统一为：AI 产出候选，人审，串行入库，沉淀成资产。人审时不只是通过或驳回，还可以改内容、换归属、整条扔掉；入库时平台会顺手清掉已无人引用的公共代码。审批需要时间，期间仓库可能已被别的入库改过，所以入库是合并而不是追加：能自动合的自动合，合不上的标出来给人。只有真冲突才需要人。

机制二：每种失败都要有名字

环要跨天、跨容器、跨进程运转，一旦卡住，人得一眼看出卡在哪一步。

事故：一批用例入库长期停在「正在合并」，恢复了四次都没用。原因有三层叠加：底层仓库对象能判断有没有真实改动，但线上实现没把这个能力接出来，探测失败就默认「有改动」，于是硬去提交一个空 commit；一般报错找不到对应的失败状态可落，网关就只留日志、状态原地不动；服务重启后，恢复程序只认「正在合并」的任务并重新投递，空 commit 就这样自我循环。

最讽刺的一点：测试替身恰好把那个可选能力实现了，测试一直是绿的，根本测不出线上漏接。

三处修法：那项能力改为接口里必须实现的方法，忘了接编译就报错；没有真实差异时不再提交，直接收尾；一般错误、超时和 panic 统统落到能重试的「合并失败」状态，停机导致的取消则维持原状，恢复程序也不再自己去重试处于失败态的任务。

状态机由此扩到七个状态：原有的待审、正在合并、已入库、已丢弃、冲突、推送失败，外加这次事故换来的「合并失败」。作者的总结：没有名字的失败，对人等于没有事实；对环来说等于环消失了，它还在转，却永远转不完一圈。

机制三：事实只有一个来源，而且能推导

环和环之间不能有两份事实，也不能传「它说是这样」。AI 生成的测试怎么和覆盖率对上号？团队的做法是用文件路径约定来推导：用例放在按「被测文件路径 / 被测函数名」组织的目录里，路径本身就说明它测的是哪个函数。为什么不让 AI 在元数据里自己填？作者的话是：

因为声明会撒谎，路径不会。

原文第五部分（二）机制三

作者随即补了一个诚实的注脚：线上有两千多条单测，归属一栏原本就是空的，团队其实没得挑；代码中也还留着「库里有值就先用库里的」这条分支，所以 AI 要是真填了，照样会被信。这件事只做到一半，剩下一半明确记作技术债。

覆盖率还有两条判断，都是被自己打脸后才定下的：

  • 多条用例按行取并集：单测一条条单独跑，每份快照只反映自己走到的分支，只取其中一份必然偏低。
  • 没跑过不等于跑了没覆盖：分母只算真正跑到的函数，这两种情况都不显示 0%。

第二条来自平台曾把「采集失败」显示成「没有数据」的教训。作者说上一篇讲过错误的覆盖率信号比没有更危险，主线 3 那两次是评测系统自身的 bug，这里是同一教训第四次出现，而这次说谎的是「事实」本身。

（三）环的入口：不信上一环的自报

平台自己重跑，结果放到审批页，判断交给人

接口管交接什么，入口管信不信。生成侧的 AI 自己跑过测试、也交了覆盖率报告，但这份结果不能采信：它可能声称通过，覆盖率却是空的。

所以平台用自己的容器池，把待审用例独立重跑一遍，逐条结果直接放上审批页当材料。结果只做参考、不卡审批，仍然是机器给事实、人来判断。

容器池本身也按环的思路设计：池里的机器并非平台自建，而是各位管理员把手头的开发容器贡献出来。一台容器分出几个槽，同一个槽里一次只跑一件事，不同槽可以同时跑；运行记录只增不改；某个槽失败了就换一个重来。谁手动发起的就用谁的私有池，平台自动发起的验证走公共池，彼此不挤。

（四）环上的货币：资产要被治理，而且是活的

为什么必须是平台，而不是一个仓库

不治理会怎样

AI 写的用例东一堆西一堆，没人说得清哪些能跑、哪些过时；评审意见发进企业微信就沉底，同样的误报下周再来；知识入库不设关，错误经验混进正式知识，比没有知识还危险。

治理的做法

需求、用例、知识在进仓前一律只是「候选」。作者把审批比作货币发行纪律：人判断过才能入库，入库后才算资产。

人的判断本身也是数据：丢掉一条用例的原因、把一条评审意见判为没价值的原因、驳回一条知识的原因，都和审批结论一起按结构存档，再反馈给生产那一端。某类候选老被丢，就说明上游的提示词或 skill 该在那儿改。

不过往回喂要有节制：人的判断得先攒到值得信的程度，自动往回喂才谈得上。拿未经校准的标签去改提示词，就是用脏数据训练上游；作者说这和主线 3 那个有 bug 的评分器是一回事，区别只是这回被带偏的是生产方。

作者认为「资产是活的生命周期」是为什么要平台而不是仓库的最硬理由。放到版本节奏里看，一条需求的背景信息得同时服务两个版本：线上那个，和正在做的那个。上线后出 bug 要打补丁，补丁期的工作方式和开发期完全不同，格外看重改动最小、兼容、数据修复和可观测。这些正是前言说的价值观型约束，AI 交付功能的本事强于守纪律的本事，所以这些不能只写进提示词等它自觉，得变成需求状态流转时必须过的判据。仓库装得下文件，装不下一个要跨两个版本、两段纪律完全不同的上下文。

（五）人是环里的节点，不是环外的验收员

平台的职责：让人下判断更省力

平台刚起步时给自己划过线：只管外环，不碰云端写代码的环境，免得长成第二个 Codespaces。后来这条线被团队亲手拆了，做出了 AgentUI，一个开在浏览器里的会话工作台，背后直接连到容器内的命令行 agent；批权限、答提问、中途插手，都能在网页上做完。

推翻的理由比原边界更根本：人不在环外验收，而是环里的一个节点。节点要干活，要批权限、定稿、审批、随时找任一 agent 对话，平台就必须把交互做进来。作者说这是主线 2 那个需求在平台层面的重演：工作流引擎给不了的掌控感，环系统得给。

人在环里，接着的问题就是人怎么跟上环的转速。作者说本质不是让人多读，而是想尽办法降低人做判断的成本。办法没有尽头，眼下做了三件：

  1. 产物从 Markdown 换成 HTML：一百多行的 Markdown 作者自己都读不完。HTML 能放表格、SVG 图、折叠和导航，还能一键分享。Anthropic 做 Claude Code 的那支团队专门写文章讲过这件事，说用了 HTML 之后人重新回到了循环里；最关键的是自定义界面要以「导出」收尾，比如导出 JSON 或提示词，让人在界面上的判断一键变回 AI 的输入。团队眼下只走了一段：trace 语义视图以及测试和覆盖率两类报告，已经做成单文件就能打开的 HTML；而需求文档、知识条目和评审意见仍停留在 Markdown。
  2. 什么都能标注，标注回灌给 AI：平台里还没有，但在开发流程插件里已经有个小回路能用：人在方案文字上圈选并写批注，批注当即被整理成结构化输入送回模型。作者的看法是，整套系统从外部得到的输入只有人的判断，所以机制要做的是别让它丢、让它能反复用。
  3. trace 报告可视化，数字不让模型碰：LLM 只管起名、分组、写说明；所有数字由确定性脚本从原始证据重新算；守恒校验不通过就退回完整的原始视图。可视化不是把 JSON 画好看，而是在不失真的前提下让人一眼看懂。
（六）环要铺满研发周期

一副骨架，铺到需求、开发、评审、测试、上线、补丁

前面的环大多围着测试和评审。但目标是整个研发周期，每个环节都值得有环。骨架只有一副：触发、生产、闸门、人审、入库、复用，铺到哪里都是它的一个实例。离团队最近的三个都在周期最前面：

  • 需求预分析：需求单一分配，agent 就开始做粗方案、找出策划案没写清的细节、评估影响面和工作量。作者强调最克制的是产出形式：待澄清清单才是核心价值，方案只是 AI 自圆其说的一种，不标清楚，读者会当成推荐。
  • bug 预分析：判断是不是 bug、出在客户端、DS 还是后台、原因和修法。它有别的环没有的优势：bug 最后真的会被修，真实答案免费回流，准确率能统计、能校准。
  • 评审预分析：人工评审开始前，agent 先扫一轮，把常见类型的 bug 筛掉，人的注意力就能集中在确实需要拍板的地方。
（七）业务团队该不该自建这么重的平台

壳用现成的，本体才自建

环铺得越满，这个问题越躲不开：业务团队有必要自建这么重的平台吗？会不会被中台轻易替代、投入打水漂？作者分两层回答。

第一层：能替换的本来就没自建

运行容器借用 AnyDev，命令行工具直接用现成的，需求单则从 TAPD 拉取。团队亲手建的只有中台提供不了的三样。一是判据，比如变异算子取自自家评审清单、补丁纪律取自自家的版本制度；二是资产模型，比如路径约定、知识模块和整套需求文档；三是环怎么接线，即哪类例外在什么时机递给谁。中台给得了壳，比如算力、会话、通用 CI，给不了本体。

第二层：钱花在哪，决定会不会白花

平台最值钱的产出不是代码，而是题集、判据、资产怎么建模、环怎么设计，再加上一路踩坑留下的失败记录；它们跟着团队走，不跟着代码走。和前言删掉 spec 文档同理：载体可以扔，想清楚的东西省不掉。即使明天平台整个被换掉，这些也一件不会浪费。

作者说这和主线 3 是同一个结论的两面：题集、判据、资产模型都是本体，本体都不通用，通用的都不是本体。哪天通用平台把壳做得更好就换掉；自建部分本来就是按「不可替代」筛出来的，这是建设原则而不是巧合。

全文的收尾：这个平台是研发体系的运行时。人、agent、资产交织成转速不同的嵌套环；人离开产出线，站到环的节点上只做判断；机器在环的接口处提供能核验的事实；资产在环之间流动、增值。回全文导读
