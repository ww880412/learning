AI Coding 深水区 · 主线 5 把判据变成流程
这条主线讲什么？

平台承载的不是功能，是嵌套的环

环由人、agent、资产编织成，转速各异。

原文声明：平台还在建设中，这一部分讲的是建设思路，不是建成报告。

第五部分 开头、（一）
不可靠 1：AI 的单次产出出错的绝对数量由累积量决定；一次会话写得再好，也不能指望无瑕
不可靠 2：人的单次注意代码不是人写的，细节超出人的观测；长会话里注意力会疲劳、变形
推不出「更认真地检查一次」
推出用多重独立检查叠加出可靠性
为什么要多个环？

AI 的产出和人的注意，单次都不可靠

让人在一个环里盯到底，和让 AI 在一个环里写到底，是同一种侥幸心理。

两个不可靠合在一起，推出多重独立检查。

第五部分 开头、（一）
1每个环独立评审靠轮询提交触发，与会话无关；测试用平台自己的容器重跑，与自报无关
2拆解注意力同一件事拆到多个场景、多个时机触发；每个场景主题单一
3闸门确定性的规则和 checklist，不消耗人的注意力，只把例外递到人面前
大环要成立，靠什么？

每个环独立触发，说出来的才是新话

大环不消灭注意力问题，它拆解注意力问题：被反复暴露的问题，比被凝视一次的更容易被发现。

闸门的判据必须是事实：是事实就硬拦截，是代理指标最多提醒（主线 1 的标准）。

第五部分（一）
环和环之间传什么？机制一

环的接口只许传事实，不许传声明

接口处传一次声明，下游所有环都在验一个假东西。

机制一：生产者不是写者——AI 负责快，人负责对；每个受治理的仓一条串行队列。

审批期间仓库可能已被别的入库推进，所以入库是合并：能自动合的自动合，合不了的标出来交给人。人只在真冲突时介入。

入库时平台把不再被引用的公共代码一并裁掉，不让垃圾进仓。

三个机制都从测试用例这条环上长出来：它是第一条转完整圈的环。

第五部分（二）机制一
一批用例卡在「正在合并」，四次恢复都失败：三层原因
1能力没透传仓库对象能判断「有没有实际改动」，生产实现没透传；探测失败默认「有改动」→ 提交空 commit
2没有失败态普通错误没有对应的失败状态，网关只记日志、不改状态
3恢复逻辑重启后只重投「正在合并」的任务 → 同一个空 commit 循环
!测试替身实现直接实现了那个可选能力，测试永远绿，测不到生产漏接线
机制二从哪来？

没名字的失败，让环永远转不到头

环跨天、跨容器、跨进程转；卡住时，人要一眼看到卡在哪一节。

一个没有名字的失败，对人来说等于没有事实。

第五部分（二）机制二
修法三处
1必需方法把那个能力变成必需方法，漏接就编译不过
2直接收口没有实际差异就跳过提交
3失败入态普通失败、超时、panic 一律进可重试的「合并失败」；恢复逻辑不再自动重试失败态
状态机：七态
→状态待审 · 正在合并 · 已入库 · 已丢弃 · 冲突 · 推送失败
7新增合并失败
怎么修？

「合并失败」这一态，是事故买来的

停机取消保留原状态。

失败必须有名字：前言里「这个失败必须有名字」的判断，在这里落成了状态机。

第五部分（二）机制二修法；前言（三）
-- 用例文件路径 = 被测函数归属的事实源
ucases/<被测文件路径>/<被测函数名>_unit.lua
-- 覆盖率事实的两条判断
合并  多用例按行取并集
区分  「没跑过」≠「跑了没覆盖」
      分母只含实际跑到的函数，两种都不显示 0%
机制三：事实源唯一、可推导

归属从路径推导，因为声明会撒谎

不让 AI 在元数据里声明被测函数归属：声明会撒谎，路径不会。

诚实的注脚：代码里还保留「库里已有值就先用它」的分支，AI 真填了还是会被信——这一半是明确的技术债。

现网有两千多条单测的归属字段本来就是空的，作者说他们其实没得选。

多用例按行取并集：单测逐条单独跑，每条快照只反映自己覆盖的分支，取任何一条都会低估。

「没跑过」和「跑了没覆盖」的区分，立在平台曾把「采集失败」显示成「没有数据」的废墟上。作者说这是同一个教训的第四次，这次撒谎的是「事实」本身。

第五部分（二）机制三
环的入口信不信上一环？

平台自己重跑，结果摆上审批页

生成侧的结果不能信：它可能声称成功而覆盖率为空。

结果仅供参考、不阻塞审批——机器提供事实，人做判断。

容器池：管理员把自己的开发容器贡献进池子；每个容器若干执行槽位，槽位内严格串行、槽位间并行；执行记录只追加不修改；失败换槽位重试。手动触发跑在触发者的私有池，平台自动验证跑公共池。

第五部分（三）
不治理用例散落、没人知道哪些能跑；评审意见发完企微就沉了，同样的误报下周再来；错误经验写进正式知识
治理进仓前一律是「候选」；人做过判断才入库，入库才成为资产
人的判断也是数据丢弃、标无价值、拒绝的原因结构化落库，回流给生产端
需求上下文要活过两个版本上线版本 + 在研版本；patch 期在意最小改动、兼容性、数据修复、可观测
环上流动的是什么？

资产不是文件，是活的生命周期

patch 期那几条是「价值观型」约束，要做成挂在需求状态机上的判据，不能写进提示词指望自觉。

回灌要克制：先把人的判断攒成可信的数据，再谈自动回灌。

作者的理由：拿一批没校准的标签去改提示词，等于用脏数据训练上游——主线 3 错误评分器的翻版，只是污染的是生产者。

作者说这是「为什么必须是平台而不是仓库」最硬的回答：仓库存得下文件，存不下要活过两个版本、两期纪律完全不同的上下文。

第五部分（四）
降低人做判断的成本：目前的三个例子
1HTML 产物测试报告、覆盖率报告、trace 语义视图已是自包含 HTML；需求文档、知识条目、评审意见还是 Markdown
2标注回灌平台里还没有；/dev 插件里跑通了小回路：划词批注当场变成结构化输入
3数字不许模型碰LLM 只命名、归组、写解释；数字由脚本从原始证据重算；守恒校验不过就退回原始视图
人在环里干什么？

人是环里的节点，平台要降低判断成本

平台起初的边界是「只做外环，不做云端编码环境」，后来自己推翻了，做了浏览器里的会话工作台 AgentUI。

人不是环外面的验收员；节点要批权限、定稿、审批、随时和任意 agent 对话。

作者引用 Claude Code 团队的文章：用 HTML 之后，人重新回到了循环里；自定义 HTML 界面必须以「导出」结尾（copy as JSON、copy as prompt），让判断一键变回给 AI 的输入。

这也是主线 2 那个需求的重演：workflow-engine 给不了的掌控感，环系统必须给。

第五部分（五）
环的骨架只有一副触发 · 生产 · 闸门 · 人审 · 入库 · 复用
最近的三个环（研发最前段）需求预分析（核心价值是待澄清清单）；bug 预分析（真值免费回流，可校准）；评审预分析
不自建（可替代的壳）容器用 AnyDev，CLI 用现成的，需求单从 TAPD 同步
自建（本体）判据、资产模型、环的接线
深入一层：业务团队该自建这么重的平台吗？

凡是本体都不通用，凡是通用的都不是本体

中台能给壳（算力、会话、通用 CI），给不了本体。

平台最值钱的产出是判据、题集、资产模型、环的设计和失败史；它们跟着团队走，不跟着平台代码走。

需求预分析的产出：待澄清清单是核心价值，方案只是 AI 的一种自洽——不标注清楚，看的人会把它当推荐。

作者说：哪天通用平台把壳做得更好，换掉就是。环的目标是整个研发周期：需求、开发、评审、测试、上线、patch。
