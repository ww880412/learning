这条主线讲什么？

编排追到根上，是 runtime 主权问题

编排（多个 agent 谁先谁后、怎么通信）问题，作者用两条线追到底，最后合流。

作者说这个认知是两项实验、三起事故加一次源码审计一起买来的。

第二部分「本部分要点」、（五）末段
workflow-engine：主 agent 做成状态机，按固定流程 spawn 子 agent
1token 消耗大子 agent 每次从干净上下文出发；review 打回三轮，implementer 就把相关代码读三遍
2体验不佳编排逻辑复杂、上手门槛高；子 agent 过程不透明，没有掌控感
3主 agent 浪费只维持秩序，最值钱的能力——直接和用户对话——闲置着
原来的编排哪里不够？

状态机编排换来了稳定，但光稳不够用

上一篇的结论是「真正贵的不是 token，真正贵的是失控」，所以选了稳定。

重新打开这扇门，不是因为「失控比 token 贵」错了，而是光有稳已经不够用。

第二部分（一）
方案一（风险低）需求分析、架构设计收回给主 agent 亲自做；拉子 agent 优先续接（resume）上一轮
状态已经落进现在的 /dev 流程
方案二（风险大）agent teams：网状通信，成员常驻、互相直接发消息、共享任务看板
状态官方标为实验特性，几乎没有公开实践——作者亲自蹚
两个方案怎么选？

低风险方案已落地，高风险的作者亲自蹚

方案一的好处：交互多的环节体验向单 agent 看齐；派活能带更多有效上下文；子 agent 不用重新探索。

方案二单看理论是解三个问题的绝佳方案：常驻适合多轮循环，网状通信让编排最灵活。

第二部分（一）末
第一项实验怎么设计的？

实验一：去掉状态机，整个流程搬上 Team

去掉 /dev 命令和 workflow-engine，换成两个 skill 串联。

审查循环点对点直连：implementer 和 code-reviewer 互发消息对审，不经主 agent 中转。

七个角色：planner、implementer、reviewer（可多实例）、test-planner、test-engineer、explorer、guardian。

产物驱动状态：arch.md 不存在就从头开始；plan.md 存在就直接执行。

实验目录：experiments/2026-05-29-team-driven-dev（五月底）。设计在纸面上很美，实跑下来提交历史里全是补丁。

每一条提示词补丁，都是一次失败会话换来的；第四类的坑没有文档，全靠翻源码和实机踩坑。

第二部分（二）第一类、第四类
栽得最狠的一个（第二类）

每分钟催一次，planner 输出缩到 1

主 agent 约一分钟催一次 planner，而 planner 单轮热身就要超过一分钟。

主 agent 把它误判成「Team 在 resume 后失效」，重建团队接着催——活锁自己养活自己。

实跑约 2.5 小时的真实需求，planner 反复「莫名 idle」，产不出 plan.md。用 tracesift 解析会话记录才挖到根因。

planner 的原话：「我的 skill 加载和验证查询又被消息打断了。」

三条铁律（后来都进了 skill）：不催正在工作的 agent，只认显式 DONE/BLOCKED，idle 是正常态（PROTOCOL-A）；planner 这类角色任务来了一次性 spawn、自包含干完；测试断言从架构文档的验收标准提前冻结，实现完成后只填占位符。

第二部分（二）第二类
不信状态符号
信超时有没有消息（卡死判据）
不信活体成员还在（进程内成员随主进程消亡）
信磁盘上的 arch.md / test-plan.md，失联就无损重建成员
限流退避重试同一成员，绝不换人
认证失效停手找人
实验一留下了什么？（第三类）

不信状态符号，信超时和磁盘产物

完整流程的编排没有推广：不是跑不通，是太脆，作者没信心交给其他同学用。

它留下了 agent-teams skill：从上百次失败会话里熬出来的运维知识库。

agent-teams skill 的内容：怎么读懂成员状态（idleReason 三态）；失败按 failureReason 语义分流；卡死判据用「超时没消息」；防消息风暴和中断活锁的通信纪律。

作者指出这几条纪律的共同点：全部是「不信声明，信事实」。

第二部分（二）第三类及末段
第二项实验怎么收窄？

只在测试流程用 Team，限定两个成员

这就是现在的 /module-test：spec 是「自带答案的交接物」，验证点矩阵早早冻结，是审查的权威基准。

测试红了且对应 spec 验证点，按代码 bug 处理，绝不软化断言求绿。

spec 里的协议锚点、读回方式、验证点矩阵全部代码核实过，不许留空。

主 agent 不中转、不代审，只按 agent-teams skill 监督进度、容错兜底。

作者跑了几十遍各类任务，有 agent-teams skill 和 test-generator skill 加持，能比较稳定地走完；还保住了 agent teams 最大的优点：随时能和任意 agent 直接对话、自由干预。

第二部分（三）
每轮评审 spawn 新 agent彻底解决「被上轮意见带着走」
常驻 reviewer（最终留下）评审时长和 token 消耗更省
常驻的代价复审时只盯上轮问题，审不全
作者的判断agent teams 方向是对的；当前实现是残缺的
作者做了什么取舍？

留下常驻 reviewer，是明知有损的取舍

残缺在于：模型没被训练过这套机制，工具的提示词和行为对 LLM 不友好。

skill 能缓解机制的不完善，缓解不了机制的残缺。

第二部分（三）末段
1遥测原文：claude code 用隐蔽手段检测使用者是否来自中国，命中后在提示词和工具调用里投毒（细节原文不展开）
2UTF-8 损坏37 份中文产出里 36 份损坏、累计 370 处 U+FFFD；CLI 拼接工具调用参数时按字节切断了多字节字符
311 小时空转只读探索任务：6556 次工具调用、1.23 亿 input token，一无所获；203 轮压缩 = 203 次从头再来
「残缺」缺在哪？

三起事故都在黑盒里，作者改不了

作者的答案：缺在对 runtime 没有主权。

空转的根因之一：压缩摘要把「生成摘要」当成用户请求，「当前进度」「待办事项」两节常只剩标题。

11 小时空转的四个因素：max_turns 限额没生效；压缩阈值卡在 100K，模型 200K 的窗口只用了一半；压缩摘要的问题（见卡面）；于是每轮压缩后 agent 都失忆，从同一组关键词重新 Grep。完整复盘见团队博客《一个 agent 空转 11 小时的复盘》。

遥测事件直接动摇了「把生产流程建在一个黑盒 CLI 上」的信任基础。这是原文作者的说法，本页未核实。

第二部分（四）
三起事故要求的可替换性，一层比一层深
1工具参数拼接UTF-8 按字节切断这种事，要能自己接管那段代码（最外层，多数底座够得着）
2注入与遥测模型看到的每一样东西，都能按来源回看（审计的底线）
3上下文压缩压缩策略能整个换掉，不用猜阈值和摘要模板（最深，长在 agent loop 里）
自建 runtime，选哪个底座？

选型的真问题是主权的边界划在哪

不是「选哪个产品」；落到实处，就是插件化能划到哪一层。

codex 暴露了更隐蔽的问题：开源不等于主权。

作者摆开的选项：从 trpc-agent-go 写起（真重复造轮子）；基于 trpc-agent-go 薄封装（必然有别的团队在做）；基于 claude/codebuddy 的 agent SDK（底层还是黑盒）；codex CLI / SDK（开源可定制，但体量大）；pi agent；DeepSeek Harness。

codex：新版多 agent 通信把子 agent 任务载荷加密，只有 OpenAI 服务端解得开；子 agent 换别家模型就跨不过去，本地调试看不到真实任务文本。作者称之为「仓库开着，协议锁着」。

pi 把 loop 和压缩策略留在 core 里；DSH 连这两样都推成插件，元框架只管装卸，模型看到的一切进 append-only 会话日志。

pi agent 先动作者跟了几个月、上手试过；扩展门槛低；定位重心是上下文治理
DeepSeek Harness 跟进「一切皆插件」，连 loop 都能换；但作者手上只有一篇官方博客

原则元框架只管装卸，能力全部做成可替换的插件
深入一层：先用哪个？

按证据强度排序：pi 先动，DSH 跟进

这是作者的计划，不是已做到的结果：真正的垂类扩充还没排上工期。

作者的理由：核心插件和基础接口还在快速迭代，现在把整条生产流程押上 DSH，等于拿生产环境替它做测试。
